# 합성 평가 데이터셋 품질 검토

최초 검토일: 2026-10-06 · 수정 전 revision 1의 기록 · 작업 ID: W0-SPEC · 상태: 자동 대조 및 검토 의견 작성, 사용자 확정 전

> 이 문서의 발견 사항·수치는 수정 전 snapshot이다. 본문·정답은 이후 revision 2로 보완했다. 최신 상태는 [보완 결과](../reviews/REMEDIATION-2026-10-06.md)와 [현재 자동 검사 결과](../reviews/audit-results-current.json)를 확인한다. 아래 92건은 최초 검사 수치이며 현재 입력과 같은 해시가 아니다.

대상은 `data/reference/manifest.yaml`의 원본 PDF 12건과 이 폴더의 합성 본문·정답 6쌍이다. 기준은 [데이터셋 계획](../../../docs/dataset-plan.md), [사양서 골격](../../../docs/spec-sheet-skeletons.md), [프로젝트 계획 H3·평가 계획](../../../docs/spec-bridge-project-plan.md), [D-003](../../../docs/decisions.md)이다.

**판단: 속성·표기 변형을 시험하는 초기 합성 자료로 활용할 수 있다. 정식 평가의 고정 정답으로 사용하기 전에는 의미가 모호한 라벨과 채점 정책을 보완해야 한다.** 실제 문서의 레이아웃 난이도와 제품군 다양성은 충분히 반영하지 못했다. 이 판단은 데이터 품질 검토이며 추출 모델의 성능 결과가 아니다.

## 1. 검토 방법과 확인 범위

원본과 합성값이 같은지는 합격 기준으로 삼지 않았다. 프로젝트가 원본에서 가져오도록 정한 것은 속성 구성·표기·레이아웃이며, 제조사·형식명·수치는 합성값이기 때문이다.

1. 원본 12건의 해시·쪽수·크기를 manifest와 대조했다.
2. PDF 텍스트를 로컬에서 추출해 핵심 표기와 정의를 확인했다. 아래 페이지는 모두 **1부터 시작하는 PDF 페이지**다.
3. REF-PUMP-01 p.4, REF-SEP-01 p.5, REF-TC-01 p.2는 렌더링 화면도 확인했다. 나머지 페이지의 시각적 레이아웃은 전수 검토하지 않았다.
4. 합성 본문은 `.spec.md`의 첫 두 `---` 사이만 대상으로 삼았다. 정답의 문자열·라벨·단위가 지정한 절 또는 표 행에 있는지 대조했다.
5. 값의 의미, 환산, 관계, 라벨 누락, 평가 누수와 시험 범위는 별도로 검토했다.

재현 명령:

```bash
python data/eval/reviews/review_dataset.py
```

사용한 환경은 로컬 `python`의 PyYAML·pypdf다. 검증 스크립트는 [review_dataset.py](../reviews/review_dataset.py), 최초 실행 결과와 당시 본문·정답 해시는 [audit-results-2026-10-06.json](../reviews/audit-results-2026-10-06.json)에 있다. 현재 스크립트는 revision 2로 갱신되었으며 위 명령은 최신 후보셋을 검사한다. 최초 검사 수치는 날짜가 붙은 JSON에 보존되어 있다. 아래 의미 검토와 원본 표기 대조를 자동 판정하지 않는다.

원본 문장·사양표·그림·실제 모델 수치는 새 산출물에 복사하지 않았다. 원본과 합성 본문·정답 및 사용자 서명 필드는 수정하지 않았다.

## 4. 정식 채점 전에 해결할 사항

### P1-01. 2S의 `bhp` 정의가 입력 본문에 없다

- 위치: HW-2S-001.spec.md 3.1, 설계 메모; answer.yaml `rated_power`.
- 원본 REF-2S-01 p.23은 해당 문서의 BHP를 **metric horsepower**로 정의하고 `0.7355 kW` 계수를 사용한다. 합성 설계 메모는 **기계식 마력**의 `0.7457`을 선택했다.
- 합성 계산은 `20,115 × 0.7457 = 14,999.7615 kW`이며 대표값 15,000과 상대오차 약 0.00159%로 정답의 0.1% 허용오차 안이다. 그러나 원본의 정의를 적용하면 `14,794.5825 kW`가 되어 약 1.36945% 차이가 난다.
- 따라서 합성값의 산술 오류로 단정할 수는 없지만, 현재 입력만으로 환산 기준이 유일하지 않다. 설계 메모는 추출기에 전달하면 안 되는 영역이다.
- 조치 제안: 합성 본문에 기계식 마력 환산 기준을 짧게 명시하고, 단위 정책과 함께 정답을 고정한다. 원본을 따른다고 주장하려면 값·정답도 함께 재설계한다. 원본의 특정 정의를 모든 문서의 bhp에 일반화하지 않는다.

### P1-02. `Weight`·`Net weight`를 `dry_weight`로 확정할 근거가 부족하다

- 위치: COMP·TC 4.2의 `Weight`, SEP 4.2의 `Net weight` → 모두 `attributes.dry_weight`.
- 단위 kg는 일치하지만 건조 중량이라는 의미는 본문에 없다. REF-COMP-02 p.7은 표준 유닛의 모터·마운팅 범위를 설명하고, REF-SEP-01 p.5는 모듈 중량에 공급 펌프·히터 등이 포함됨을 각주로 명시한다. REF-TC-01 p.2는 `Weight`라고 표기한다.
- 따라서 Weight/Net weight가 언제나 Dry weight의 동의어라는 규칙은 이 근거로 확정할 수 없다. SEP의 치수·중량이 분리기 단품인지 공급 모듈인지도 입력에 명시하는 편이 좋다.
- 조치 제안: 가상 문서의 본문에 건조 상태와 포함 구성품을 명시하거나, W1에서 일반 중량 및 중량 기준을 표현하도록 정답·스키마를 맞춘다. 단어 치환만으로 의미를 고정하지 않는다.

### P1-03. SEP의 정상 조건부 값이 함정에도 등록되어 있다

- 위치: `rated_throughput.conditional_values`의 2,100 l/h와 `distractors`의 동일 문자열.
- 이 값은 정상적인 추가 조건의 정답이다. 380 cSt 대표값으로 대체하거나 E5 불일치로 판정하는 것은 잘못이지만, 700 cSt 조건을 보존해 추출하는 것은 맞다.
- `ANSWER-KEY.md`의 함정 정의는 “추출하면 안 되는 값”이므로, 현재 설명대로 일반 FP 평가를 구현하면 올바른 추가 추출을 오답 처리할 수 있다. TC 회전수, COMP 기준 온도, 4S 주파수도 해당 스키마의 비대상 값이며 본질적인 오류값은 아니다.
- 조치 제안: 조건부 값은 정답으로 채점하고, 함정은 **어떤 속성·클래스·조건으로 잘못 매핑했는가**로 평가한다. 대표값 정책과 조건부 값의 TP/FN 집계 단위를 평가 전에 고정한다.

### P1-04. “모든 출현”을 평가하기에는 일부 라벨이 빠져 있다

- PUMP `medium`: 표의 `Seawater`만 기록되어 있고 1.3의 `seawater cooling service`, 1.4의 `Main seawater cooling system`은 없다.
- COMP `cooling_type`: 표의 Cooling과 3.2는 기록되어 있지만 1.3의 `Air-cooled`, 표 1행의 `air-cooled`는 없다.
- SEP의 heavy fuel oil은 1.4·표 Application·처리량 조건에도 등장한다. 직접 값의 출현만 셀 것인지, 다른 속성 문구 안의 의미 출현도 셀 것인지 기준이 필요하다.
- 조치 제안: 단순 문자열 출현과 의미상 속성 출현을 구별하고 정책에 맞춰 전수 라벨을 보완한다. 이번 92건 검사는 **이미 기록된 출현의 존재 검사**다. E5 출현값 회수율의 완전한 정답이라는 증거가 아니다.

### P1-05. 현재 파일을 그대로 입력하면 평가 정보가 노출된다

- `.spec.md`의 제목에 클래스 약칭이 있고, 뒤의 설계 메모에는 V1·관계·정규값·함정·계산식이 있다. 파일명도 PUMP/COMP/2S/4S/SEP/TC를 구별한다.
- 이 폴더 전체에는 정답 YAML·관찰 메모·이 보고서가 함께 있다. 일반 Markdown glob으로 문서를 읽으면 평가기 자료가 입력에 섞일 수 있다.
- 조치 제안: 렌더링 시 첫 두 구분선 사이의 기술 사양 본문만 사용하고, 추출기에는 중립 문서 ID와 본문/렌더링 파일만 전달한다. 메타데이터·정답·설계 메모는 평가기에서만 읽는다. 본문의 정상적인 제품 설명은 분류 단서로 유지한다.

| P2-08 | TC 속성 수가 7개로 목표 8~12개보다 적음 | D-002의 목표와 차이를 W1에서 검토한다. 개수를 맞추기 위해 근거 없이 속성을 추가하지 않는다. 현재 모두 잠정 스키마다. |
| P2-09 | V1의 개별 출처와 제조사명 비중복 확인 기록이 없음 | 관찰 문서의 묶음 참조를 넘어 변형별 source ID·페이지를 연결한다. 가상 회사명의 실제 회사 비중복 여부는 이번 로컬 검토에서 확인하지 않았으므로 미확인으로 둔다. |

`missing_required: []`와 `expected_status: pass`도 W1 온톨로지가 확정되기 전의 초안 기대값이다. 현재 저장소에는 온톨로지 정의 파일이 없으므로 클래스·속성 ID, 열거값, 필수 속성을 스키마로 검증하지 못했다.

## 7. 평가에 사용할 때의 순서

1. P1-01~05의 의미와 입력·채점 정책을 정하고 필요한 본문·정답을 함께 수정한다.
2. W1에서 클래스·속성·조건·중량 기준·단위 정책을 온톨로지와 대조하고 잠정 정답을 확정한다.
3. 기술 사양 본문만 DOCX/PDF로 만들고 추출 텍스트와 정답을 다시 대조한다. `pdf_page`는 실제 생성 파일 기준으로 채운다.
4. 사용자가 검토 후 `reviewed_by`를 작성한다. 자동 검사는 서명을 대신하지 않는다.
5. 추후 추출 시스템이 준비되면 프로젝트의 A~D 구성으로 G1/G2·단위/위치 정확도·정상 문서 오탐 수를 별도 보고한다. 대표 속성은 현재 55개지만 조건부 값·복수 출현·범위/치수 객체의 집계 정책을 먼저 고정해야 한다.

이번에 수행한 것은 **원본 대조와 데이터셋 품질 검토**다. 모델 추론, 추출 F1, 클래스 매핑 정확도, 오류 검증 재현율, 중복 검사 성능은 **미실행**이다. 사용자 승인이나 CP-S1~S4 통과를 의미하지 않는다.
