# spec-bridge

선박 기자재 제품 사양서(PDF·DOCX·XLSX)를 읽어 **간이 온톨로지에 맞춘 제품 정보로 만들고**, 검증·중복 검사를 거쳐 **담당자 검토 뒤에 등록**하는 로컬 도구입니다. 로컬 모델(Ollama)로 동작하고, 등록되는 모든 값은 원문 위치나 사람 수정 기록을 근거로 가집니다.

> **합성 데이터 고지** — 저장소의 사양서, 제조사, 제품, 수치는 모두 이 프로젝트가 만든 **합성 데이터**입니다(`origin: synthetic`). 실제 제조사·제품·규격 값이 아닙니다. 온톨로지의 클래스 구조와 필수 정책도 프로젝트가 정한 합성 등록 정책이며, 업계 표준이나 법적 요건이 아닙니다. 실제 제조사 문서는 레이아웃·속성 이름 참고용으로만 로컬에서 읽었고, 저장소에는 넣지 않습니다(목록만 [`data/reference/manifest.yaml`](data/reference/manifest.yaml)).

## 문제

기자재 사양서는 제조사마다 표, 문단, 비고 형식이 다릅니다. 값 하나에도 **기준·조건·범위**가 붙습니다. 예를 들어 같은 "30 bar"도 최대 압력인지 사용 압력인지, 어떤 측정 기준인지에 따라 다른 사실입니다. 규칙 코드로 표기 변형을 하나씩 막으면 규칙이 끝없이 늘어나고, LLM에만 맡기면 문서에 없는 문맥을 지어냅니다.

## 해결 흐름

```
사양서 업로드
  → 파싱(Docling·openpyxl·python-docx, 블록마다 원문 위치)
  → 클래스 분류(LLM)
  → 값 추출(LLM, 원문 그대로) → 결정론 정규화(단위·형식·사전)
  → 값마다 문맥 해석: 해결 사례 검색(RAG) + LLM + 코드 검증(근거 구절이 원문에 있어야 통과)
  → 검증(필수 누락·단위·형식·허용값·불일치) + 중복·유사 검사
  → ⏸ 담당자 검토(원문 하이라이트, 수정, 확인, 보강 요청서)
  → 등록(SQLite + 표준 JSON) 또는 기존 제품에 연결
```

- **역할 분담**: LLM은 해석(비고 → 어휘), 코드는 측정·검증, 지식은 데이터(해결 사례 KB)가 맡습니다.
- **사람이 마지막에 결정합니다.** 시스템은 빠진 값을 채우지 않고 보강 요청 목록을 만듭니다. 담당자의 수정은 원문 위치와 사유를 함께 기록하고 같은 정규화·검증을 거칩니다. 다만 입력값이 원문과 같은지는 자동으로 보장하지 않습니다. 자동 병합은 하지 않습니다.
- **오프라인**: `OFFLINE=1`이면 루프백이 아닌 모델 서버를 거부합니다. 시연 중 앱과 모델 서버의 외부 연결은 0으로 관찰됐습니다([보고서 §9](docs/reports/w6-final-evaluation.md)).

## 최종 결과 (동결 시스템, 로컬 `exaone3.5:7.8b`)

사실 F1은 정규화한 값과 문맥(기준·조건·범위)이 정답과 모두 같아야 맞는 것으로 칩니다. 테스트 분할의 최종 평가는 시스템을 해시로 동결한 뒤 구성마다 한 번 실행했습니다. 개발 중에는 입력 파싱 점검과 제한된 정답 접근 예외가 있었고, 쓰지 않고 폐기한 사실까지 D-023·D-024·D-028에 기록했습니다.

| 구성 | 개발 F1 (24건) | **테스트 F1 (16건)** | 테스트 문맥 키 (/72) | 지어낸 문맥 | 수기 사양서 F1 (6건) |
|---|---|---|---|---|---|
| R 규칙 기준선 | 0.551 | 0.521 | 0 | 0 | 0.097 |
| E0 LLM, 사례 없음 | 0.573 | 0.495 | 4 | 46 | 0.563 |
| **E1SV LLM + 사례 검색 + 검증** | **0.946** | **0.913** | **62** | **8** | 0.549 |

| 목표 (테스트 E1SV) | 기준 | 값 |
|---|---|---|
| G1 사실 F1 | ≥ 0.90 | 0.913 |
| G2 분류 top-1 | ≥ 0.95 | 1.000 |
| G3 검증 재현율 | ≥ 0.95 | **0.875 (미달)** — 추출 누락 6건이 원인 |
| G4 중복·유사 재현율 / 정밀도 | ≥ 0.90 / ≥ 0.80 | 0.938 / 1.000 |

- **읽을 때 함께 볼 한계**: 개발·테스트 문서는 같은 합성 생성 규칙에서 나왔습니다(계열로만 분리). 테스트는 16건이고 모델은 하나입니다. G2·G4의 높은 값에는 이 데이터의 지름길(키워드 분류, 모델명 접두사로 유사 판정)이 크게 작용합니다([모델·데이터 카드 §6](docs/model-data-card.md)).
- 사전 등록 기준(D-080)은 테스트에서 모두 성립했습니다(사용자 판정). E1SV−E0 문맥 키는 +58이고 95% 구간은 [46, 71]입니다. E1SV−R 사실 F1은 +0.392이고 구간은 [0.329, 0.462]입니다.
- **수기 사양서에서는 한계가 드러났습니다.** F1이 0.549이고 문맥 키는 13개 중 1개를 맞혔습니다. 놓친 사실 28개 중 15개는 정규화 사전 밖 표기(`t`, `barg`, `Seawater` 등)였고, 나머지는 문서 구절형 범위와 조건 해석 실패, 추출 누락입니다.
- **평가 뒤 보완(동결 평가 성능과 별개)**: 사전 밖 표기를 검토 화면에서 담당자에게 알리는 기능을 추가했습니다(D-091). 같은 수기 오답으로 확인한 사후 결과이며 독립 평가가 아닙니다. 사전에 용어가 정해진 속성만 다룹니다.
- 전체 비교표, 오답 분석, 한계, 재현 명령: [W6 최종 평가 보고서](docs/reports/w6-final-evaluation.md). 평가 실행의 예측·점수는 `data/eval/w6-runs/`에 있어 모델 없이 다시 채점할 수 있습니다.
- 테스트 커버리지 91%(문장 기준). GitHub Actions(모델 서버 없는 검사)는 첫 실행에서 통과했습니다(보고서 §10).

## 빠른 시작

```bash
uv sync --frozen
uv run docling-tools models download layout tableformer -o var/models/docling
ollama pull exaone3.5:7.8b
ollama pull bge-m3
npm --prefix web ci
npm --prefix web run build
OFFLINE=1 SPEC_BRIDGE_APP_DIR=var/app uv run uvicorn spec_bridge.api.app:app --host 127.0.0.1 --port 8010
```

브라우저에서 `http://127.0.0.1:8010/`을 열고 `data/synth/inputs/`의 사양서를 올립니다. 모델 다운로드(Docling·Ollama)만 네트워크를 쓰고, 그 뒤로는 오프라인으로 동작합니다. Docling 모델이 없으면 PDF 처리가 거부됩니다(파싱 중 자동 다운로드 없음). 검사·W6 평가 재현·오프라인 확인 방법은 [실행 가이드](docs/run-guide.md)에 있습니다.

## W6 이후 추가한 기능

W6 평가 수치와 동결 기록에는 영향이 없습니다(`freeze verify`·`manifest check` 일치).

- **문맥 편집**(D-100): 검토 화면에서 담당자가 사실의 기준·조건·범위를 한 번에 한 축씩 고칩니다. 단어는 온톨로지 어휘에서만 고르고, 범위 구절은 문서에 있어야 합니다. W6 문맥 오답이 이 수정으로 정답 문맥에 닿는지 사후 확인했습니다(테스트 9/9, 수기 11/11, 독립 평가 아님).
- **BOM 1단계**(D-101): Excel·Markdown BOM 표의 행을 제조사·모델로 기존 제품에 식별하고 `has_component`(공급 범위 포함) 관계를 추가합니다. 명령줄 미리보기 뒤 `--apply`로 저장하고, 찾지 못한 행은 검토 대기로 남깁니다. 합성 BOM 4건 12행이 정답과 같게 식별됩니다(기능 확인).
- **BOM 화면**(D-103): 검토 화면의 "BOM 연결"에서 업로드 → 미리보기 → 적용합니다. 검토 대기 행은 담당자가 같은 종류의 등록 제품을 사유와 함께 지정하고, 제품 상세에 구성품과 상위 제품이 보입니다.

- **G5 후속 실험**(D-107~D-111, [보고서](docs/reports/g5-followup-bom.md)): 표기가 제각각인 BOM 행을 등록 제품에 연결하는 실험입니다. 테스트 80행(합성)에서 LLM + 코드 검증(C·E)이 규칙(R)보다 정확도가 +0.31 높았고(1.000 대 0.688) 잘못 연결은 0입니다. 다만 사후 진단에서 코드 검증만으로도 모든 행이 풀려, 이 차이를 LLM의 해석 기여로 볼 수 없습니다(수락 정책의 차이, D-113·D-114). 해결 사례 검색(E)은 C보다 낫지 않아 사전 등록 기준 (c)가 미달이고, 가설은 불성립입니다. 결론 범위는 선박 기계 목록에서 관찰한 표기 패턴 안입니다.
- **BOM 후보 제안**(D-112): BOM 화면의 검토 대기 행에서 "제안 받기"를 누르면, 로컬 모델이 후보를 고르고 코드가 모델 코드와 클래스를 확인한 제안이 지정 양식을 채웁니다. 담당자가 "지정"으로 확정하고, 자동 연결은 하지 않습니다.

## 이후 확장 (미구현)

- **BOM 행에서 새 제품 등록**: 하지 않습니다. 등록되지 않은 구성품은 사양서로 먼저 등록합니다(NFR-07).
- **호스트 연동**: Atlas CMMS([설계안](docs/host-integration-design.md))와 연동합니다. 대안 호스트 openMAINT는 조사만 해 두었습니다.
