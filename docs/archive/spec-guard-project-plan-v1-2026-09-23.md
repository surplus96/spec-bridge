## 🧭 개발 헬퍼 모델 운영 지침 (Sonnet 5용 — 작업 시작 전에 반드시 읽을 것)

> 이 장은 이 문서를 받아 개발을 돕는 **헬퍼 모델(기본: Claude Sonnet 5)** 에게 주는 지침이다. 헬퍼는 작업 중 이 지침에 따라 사용자에게 **안내·경고·중단**을 해야 한다.
> 배경: Sonnet 5는 이 계획 작업의 대부분(표준 스택 구현·테스트·리팩터링)에 충분하다. 다만 ① 미묘한 설계·통계 오류를 놓칠 수 있고 ② **도메인 사실 오류는 어떤 모델을 써도 사라지지 않는다.** 그래서 정해진 시점에만 Opus급 모델로 교차 검토하고, 도메인 사실은 모델이 아니라 **절차**로 막는다.

### H1. 작업 진행 규칙

1. **한 번에 작업 ID 하나만** 진행한다 (예: `1-2`, `MRO-FR-03`, `FR-05`). 시작할 때 해당 작업의 목표와 완료 기준(DoD)을 한 줄로 다시 말하고 시작한다.
2. **교육 모드**: 사용자가 직접 타이핑하며 이해하는 방식이다. 전체 코드를 완성해 주지 말고 **단계별 설명 + 참고 코드 조각**을 제시한다. 사용자가 명시적으로 요청할 때만 전체 구현을 보여준다.
3. **완료 선언 조건**: DoD를 명령 실행 결과(테스트, 린터, 평가 수치)로 확인하기 전에는 "완료"라고 말하지 않는다. 확인하지 못했으면 "미확인"이라고 명시한다.
4. **범위 고정**: "선택"으로 표시된 작업은 사용자가 지시할 때만 시작한다. 새 아이디어는 작업하지 말고 문서의 "이후" 목록에 제안만 한다.
5. **커밋·푸시·외부 전송**은 사용자가 요청할 때만 한다.
6. 계획과 다르게 진행해야 하면 먼저 차이와 이유를 알리고 승인을 받는다.

### H2. 교차 검토 운영 (Sonnet 5 → Opus급)

**정기 체크포인트**: 이 문서의 🔶 표시(H4 체크포인트 표와 각 주차 DoD 옆)에 도달하면 헬퍼는 다음 작업으로 넘어가지 말고 아래 절차를 따른다.

1. 사용자에게 알린다: `🔶 교차 검토 체크포인트 [ID] 도달 — 다음 단계 진행 전 Opus급 모델 검토를 권장합니다.`
2. **검토 패키지**를 작성해 제공한다 (사용자가 복사해서 상위 모델에 전달하는 용도):
   - 배경 요약 (5줄 이내): 무엇을 왜 만들었는가
   - 검토 대상: 파일 경로·핵심 코드 발췌 또는 diff, 산출된 수치
   - 체크포인트 표의 **검토 질문 목록** + 헬퍼 스스로 확신이 낮은 지점
   - 전제·가정 목록
3. 검토 결과를 사용자가 가져오면 `docs/decisions.md`(결정 기록)에 **날짜 · 체크포인트 ID · 지적 사항 · 조치 · 미해결 항목**을 남기고, 지적 사항을 해결한 뒤 다음 작업으로 진행한다.
4. 헬퍼는 **자기 작업을 스스로 "검토 통과"로 판정하지 않는다.**

**수시 에스컬레이션 트리거** — 체크포인트가 아니어도 아래 상황이면 즉시 알리고 교차 검토를 제안한다.
- 같은 버그를 두 번 고쳤는데도 재현될 때
- 결과가 **너무 좋을 때** (예: 재현율이 기준선보다 0.3 이상 급등, 정확도 1.0) → 누수·평가 오류를 먼저 의심
- 비동기 루프·동시성·트랜잭션 관련 코드를 수정할 때
- README·케이스 스터디에 들어갈 수치나 주장을 새로 만들 때
- 되돌리기 어려운 변경 (DB 스키마 변경, 데이터 삭제, 이력 재작성)

### H3. 모델을 바꿔도 해결되지 않는 위험 — 도메인 사실 프로토콜

**위험**: 규칙 조항 번호, 개정판, 규제 수치 한도, 제출도서 항목, 장비 파라미터, 정비 절차는 모델이 **그럴듯하지만 틀리게** 말할 수 있다. 상위 모델로 바꿔도 이 위험은 남는다. 이 오류는 테스트를 통과한 상태로 결과물에 들어가서 포트폴리오의 신뢰를 무너뜨린다.

**헬퍼가 지킬 규칙**
1. 규제·규격·장비 관련 수치나 조항을 **기억에 의존해 사실처럼 쓰지 않는다.** 이번 세션에서 사용자가 제공한 원문이 없으면 `[미검증]` 태그를 붙이고, 확인 방법(어느 문서의 어느 부분을 볼지)을 함께 안내한다.
2. 도메인 데이터가 필요하면 먼저 사용자에게 **원문 발췌(문서명·판본·페이지 포함)** 를 요청한다. 헬퍼는 붙여 넣은 원문을 **요약·구조화만** 한다.
3. 레지스트리·마스터 데이터 항목은 `source`(문서명), `edition`(판본), `location`(페이지·조항), `verified_by`(검증자) 필드가 없으면 만들지 않는다. `verified_by`는 **사용자만** 채운다.
4. 테스트에 쓰는 규제 수치는 테스트 코드에 직접 적지 말고 **레지스트리·마스터 데이터에서 읽어 온다.** 그래야 원문이 바뀌거나 오류가 발견됐을 때 한 곳만 고치면 된다.
5. **개발 중 인용 가드**: 코드·문서·프롬프트에 등장하는 조항 ID는 레지스트리에 존재해야 한다. 헬퍼는 새 조항 ID가 등장하면 레지스트리 존재 여부를 확인하고, 없으면 경고한다.
6. 합성·가정 데이터는 파일과 README에 **합성/가정임을 명시**한다. 실제 데이터처럼 서술하지 않는다.
7. 확신이 없으면 "모른다"고 말하고 확인 절차를 제안한다. 추측으로 빈칸을 채우지 않는다.

## 1. 개요

### 1-1. 한 줄 정의

**SpecGuard**: 조선 기자재(주기관) 구매사양서(POS)를 **근거 조항을 인용하며 생성하고**, 규칙 위반·불일치·누락을 **검증하며**, 설계 변경 시 **영향받는 조항을 찾아 수정안(redline)을 제시하는** 로컬 우선 에이전트.

### 1-2. 문제와 동기

- 한화오션은 Cohere와 POS 생성·검증 PoC를 진행 중이며, 첫 대상은 주기관 사양이다. 범위는 기존 선박 데이터 기반 생성, 사양 변경 반영, 표준 대비 검증이다.
- 조달 현업에서는 벤더 데이터와 사양 관리가 엔지니어 업무의 큰 비중을 차지하고, 수작업 검토 과정에서 불일치가 생긴다.
- 방산·조선은 보안 요구 때문에 외부 클라우드 사용이 제한된다 → **오프라인 동작**이 필수 조건.

### 1-3. 목표 (성공 기준)

| # | 목표 | 측정 |
|---|---|---|
| G1 | 결정론 유형 결함(규칙 위반·수치 오류·내부 불일치) 검출 | 재현율 ≥ 0.95 |
| G2 | 모든 판정에 근거 조항 인용, 허위 인용 없음 | 허위 인용 0건, 인용 정확도 ≥ 0.85 |
| G3 | 설계 변경의 영향 조항 식별 | 재현율 ≥ 0.9 |
| G4 | 오프라인 모드 완전 동작 | 외부 네트워크 호출 0회 (테스트로 증명) |
| G5 | 설계 선택을 수치로 정당화 | 4단계 비교 실험 표 |

### 1-4. 범위

| 포함 (MVP) | 제외 |
|---|---|
| 기자재 1종: **2행정 주기관** | 도면·CAD, 3D 모델 |
| 선박 케이스 4종 (합성) | 실제 메이커 견적 비교·가격 |
| 규칙 조항 약 30개 (MARPOL VI, IACS UR M44, KR/DNV 일부) | 상업 조건(보증·납기·지불) |
| **POS 생성 언어: 영문(확정)**, 한국어 규칙(KR)은 검색 대상으로만 지원 | 주기관 외 기자재 (확장 과제로 문서에만 언급) |
| 로컬 LLM 기본, 클라우드는 비교용 | 파인튜닝 |

### 1-5. 명칭·표기 원칙

- "한화 공개 사례(Cohere×한화오션 PoC)에서 착안한 독립 프로젝트"로만 표기하고, 로고나 협업을 암시하는 표현은 쓰지 않는다.
- 합성 데이터임을 README 첫 화면에 명시한다.
- 메이커 PDF·규칙 원문은 저장소에 커밋하지 않고, 다운로드 스크립트와 출처만 제공한다.

## 2. 사용자 시나리오

**S1. 초안 생성** — 설계 엔지니어가 선박 케이스(선종, 운항해역, 선급, 연료)와 엔진 선정값을 입력한다 → SpecGuard가 8개 섹션의 POS 초안을 생성하고, 조항마다 근거(규칙 ID·조항 번호 또는 입력 파라미터)를 단다 → DOCX로 내보낸다.

**S2. 검증** — 기존 POS(합성 결함 포함)를 올린다 → 결함 목록이 심각도·유형·위치·근거 조항과 함께 표시된다 → 엔지니어가 결함별로 수용·기각·메모를 남긴다.

**S3. 설계 변경 반영** — "연료를 VLSFO에서 LNG 이중연료로 변경" 같은 변경 요청을 입력한다 → 영향 조항 N개와 각각의 수정안(redline)이 제시된다 → 엔지니어가 승인한 변경만 반영되고 변경 이력이 남는다.

### 4-4. 결함 분류와 주입 규칙

| 유형 | 정의 | 주입 방법 | 검출기 | 주입 비율 |
|---|---|---|---|---|
| D1 규칙 위반 | 적용 규칙 요구 미충족 | 적용 조건은 유지한 채 요구값 제거·변경 | 결정론 | 20% |
| D2 수치 오류 | 계산 한도 초과, 범위 이탈 | 보증값을 한도 초과로 변경 | 결정론 | 20% |
| D3 내부 불일치 | 섹션 간 값 불일치 | 한 섹션의 값만 변경 | 결정론 | 20% |
| D4 필수 누락 | 체크리스트 항목 누락 | 제출도서·시험 항목 삭제 | 체크리스트 + LLM | 15% |
| D5 구판 인용 | 개정 전 판본 인용 | 판본 문자열 교체 | 레지스트리 | 10% |
| D6 변경 미반영 | 파라미터 변경 후 종속 조항 유지 | 변경 시나리오에서 종속 조항 일부만 갱신 | 영향 그래프 | 10% |
| D7 모호 문구 | 검증 불가능한 표현 | "필요 시 적절히" 등의 문구 삽입 | LLM | 5% |

**규모**: 케이스 4종 × 변형 10건 = POS 40건, 결함 약 200개 (문서당 3~7개). 이 중 D7과 인용 정확도 측정용으로 50건을 **직접 검토해 라벨을 확정**한다.

### 4-5. 규칙 카탈로그 형식 (YAML, 항목별 필드)

`rule_id` · `source_clause`(레지스트리 참조) · `kind`(computational / checklist / llm) · `applies_when`(적용 조건) · `check`(검사 내용 서술 또는 함수 이름) · `severity`(critical/major/minor) · `message`(메시지 템플릿)

**MVP 규칙 예시 (결정론)**
- **R-NOX-LIMIT**: 정격 회전수로 Tier 한도를 계산하고 보증 NOx 값과 비교
- **R-NOX-T3**: NECA 운항이면 Tier III 대응 기술 명시 필수
- **R-SOX-FUEL**: 운항해역별 황 한도 대비 연료 황 함량 확인, 스크러버가 있으면 예외
- **R-CONS-SMCR**: 모든 섹션의 SMCR 출력·회전수 일치
- **R-UNIT**: 출력 단위 혼용(kW/bhp) 금지
- **R-DOC-M44**: 제출도서 목록이 M44 필수 항목을 포함하는지 확인 (항목 매핑은 W1에서 확정)

## 5. 아키텍처

### 5-1. 설계 원칙

1. **수치·규칙은 코드가, 문장·해석은 LLM이** (uptime-copilot에서 검증된 원칙)
2. **스키마가 진실원천**: 문서는 스키마를 렌더링한 결과이고, 검증은 문서에서 추출한 값과 스키마를 비교한다
3. **인용 없는 판정은 판정이 아니다**: 모든 결함에 근거 조항 ID가 있어야 하고, 그 ID는 레지스트리에 존재해야 한다
4. **로컬 우선**: 클라우드는 비교 실험용 옵션

### 5-2. 구성요소

| 구성요소 | 역할 | LLM 사용 |
|---|---|---|
| Ingest | 규칙 PDF 파싱(Docling) → 조항 청킹 → 레지스트리·벡터DB 적재 | ❌ |
| Extractor | POS 문서에서 사양 값을 스키마로 추출 | ✅ (구조화 출력) + 정규식 보조 |
| Rule Checker | YAML 규칙 카탈로그 실행 | ❌ |
| Clause Judge | 누락·모호 문구 판정, 관련 조항 검색 후 인용 | ✅ |
| Citation Guard | 인용 ID 화이트리스트 검증, 실패 시 재시도 1회 후 기각 | ❌ |
| Drafter | 스키마 + 검색 조항 → 섹션별 문장 생성 (조항별 source_refs) | ✅ |
| Impact Analyzer | 파라미터→조항 의존 그래프(networkx) 탐색 → 영향 조항 → Drafter로 재생성 → 조항 단위 diff | 부분 |
| Orchestrator | LangGraph: 모드별(생성/검증/변경) 그래프, HITL 중단점 | — |
| Audit | 모든 호출·결정 기록 | ❌ |

### 5-3. 그래프 흐름 (모드별)

- **검증 모드**: 문서 입력 → Extractor → (병렬) Rule Checker ∥ Clause Judge → Citation Guard → 결함 통합·중복 제거 → **HITL(결함 확정)** → 리포트
- **생성 모드**: 스키마 입력 → 적용 규칙 선택(applies_when) → 섹션별 Drafter → 생성 결과를 검증 모드로 자가 점검 → 결함이 있으면 해당 섹션만 재생성(최대 2회) → DOCX
- **변경 모드**: 변경 요청 → 파라미터 diff → Impact Analyzer → 영향 조항 재생성 → redline → **HITL(조항별 승인)** → 새 판본 저장

### 5-4. 저장소 구조 (제안)

