# 문맥 편집 설계 (D-100)

2026-10-16 · 상태: **승인**(사용자 "권장안으로 전부 진행해줘", 결정 1~8 모두 권장안) · 순서 근거: D-099

**목표**: 검토 화면에서 담당자가 사실의 기준·조건·범위를 고칠 수 있게 한다. W5 결정 "문맥은 편집하지 않는다"(`registry/edits.py`)를 바꾼다. 값 수정과 같은 경로(정규화기 → 검증 → 이력)를 쓰고, W6 동결 기록과 재현 guard 파일은 바꾸지 않는다.

## 결정

| # | 결정 | 내용 |
|---|---|---|
| 1 | 범위 | 기준·조건·범위를 모두 고칠 수 있다 |
| 2 | 단어 축 | 온톨로지 어휘(`vocabularies.basis`, 조건의 token 축)에서만 고른다. 자유 입력은 거부한다. 기준의 `unknown`과 "비우기"는 축을 지운다 |
| 3 | 수치 조건 | `Normalizer.condition`으로 읽는다(`60 Hz`, `380 cSt at 50 °C`). 형식·단위·차원이 맞지 않으면 거부한다 |
| 4 | 근거 | 사유는 필수다. 범위 구절은 문서 블록에 있어야 한다(대소문자 무시, `has_token`). 기준·조건은 원문 일치를 강제하지 않는다(CP-S4 결정 5와 같은 정책) |
| 5 | 단위 | 수정 하나 = 축 하나 = 사유 하나. 화면은 여러 축을 고친 뒤 저장하면 축마다 수정을 차례로 보낸다 |
| 6 | 같은 사실 | 고친 결과가 다른 사실과 같아지면(속성·값·단위·문맥) 거부한다. 자동 병합은 없다 |
| 7 | 고친 뒤 | 검증을 다시 돌린다(E5가 생기거나 풀린다). 사실에 "수정됨", 해당 문맥 표시에 "확인함"을 붙인다 |
| 8 | 화면 | 값이 있는 축만 보이고 "축 추가"로 나머지를 고른다. 속성별 축 목록은 온톨로지에 없으므로 만들지 않는다(H3) |

## 형태

- `FactEdit(op="context", target="fact", index, axis, value_text, reason)`.
  - `axis`: `basis.<축>`, `condition.<축>`, `scope`
  - `value_text`: 단어, 수치 조건 문구, 범위 구절. 비우면 축을 지운다(범위는 `main_equipment`).
- 수정 기록(`HumanEdit`)은 기존 필드에 `axis`를 더한다. `outcome`은 `fact`다. 그래서 등록 저장소의 `human_edit` 근거 규칙이 그대로 적용된다.
- `ReviewPrompt.context_axes`: 축마다 종류(`token`·`quantity`·`reference_quantity`·`scope`), 고를 수 있는 단어, 쓸 수 있는 단위.
- `ContextHint.reviewed`: 그 사실에 문맥 수정이 있으면 참이다.

## 범위 밖

- 사실을 추가하면서 문맥을 함께 넣기(추가 후 문맥 수정 두 단계).
- 문맥 표시를 등록 차단 사유로 바꾸기(D-069 유지).
- W6 수치와 동결 기록의 변경. 바꾸는 모듈(`registry/edits.py`, `graph/`, `api/`, `web/`)은 guard 밖이다.

## 구현 결과 (2026-10-16)

- **결정 5 화면 변경**: 화면은 한 번에 한 축을 저장한다. 수정 명령은 작업자 스레드에서 처리되고 판본이 매번 오르므로, 여러 축을 연달아 보내려면 처리 완료를 기다려야 한다. 그래서 단순하게 두었다. 서버 규칙(수정 하나 = 축 하나)은 그대로다.
- **함께 고친 결함(등록 저장소 schema 3)**: `human_edits`의 `CHECK (op IN ('set','add','remove'))`와 `INSERT OR IGNORE`가 만나, 문맥 수정 기록이 **오류 없이 버려졌다**. 등록 사실은 그 수정을 근거로 가리키는데 수정 기록이 없는 상태가 된다(NFR-07 위반). API 테스트가 잡았다.
  - schema 3: `op`에 `context`를 더했다. schema 2 파일은 수정 표를 다시 만들고 기존 행을 옮긴다.
  - 삽입을 `ON CONFLICT(edit_id) DO NOTHING`으로 바꿨다. 같은 수정의 반복만 건너뛰고, 표 규칙에 어긋난 행은 오류가 된다.
- **사후 확인(독립 평가 아님)**: W6 실행의 문맥 오답에 이 기능을 적용할 수 있는지 확인했다. 짝지어진 문맥 오답(예측과 정답의 속성·값이 같고 문맥만 다름, 또는 값과 문맥이 함께 다름)마다 정답 문맥으로 가는 축 수정을 실제 `_context_value`에 넣었다.
  - 테스트 E1SV 9/9, 수기 E1SV 11/11이 문맥 수정만으로 정답 문맥에 닿는다(축 1~3개). `value_and_context` 2건은 값 수정도 함께 필요하다.
  - 수기 DOC-003 범위 1건은 문서에 적힌 구절(쉼표 포함)을 그대로 넣어야 받아들여진다.
  - 이는 "고칠 수단이 있다"는 확인이다. 담당자가 그 오답을 찾아낸다는 뜻은 아니다. 문맥 확인 표시는 거부된 제안이 있을 때만 뜬다(D-069).
