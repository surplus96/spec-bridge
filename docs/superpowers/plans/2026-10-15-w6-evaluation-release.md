# W6 평가·보안·공개 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: superpowers:executing-plans. 헬퍼가 스크래치에서 검증한 코드를 작업 트리에 직접 적용하고 설명한다(메모리 `education-mode-full-code`). 사용자는 LLM 실험, 서버, 설치, 녹화, 푸시를 직접 실행한다. 서브에이전트는 사용자가 요청할 때만 쓴다. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 고정한 시스템(코드·프롬프트·KB·채점기 해시)으로 **테스트 분할과 수기 사양서를 한 번만** 평가한다. G1~G5와 W4-R ③ "탁월"을 사전 등록한 기준으로 정직하게 보고하고, 오프라인 보장·실행 가이드·공개 문서를 갖춘 뒤 🔶 CP-S4에서 멈춘다.

**Architecture:** 평가 순서는 고정한다. ① 동결 전 정리 → ② 기준·구성·해시를 결정 기록으로 사전 등록 → ③ 개발 분할 재현 실행(동결 해시 확인) → ④ 테스트 분할·수기 사양서 단일 실행 → ⑤ 보고. ④ 뒤에는 결과를 보고 코드·프롬프트·KB를 고치지 않는다. 고치면 그 결과는 "사후 개선"으로 따로 표시하고 G 판정에는 쓰지 않는다.

**Tech Stack:** 기존(Python·uv·pytest·ruff·mypy, LangGraph, FastAPI, React·Vite) + Docker Compose, GitHub Actions(파일만 작성, 실행은 사용자 푸시).

**Spec:** [계획서](../../spec-bridge-project-plan.md) 1-3(G1~G5)·W6 표·CP-S4·6-2, decisions.md D-020(테스트 격리)·D-036(채점기 ID)·D-048/D-052(사전 등록 기준)·D-053(E1SV)·D-065·D-067·D-078, [W4-R 보고서](../../reports/w4r-rag-semantic-mapping.md) §7, [W5 보고서](../../reports/w5-review-ui-registration.md) §6.

## Global Constraints

- **테스트 분할은 ④에서 한 번만 실행한다.** 그 전에는 헬퍼가 테스트 문서·정답 내용을 읽지 않는다. 실행 뒤 오류 분석에서는 읽을 수 있지만, 그 뒤의 수정은 G 판정에 쓰지 않는다(D-020).
- **동결 대상**: 채점기 ID, 프롬프트 모듈 해시, RAG 모듈 해시, KB sha256, 온톨로지 sha256, 개발 사전 sha256, 모델(digest)과 옵션. ②의 결정 기록에 적고, ③·④의 `run.json`과 같은지 확인한다.
- **채점기 변경**: 테스트 분할 지원을 위해 채점 모듈을 고치면 채점기 ID가 바뀐다. 새 ID를 기록하고, 기존 개발 실행을 모두 재채점한다(D-036). 원 `metrics.json`은 덮지 않는다.
- **외부 전송**: 테스트 문서를 클라우드 모델로 보내는 행은 사용자 승인이 있을 때만 실행한다(결정 3). 저장소 공개와 푸시는 사용자가 한다.
- **H3**: 보고서·README에 장비 수치나 규제 해석을 새로 쓰지 않는다. 합성 데이터임을 첫 화면에 밝힌다.
- 완료 판정: `uv run pytest -q`, `uv run ruff check .`, `uv run mypy spec_bridge tests`, `npm --prefix web run check`, `npm --prefix web run build`. 포맷은 바꾼 파일에만 적용하고, 채점기 ID 고정 테스트를 유지한다.

## Review Focus

1. **실행 순서 위반**: 동결 기록(②)보다 먼저 만들어진 테스트 실행 폴더가 있으면 안 된다. 실행기는 동결 기록의 해시와 현재 해시가 다르면 테스트 분할 실행을 거부한다 → Task 1 테스트.
2. **분할 간 누수**: 테스트 실행의 정규화기·중복 판정은 테스트 분할의 등록 목록만 쓰고, KB는 개발 사례만 담는다(테스트 계열 0건) → Task 1 테스트.
3. **실패 문서를 분모에서 빼지 않기**: 파싱·분류 실패도 정답 사실을 모두 놓친 것으로 센다(W3 원칙). 수기 사양서 파싱 실패 포함 → Task 2·4 테스트.
4. **작은 표본의 과장**: 테스트 16건·수기 6건이다. 모든 수치에 문서 수와 부트스트랩 구간을 붙이고, 개발셋 대비 하락은 원인과 함께 그대로 보고한다 → Task 5 보고서 검토 항목.
5. **오프라인 보장의 범위**: 소켓 감시는 네이티브 확장과 자식 프로세스를 못 본다(CP-S3 R5). 오프라인 확인은 감사 기록과 OS 수준 관찰을 함께 쓰고 한계를 적는다 → Task 6.

### 결정 2: 테스트 분할 사전 등록 기준 (실행 전 고정)

D-052 기준을 문서 수에 맞춰 옮긴다. 비교 대상은 같은 동결 코드로 실행한 E0와 R이다.

| 기준 | 정의 | 판정 |
|---|---|---|
| (a) | E1SV − E0 문맥 키 TP의 95% 쌍체 부트스트랩 하한 > 0 | ① 효과 |
| (b) | E1SV 지어낸 문맥 ≤ 문서당 0.667 × 문서 수(개발 기준 16/24, 테스트 16건이면 ≤ 10) | ① 효과 |
| (c) | E1SV − R 사실 F1 하한 > 0 | ① 효과 |
| 목표권 | 문맥 키 TP ≥ 테스트 문맥 키의 51.5%(개발 50/97과 같은 비율) | ② 목표권 |
| ③ 탁월 | 테스트 분할에서 ①·②가 성립하고, 수기 사양서(결정 1이 A·B일 때)에서 (c)와 목표권이 성립 | ③ |

G1~G4는 계획서 목표를 그대로 쓴다(G1 사실 F1 ≥ 0.90, G2 top-1 ≥ 0.95, G3 재현율 ≥ 0.95, G4 R ≥ 0.90·P ≥ 0.80). 부트스트랩은 10,000회, seed 7, 문서 단위다.
