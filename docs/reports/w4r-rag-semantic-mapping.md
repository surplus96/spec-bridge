# W4-R RAG 기반 의미 매핑 — 개발 분할 결과

2026-10-13 · 작성: 헬퍼 모델 · 상태: **개발셋 결과 기록**(헬퍼는 가설 성립을 일반화해 판정하지 않는다. 판정은 사전 등록 기준 D-048·D-052에 따른다)

집계 수치만 싣는다(정답 내용 없음). 원자료는 `var/eval/<run_id>/`, `var/rag/`(재생성 가능, 커밋 안 함). 근거 결정: D-041~D-053.

## 1. 질문

W3~W4-1에서 값과 단위는 맞히지만 **한정 정보(기준·조건·범위)**는 맞히지 못했다. 규칙 기준선 R, zero-shot LLM C, 클라우드 모델이 모두 문맥 키 0~12/97에 그쳤다. 이 매핑을 코드 규칙으로 풀려 하면 표기 변형마다 규칙이 늘어난다. 이번 실험의 질문은 하나다(G5 핵심 가설, D-042).

> 코드 규칙으로 풀기 어려운 의미 매핑을, **검색된 해결 사례를 쓰는 LLM(RAG) + 코드 검증**으로 풀 수 있는가?

## 2. 설계 요약

```
C(optional)로 값 추출 ─▶ 값마다:
   질의(라벨 + 비고) ─▶ 하이브리드 검색(BM25 + bge-m3, 같은 계열 제외) ─▶ 해결 사례 3개
   ─▶ 프롬프트(어휘 정의 + 사례와 모범 답안 + 현재 줄) ─▶ 로컬 LLM(필드별 값 + 근거 구절)
   ─▶ 코드 검증(근거 구절 실재 · 어휘 · 수량 숫자 실재 · 단위 차원 · 범위는 비고에서만)
   ─▶ [E1SV] Self-RAG 지지 판정(지우기만 가능) ─▶ 결정론 정규화 ─▶ 사실
값 칸 하나가 두 속성에 연결되면 [E1SV] 검색 사례의 속성 투표로 하나만 남김
```

- **역할 분담**: LLM은 해석(비고 → 어휘), 코드는 측정·검증, 지식은 데이터(KB)가 맡는다(계획서 5-1 개정, D-042).
- **지식 베이스**: 개발 정답 사례 234개(12계열). 한정 정보가 있는 사례가 113개, "비워야 할 때"의 사례가 121개다. 근거 구절은 코드가 찾은 경우에만 채웠다(270필드 중 242). sha256 `cfc116a6…`(D-045).
- **LangChain 경계**: 검색기는 `BaseRetriever` 상속, 조합은 LCEL이다. LLM 호출은 기존 제공자를 `Runnable`로 감싸 감사 기록·오프라인 가드·결정성을 유지했다(D-043·D-046).
- **누수 통제**: KB는 개발 분할만으로 만든다(테스트 분할은 생성기가 거부). 평가 때는 질의 문서와 같은 계열의 사례를 검색에서 뺀다. 테스트 분할은 실행하지 않았다.

## 3. 검색 품질 진단 (생성 없이, D-047)

한정 정보가 있는 질의 113개, 같은 계열 제외. 적중 = 모범 답안이 질의와 완전히 같은 사례. **이론 상한은 0.814**다(다른 계열에 같은 답이 있는 질의가 92개).

- FAISS는 PyTorch(Docling)와 OpenMP 런타임이 충돌해 한 프로세스에서 쓸 수 없다. 운영 경로는 Chroma를 쓴다(D-044).

## 5. 확인된 것

1. **검색 사례의 효과는 크고 확실하다.** 같은 모델에 같은 질문을 하고 사례 유무만 바꿨을 때(E0 → E1) 문맥 키가 9 → 83, 지어낸 문맥이 60 → 27로 바뀌었다. 코드 검증에서 탈락한 필드도 730 → 433으로 줄었다.
2. **문제 분해만으로는 부족하지만, 분해는 원래 맞던 것을 지킨다.** E0은 문맥 없는 키 117/117을 유지했다. W4-1 필수형은 26/117로 무너졌던 것과 대조된다. 다만 문맥 키는 9개에 그쳤다.
3. **범위(scope)가 병목이었다.** 문맥이 있는 정답 키 97개는 모두 범위를 갖는다. E0은 범위를 25/97만 정확히 맞혔고, 사례가 이 병목을 풀었다.
4. **근거 구절 검증이 지어내기를 막는다.** E0에서 모델은 비고가 없는 줄에도 범위를 붙이려 했지만(198건), "범위는 비고에서만" 검증이 모두 걸렀다. 수량 조건의 숫자 실재 검사는 사례 값 복사를 막았다(E0 156건, E1 77건).
5. **코드 검증의 빈틈은 의미 판단이고, Self-RAG가 메웠다.** 인용 구절이 줄에 있지만 그 값을 뜻하지 않는 경우(치수에 R1 등)는 코드가 못 잡는다. 지지 판정이 6개 필드를 지웠고 **6개 모두 실제로 틀린 토큰**이었다. 맞는 필드를 지운 경우는 0이다.
6. **추출 단계의 오류도 KB로 풀었다.** 건조 중량 줄을 두 속성에 연결하는 W3부터의 오류 15건을, 검색 사례의 속성 투표가 모두 `dry_weight`로 정리했다(동점 0). 규칙을 새로 쓰지 않았다.
7. **결정성**: E1과 E1SV에서 같은 질의에 대한 체인의 1차 응답이 같았다(탈락 사유 집계가 동일). W4-0 잡음 0(D-038)과 함께, 실행 간 차이는 설정 차이다.

## 7. 한계와 해석 범위 (반드시 함께 인용)

- **개발셋 내부 추정이다.** KB와 평가가 같은 개발 분할에서 나왔다. 같은 계열 제외로 자기 누수는 막았다(검색 사례 738건 중 같은 계열 0건).
- **합성 생성 규칙 공유**: 합성 문서는 계열이 달라도 같은 문구 규칙을 쓴다(D-039). 실제 문서에서는 비슷한 사례가 이만큼 잘 검색되지 않을 수 있다. 검색 상한(0.814)도 이 데이터의 성질이다.
- **개발셋 조정 3회**: 생성 단계 기준 W3 2차, W4-1, E1SV다. 검색 설정은 생성 결과를 보기 전 진단으로 1회 정했다.
- **급등(H2 트리거)**: 사실 F1 +0.396은 누수 의심 기준(0.3)을 넘는다. 자기 누수 점검은 통과했지만, 위 두 요인 때문에 일반화를 주장하지 않는다.
- **모델 하나**: 로컬 EXAONE 3.5 7.8B만으로 E를 실행했다. 클라우드 행은 C 설계로만 있다(D-034).
- **비용**: 문서당 LLM 호출이 2회에서 약 16회로 늘었고, 지연은 26 s에서 81 s로 늘었다(NFR-04 상한 5분 안).
