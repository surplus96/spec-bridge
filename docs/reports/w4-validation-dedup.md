## 2. 검증기 (G3)

**정답 재현**: 개발 정답 24건 모두에서 Finding의 (코드, 속성, 규칙 종류)와 필수 누락 목록이 정답 계약과 같다. 정상 문서 12건은 Finding 0과 `ready`다. 정답 계약을 코드가 정확히 구현했다는 뜻이다.

**실제 파이프라인 출력에 적용**(이슈 12건, 정상 문서 12건):

| 실행 | G3 재현율 | G3 정밀도 | 정상 문서 오탐 | REVIEW |
|---|---|---|---|---|
| R 규칙 기준선 | 1.000 | 0.750 | 3 | 0 |
| C zero-shot | 1.000 | 0.750 | 3 | 3 |
| E1 (+ RAG) | 1.000 | 0.923 | 1 | 3 |
| **E1SV (운영 구성)** | **1.000** | **0.923** | **1** | 1 |

- **확인**: R과 C의 오탐 3건은 모두 **E5(문서 내 불일치) 오경보**였다. 점도 조건이 다른 두 처리량 값이 문맥 없이 한 키로 뭉쳐 불일치로 보였다. E1SV는 문맥을 붙여 이를 모두 없앴다. **한정 정보 추출이 검증 정밀도의 전제**라는 실측이다.
- G3 목표(재현율 ≥ 0.95)는 개발셋에서 충족했다. 단 이슈가 12건뿐이라 표본이 작다.

## 3. 중복·유사 판정 (G4)

블로킹은 같은 클래스 기준이다. 제조사(등록명·별칭)와 모델 식별 키가 같으면 duplicate, 같은 제조사이면서 모델명 유사도 ≥ 60이면 similar로 판정한다. 판정마다 식별 비교·이름 점수·값이 다른 속성을 근거로 남긴다.

| 실행 | duplicate | similar | 오탐 | P / R |
|---|---|---|---|---|
| R, C, E0, E1, E1SV, 클라우드 | 4/4 | 176/176 | 0 | 1.000 / 1.000 |
| B (모델이 직접 정규화) | 4/4 | 161~169/176 | 0 | 1.000 / 0.92~0.96 |

**한계, 이 수치는 판정기의 능력이 아니다.** 이 합성 데이터에서는 **제조사 하나로 similar와 new가 완전히 갈린다**(similar 176쌍은 모두 같은 제조사, new 180쌍은 모두 다른 제조사, D-016의 계열 정의 때문). 같은 정답 식별 정보로 기준선을 비교한 결과는 다음과 같다.

| 방법 | P | R |
|---|---|---|
| 모델명 접두사 규칙(D-018) | 1.000 | 1.000 |
| 제조사 + 모델명(구현) | 1.000 | 1.000 |
| 모델명 유사도만(≥ 62.5) | 0.549 | 1.000 |
| 모델명 유사도만(≥ 70) | 0.684 | 0.661 |

속성 거리는 구별력이 없다. **FR-10의 "이름·속성 유사도 판정"은 이 데이터로 검증되지 않았다.** 같은 제조사의 다른 제품군이나 다른 제조사의 유사 제품이 들어간 데이터가 필요하다. 임베딩 기반 유사 제품 검색은 이 데이터가 생긴 뒤에 시험할 후보로 남긴다.

## 6. 하지 않은 것과 정리 대상

- **W4-8 구성 D(검증 피드백 재추출) 보류**: E1SV의 Self-RAG 지지 판정이 비슷한 역할(근거 없는 필드 제거)을 이미 한다. 남은 오답은 "누락"이라 재추출보다 개선 후보 3이 맞다. 실행 비용(실험 1회 약 40분) 대비 가치가 낮다고 보고 W6 최종 비교 때 다시 판단한다.
- **코드 정리(W5 착수 전 권장)**:
  - 검증기가 평가 모듈의 `fact_key`를 import한다.
  - API가 실험 실행기의 `make_rag`를 import한다.
  - `langchain-community` 지원 종료 경고가 남아 있다(오프라인 테스트의 BM25 import).
  - 공용 모듈로 옮기면 채점기 해시가 바뀌므로, 옮길 때 새 ID를 기록한다.
- 테스트 분할, 독립 수기 사양서, LangGraph 등록 그래프·HITL·UI(W5)는 아직이다.
