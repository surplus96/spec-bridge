# W6 최종 평가 — 개발·테스트·수기 사양서

2026-10-15 · 작성: 헬퍼 모델 · 상태: **판정 완료**(2026-10-16, 사용자, D-090). 사전 등록 기준(D-080)에 대해 헬퍼가 계산한 값과 사용자의 판정을 싣는다(H4).

원자료는 `var/eval/<run_id>/`에 있다(커밋 안 함). 모든 수치는 §8의 명령으로 다시 만들 수 있다. 근거 결정은 D-080(사전 등록), D-086(동결), D-087(개발 재현), D-089(C 행)이다.

## 1. 요약

- **테스트 분할(16건)**
  - 사전 등록 기준 (a)·(b)·(c)와 목표권이 모두 기준값을 충족한다.
  - E1SV의 사실 F1은 0.913이다(개발 0.946).
- **수기 사양서(6건)**
  - (c)는 충족한다(E1SV−R F1 하한 +0.286).
  - 목표권은 미달이다(문맥 TP 1, 필요 7). 그래서 ③ "탁월"의 수기 조건은 성립하지 않는다.
- **G 목표(테스트 E1SV)**
  - G1·G2·G4는 기준값을 충족한다.
  - G3 검증 재현율은 0.875로 기준 0.95에 못 미친다.
  - 오류 분석 결과, G3 미달과 G4 누락은 모두 **추출 단계에서 빠진 사실 6개**에서 나왔다(§6.2).
- **수기 세트의 약점**은 원문 파싱이 아니다. 원인은 둘이다.
  - 개발 사전에 없는 단위·값 표기: `t`, `cm`, `barg`, `Seawater`, `HFO / MGO` 등
  - 문서 구절로 쓴 범위를 채우지 못함(§6.3)

## 6. 오류 분석

- 도구는 `spec_bridge/eval/errors.py`다(새 모듈, 채점에 쓰지 않는 읽기 전용 분석, 테스트 9건).
- 놓친 정답 키와 남는 예측 키가 같은 사실을 가리키면 짝지어 한 번만 센다. 원인은 아래 순서로 정한다.

| 원인 | 뜻 | 계획서 분류 |
|---|---|---|
| value | 같은 키, 다른 값 | 근접 오답(값) |
| context | 같은 속성·값, 기준·조건·범위가 다름 | 근접 오답(문맥) |
| attribute | 같은 값이 다른 속성에 붙음 | 속성 오연결 |
| value_and_context | 같은 속성, 키와 값이 모두 다름 | 근접 오답 |
| unresolved | 값을 원문에서 찾았지만 정규화하지 못함 | 정규화 |
| parse | 파싱된 텍스트에 그 속성의 정답 관측이 없음 | 파싱 |
| not_extracted | 파싱 텍스트에는 있는데 모델이 내지 않음 | 추출 누락 |
| extra | 정답이 설명하지 못하는 예측 키 | 과잉 |

분류 오답은 문서 단위로 따로 센다.

- **not_extracted 6건**: 모델이 받은 줄 목록에 값이 있었는데 응답에 넣지 않았다.

| 문서 | 놓친 속성 | 원문 줄(모델 입력) |
|---|---|---|
| SYN-009 | maker, model_designation | `[L5] Manufacturer — …`, `[L6] Model designation — …` (표 밖 문단) |
| SYN-022 | application, medium | `[L9] Service \| fresh water`, `[L10] Fluid \| lube oil` |
| SYN-025 | rated_throughput(700 cSt 행) | 표 4행 |
| SYN-028 | application | `[L12] Service \| generating-set` |

- **이 6건이 G3·G4 미달을 모두 설명한다.**
  - **G3**
    - E1 오탐 4건은 SYN-009(2건), SYN-022(1건), SYN-028(1건)에서 나왔다. 필수 속성을 추출이 빠뜨려서 검증기가 "필수 누락"을 냈다. 문서에는 그 값이 있었으므로 오탐이다.
    - E4 누락 1건(SYN-022)은 **application**을 추출하지 못해 허용 목록 검사가 실행되지 않은 경우다. Separator의 허용 목록은 application에 있다. 처음에는 medium으로 잘못 적었고 CP-S4 R7로 고쳤다.
  - **G4**: 유사 5쌍 누락은 모두 SYN-009다. 제조사·형식명이 없으니 매칭기가 등록 제품과 비교할 단서가 없었다.
  - 검증기와 매칭기 자체의 오판은 이번 테스트에서 찾지 못했다.
- 같은 형태의 줄이 다른 곳에서는 잘 추출됐다. 예를 들어 SYN-009의 `[L12] Fluid | sea water`는 medium으로 추출됐는데, SYN-022의 `[L10] Fluid | lube oil`은 빠졌다. 그래서 특정 라벨 문제가 아니라 **소형 모델의 누락**으로 본다. 다만 문서 수가 작아 패턴을 단정하지 않는다.

## 7. 한계

1. **합성 생성 규칙 공유**: 개발·테스트 분할은 같은 생성기에서 나왔다. 테스트 F1 0.913은 "같은 생성 규칙의 새 문서"에 대한 일반화다. 수기 세트 F1 0.549가 생성기 밖 표기에 대한 첫 신호이고, 차이가 크다.
2. **표본 크기**: 테스트 16건, 수기 6건이다. 수기 부트스트랩 구간이 넓다([0.286, 0.622]). G3의 이슈 정답은 8개뿐이다(한 건 = 0.125).
3. **모델 하나**: 로컬 `exaone3.5:7.8b` 하나로 평가했다. 클라우드 행은 테스트 문서 외부 전송 승인이 없어 돌리지 않았다(D-080 결정 3).
4. **개발셋 조정 횟수**: 생성 단계 3회, 검색 설정 0회다(D-053). 동결 뒤 조정은 0회다.
5. **수기 사양서 독립성**: 헬퍼 초안이고 `reviewed_by: null`이다. 헬퍼가 개발 중에 열람했고, 변환 판단 3종이 들어갔다(D-082). 연기 시험에서 R 결과를 동결 전에 봤다.
6. **정규화 사전 범위**: 개발 사전에 없는 단위·값 표기는 `unresolved`·`value` 오답이 된다. `°C` 표기도 같다(D-082). 자동 추출 지표에는 오답으로 잡힌다. 운영 경로에서는 다음과 같이 담당자에게 간다.
   - `unresolved`는 검토 화면 경고와 보강 요청서로 간다(W5).
   - 사전 밖 `value`는 D-091 보완 뒤 "표준 용어 확인" 알림으로 간다. 수기 7/7, 테스트 1/1이고, 맞는 값에 대한 알림은 0이다. 이 기능은 평가 뒤 같은 오답을 보고 만들었으므로 사후 확인이며 독립 평가가 아니다(CP-S4 L4).
   - 문맥 차이는 "문맥 확인 필요"로 표시되지만, 담당자가 문맥을 고치는 기능은 없다(보류, D-091).
7. **사후 참고 행**: Copt는 결과를 본 뒤 추가했다(D-089). 판정에 쓰지 않는다.
