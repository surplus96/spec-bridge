# spec-bridge 이후 단계 가이드

작성: 2026-10-06 · 근거: [D-005](decisions.md), [프로젝트 계획 W1~W6](spec-bridge-project-plan.md), [데이터셋 계획](dataset-plan.md)

진행 순서는 **6개 클래스 유지 → 온톨로지 범위 확정 → 클래스별 사례 다양화 → 주요 기능과 평가 완성**이다. 지원 범위는 2행정 주기관·4행정 엔진·펌프·공기압축기·유청정기·과급기의 제품 정보 생성·등록 자동화다. 선박 제조 전체를 포괄하는 분류 체계로 설명하지 않는다.

현재 원본 12건, 별도 보완 후보 6건, 신규 실제 파일 사양서·정답 40쌍, 등록 입력 150개, BOM 4건과 비교 라벨 10쌍을 준비했다. 새 패키지는 자동 품질 검사 완료·사용자 의미 검토 및 정식 확정 전이다. 온톨로지·등록 저장소·파서·추출기·검토 UI는 이후 구현 대상이며, 현재 후보셋에는 온톨로지 연결·렌더링 파일 검증·사용자 서명이 남아 있다.

## 이번 세션의 범위 — 데이터셋 완성

사용자 결정(D-006)에 따라 이번 세션은 데이터 명세·합성 문서·정답·등록 샘플·평가 계약과 품질 점검까지만 진행한다. 로더·실행 스키마·파서·추출기·검증기·UI 구현은 후속 세션이다. 아래 W1~W6 설명은 전체 프로젝트 로드맵이며 이번 세션의 완료 조건과 구별한다. 기존 공통 모델 참고 코드는 보관하되 데이터셋 진행도에 포함하지 않는다.

## 1. 온톨로지의 의미와 범위 확정 — W1, FR-01

먼저 코드보다 **속성 정의표**를 작성한다. 참고 문서와 관찰 메모에서 속성과 표기·조건을 확인하고, 프로젝트가 정할 등록 정책을 구별한다. 클래스 계층은 D-002를 유지한다.

| 정의표 항목 | 적을 내용 |
|---|---|
| 클래스·속성 후보 | 어느 클래스의 어떤 정보를 다루는가; 공통·상속·고유 구별 |
| 의미·대상 | 장비 전체/구성품, 중량·치수의 포함 범위 |
| 자료형 | 수치, 문자열, 열거형, 목록, 치수 객체, 범위 객체 |
| 정규 단위·차원 | 원문 단위와 변환 후 단위; 압력·유량·길이 등의 차원 |
| 조건·기준 | FAD, gauge/absolute, MCR, 엔진 축출력, 연료 기준 점도 |
| 필수 여부 | 등록을 위해 필요한 이유; 형식에 따른 조건부 필수 여부 |
| 출처·확인 상태 | 원본 ID·판본·페이지, synthetic 정책 여부, 사용자 검증 |

Pump부터 한 클래스의 정의표를 만들고 나머지 5개로 확장하는 순서가 이해하기 쉽다. 특히 펌프 형식별 head/압력, 압축기 용량 기준, 조건별 처리량, 정격 출력, 중량 범위를 해결한다. 필수 여부는 합성 문서에 값이 있다는 이유만으로 정하지 않는다. 속성 개수를 맞추기 위해 근거 없는 항목을 추가하지 않는다.

**완료 기준:** 여섯 클래스의 속성 의미·자료형·단위·조건·필수 이유가 설명되고 미해결 사항이 표시되어 있다. 실제 사실은 H3 근거 요건을 충족해야 하며 사용자 검증 없이 허용 범위·제조사 규칙을 확정하지 않는다. 아직 온톨로지가 없으므로 기존 정답의 클래스·속성 ID도 후보로 대조한다.

## 2. 정의를 실행 가능한 스키마로 구현 — W1, FR-01~03

정의표를 온톨로지 YAML로 옮기고 로더·무결성 검사를 만든다. 이 정의에서 클래스별 Pydantic/JSON Schema와 정의서를 생성한다. 공통 속성을 상속하되 장비별 속성과 조건을 표현할 수 있어야 한다.

제품 출력 스키마와 평가 정답 스키마는 구별한다. 제품 출력은 값·조건·관계·근거를 표현하고, 정답 레코드는 파일 매핑·출현 라벨·작성 이력 등 평가기 메타데이터까지 담는다. 정답 YAML 전체를 제품 스키마에 그대로 넣지 않는다.

현재 합성 6건을 스키마와 대조해 데이터 오류와 온톨로지의 표현 부족을 구별한다. 온톨로지·사전의 내용은 원본 및 개발 자료에서 정의하며 평가 정답을 보고 추출기에 유리하게 조정하지 않는다. 현재 6건을 설계 과정에서 참고한 이력은 D-003과 함께 밝힌다.

등록 저장소는 제조사+정규 형식명 등 프로젝트의 식별 정책과 등록 이력을 표현하도록 설계한다. 이후 중복 검사의 비교 대상이 될 가상 등록 목록 150건을 준비한다.

**완료 기준:** 무결성 테스트와 생성 스키마 검사가 통과하고, 기존 W1 DoD인 수기 사양서 정답 1건 대조를 충족한다. 추가로 나머지 5건의 표현 가능 여부·미해결 항목을 기록한다. 이후 기존 계획의 **CP-S1** 검토 패키지를 마련한다. 자동 검사만으로 사용자 서명이나 검토 통과를 대신하지 않는다.

## 3. 클래스별 사례 다양화와 파서 — W2

기존 계획대로 합성 사양서 **40건**, 등록 목록 **150건**, BOM **4건**, 중복·유사 정답 쌍 **10건**을 구성한다. 각 수치는 데이터셋 계획의 목표이며 현재 생성 완료 수치가 아니다.

- 클래스 배분은 7·7·7·7·6·6건, 파일 형식은 PDF 20·Excel 12·DOCX 8건이다.
- 표·서술·혼합 레이아웃을 만들고 단위 위치, 조건부 값, 반복 기재, 실제 관찰한 표기 변형을 다양화한다.
- 정상 문서 최소 10건을 확보하고 V1 및 E1~E7의 사례·정답을 구성한다. 별도 함정 목록을 다시 만들 필요는 없다. 비대상 정상 정보와 오류 주입 라벨은 구별한다.
- 생성 시드와 정답 생성 과정을 고정하고 제품 계열 기준으로 개발/테스트를 분리한다. 같은 제품의 표현만 바꾼 문서가 양쪽에 섞이지 않도록 한다.
- 현재 6건은 별도 보완 후보셋으로 관리한다. 완전한 독립 평가셋의 사람 작성 여부는 D-003에 따라 W2에서 결정한다.

PDF·Excel·DOCX 파서는 값뿐 아니라 페이지·시트·셀·표 행·절 등 근거 위치를 보존해야 한다. 현재 후보 문서도 실제 DOCX/PDF로 만든 후 페이지 라벨을 확인한다.

**완료 기준:** 시드로 40건과 정답이 재현되고 모든 문서를 위치 정보와 함께 파싱한다. 정답·설계 정보가 모델 입력에 섞이지 않는지 확인하고 **CP-S2** 검토를 진행한다.

## 4. 매핑·추출·정규화 — W3

클래스 매핑 → 해당 클래스 스키마로 속성 추출 → 단위·별칭·형식명 정규화 순으로 구현한다. 모든 출현과 조건을 유지해 나중에 불일치 여부를 검사할 수 있도록 한다. 지원 클래스 밖 입력을 기존 여섯 클래스 중 하나로 강제하지 않도록 unknown 처리도 정의한다.

개발셋에서 A(LLM 단독), B(온톨로지 스키마 추가), C(결정론 정규화 추가)를 동일 입력 정책으로 비교한다. 모델·프롬프트·재시도·설정과 실패 건수를 기록한다. 클래스 정확도와 속성 P/R/F1을 분리하고, 파싱·추출 실패도 분모에서 제외하지 않는다.

**완료 기준:** G1/G2 첫 결과가 파일로 저장된다. 기존 목표 추출 F1 ≥ 0.8의 달성 여부와 실패 원인을 함께 기록하고 **CP-S3**에서 채점 정책·누수·결과 해석을 검토한다.

## 5. 검증·중복 검사·검토·등록 — W4~W5

W4에서는 필수 누락·단위·형식·조건별 불일치 검증과 기존 목록 대비 duplicate/similar/new 판정을 구현한다. 검증 근거를 표준 JSON에 포함하고, 검증 피드백 재추출을 포함한 D 구성을 비교한다. 불확실한 범위나 제품 식별 규칙을 모델 추측으로 채우지 않는다.

W5에서는 담당자가 원문과 추출값·오류·중복 후보를 함께 보고 수정할 수 있도록 UI를 만든다. 등록 확정 후 DB 또는 표준 JSON에 저장하고 수정·등록 이력을 남긴다. 같은 요청의 반복으로 중복 등록되지 않는지도 확인한다.

**완료 기준:** 문서 1건 업로드부터 근거 확인·수정·최종 등록까지 이어지고, 클래스·속성·검증·중복 판정이 출력된다. 원문의 주요 기능 각각을 실제 사례로 시연한다.

## 6. 고정된 테스트셋 평가와 제출 — W6

개발셋에서 조정한 모델·사전·규칙·중복 임계값과 채점 정책을 고정한 뒤 테스트셋을 평가한다. 별도 후보셋 결과는 따로 보고하며 설계에 사용된 자료를 완전한 독립 평가로 설명하지 않는다.

제출물은 과제 원문의 웹 데모·온톨로지 스키마 정의서·속성 추출 정확도 평가 결과를 중심으로 구성한다. 클래스 매핑, 속성 추출, 오류 검증, 중복·유사 판정 지표와 실패 사례도 함께 설명한다. 실제 제품 문서 전체에 대한 성능으로 확대 해석하지 않는다.

**완료 기준:** G1~G5 목표 달성 여부, 실행 설정·분모·버전·해시·미달 원인이 재현 가능한 결과로 남는다. 기존 계획의 **CP-S4** 공개 전 검토를 수행한다.

## 데이터셋 현재 상태와 다음 단계

[후보 패키지](../data/synth/README.md)의 사양서·정답 40쌍, 등록 입력 150개, BOM 4건과 지정 비교 라벨 10쌍을 작성했다. 개발/테스트 24/16, PDF/Excel/DOCX 20/12/8 배분과 실제 위치를 확인했다. [자동 검사 결과](../data/eval/reviews/dataset-package-checks.json)와 [파일 해시](../data/synth/release-inventory.yaml)를 검토 기준으로 남겼다.

현재 완료 범위는 **후보 데이터셋 생성·자동 품질 검사**다. [검토 패키지](dataset-review-package.md)의 사용자 의미 검토 및 수정 반영 뒤 정식 확정한다. 추가 원본은 구체적인 근거 부족이 발견될 때 보강한다. 이번 세션에서 기능 로더·파서·추출기·검증기·UI는 구현하지 않았고 프로젝트 체크포인트 통과도 선언하지 않는다.

추가 검사에서 발견한 BOM 경고 3·판정 보류 1건은 후보 v2의 합성 사양·정격 기준 보완으로 해소했다. 기술 의미·실제 장비 호환성과 Office GUI 검토는 자동 승인하지 않았으며 사용자의 최종 검토를 위한 자료를 제공한다.
