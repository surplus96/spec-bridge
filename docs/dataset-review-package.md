# 합성 데이터셋 후보 검토 패키지

2026-10-07 · DATASET-PACKAGE · 상태: 생성·자동 품질 검사 완료, 사용자 의미 검토/정식 확정 전

6개 클래스의 제품 문서 추출·검증·중복 비교에 사용할 합성 후보 패키지를 작성했다. 기능 로더·파서·추출기·검증기·UI는 구현하지 않았다. [전체 자료](../data/synth/README.md), [입력 매핑](../data/synth/dataset-manifest.yaml), [해시 인벤토리](../data/synth/release-inventory.yaml)를 검토 기준으로 사용한다.

## 생성된 자료와 검사 범위

- 사양서 40건: PDF 20·Excel 12·DOCX 8, 개발 24·테스트 16.
- 등록 제품 150개: 개발 90·테스트 60. 작성용 계열/사례 메타데이터 제거.
- BOM 4건 및 지정 비교 정답 10쌍: 중복 6·유사 4.
- 원문 관찰 409개·정규 사실 368개, 같은 조건의 값 집합 기준 366개 그룹. E1~E5 라벨 20개.
- 실제 PDF 값 영역·Excel 셀·DOCX 표 셀/문단에서 근거 문구를 대조했다. 모든 형식의 해시·표기·참조와 계열 분할도 점검했다.
- DOCX 8건은 Pandoc의 독립 문서 reader로 다시 읽었다. PDF 대표 1건을 이미지로 확인했다. Excel은 OOXML 구조·셀 내용·행 높이/줄바꿈 설정을 검사했으며 Excel GUI의 전수 시각 검토는 수행하지 않았다.
- 기존 원본 12건과 handwritten 6건의 의미 검증/서명 상태는 그대로 유지한다. 새 파일도 reviewed_by는 null이다.

숫자는 자료 구성과 무결성 검사 결과이며 모델 성능이 아니다. 내용과 정답이 같은 작성 절차에서 만들어졌으므로 자동 대조만으로 독립적인 정답 정확성을 보장하지 않는다.

## 확인할 핵심 사항

1. 클래스 경계, 속성의 출력 대상·중량/치수 포함 범위·조건이 기술 문구와 일치하는가?
2. E1의 필수 항목 요구가 프로젝트 등록 정책으로 적절한가? 선택 속성 누락을 오류로 표시하지 않았는가?
3. E2/E3의 원문을 교정해 정답을 만들지 않았는가? E5의 두 값은 정말 같은 조건/기준/범위인가?
4. E4 용도 목록이 합성 지원 범위임을 명확히 구별했는가? 실제 업계의 모든 용도를 부정하는 규칙이 아닌가?
5. 정상 복수 조건과 반복 표기를 오류로 오인하지 않았는가? 표기 출처를 일반 동의어 검증으로 확대하지 않았는가?
6. 등록 비교에서 지정되지 않은 유사 후보를 음성으로 취급하지 않는가? BOM의 가상 연결을 실제 호환성으로 해석하지 않는가?
7. 입력에 정답·계열·사례 정보가 섞이지 않았는가? 실제 Office 뷰어에서 읽기 불편한 문서가 없는가?

## 재현과 변경 관리

현재 생성 환경은 로컬 Miniforge Python, PyYAML, ReportLab, pypdf다. DOCX/Excel 패키지는 Python 표준 ZIP/XML 도구로 작성하며 DOCX 교차 reader 검사는 로컬 Pandoc을 사용했다. PDF 폰트 경로는 `/System/Library/Fonts/Supplemental/Arial.ttf`로, 다른 OS에서는 동일한 글리프를 지원하는 폰트를 설정하고 위치/해시를 다시 확인해야 한다.

생성 순서는 create_dev_drafts.py --split dev/test → check_dev_drafts.py --split dev/test → render_dataset.py → check_rendered_dataset.py다. BOM/비교 라벨/표기 목록은 해당 정답과 원장으로 작성했다. 원장 또는 파일이 변경되면 보조 라벨과 해시도 갱신하고 check_dataset_package.py를 다시 실행한다.

[정답 계약](../data/synth/answer-contract.yaml), [작성 규칙](../data/synth/dev-authoring-rules.yaml), [제품 원장](../data/synth/product-ledger.jsonl)은 평가 전에 고정해야 한다. 현재 인벤토리는 검토할 후보 버전을 특정하는 용도다. 검토자가 지적 사항과 수정 결과를 기록하고 서명한 뒤 정식 확정 상태로 전환한다.

이번 완료는 **데이터셋 후보 생성·자동 검사**다. 전체 프로젝트 W1/W2 DoD나 CP-S1/CP-S2 통과, 실제 추출 성능 평가, 사용자 기술적 승인으로 선언하지 않는다.

## 추가 자동 검사 — 보완 전 기록(2026-10-07)

[추가 검사 결과](../data/eval/reviews/additional-quality-checks.json)를 작성했다. 정답 이슈 라벨과 별도로 원문 관찰의 자료형·단위 및 명세의 필수/열거/동일 조건 규칙에서 E1 6·E2 4·E3 4·E4 4·E5 2건을 재계산했고 정답과 일치했다. 속성 사실 368개에 대해 대상 범위·조건 구조를 점검하고 엔진 출력의 정격점 연결 15건도 대조했다. 실제 기술 의미 전체를 독립적으로 증명하는 검사는 아니다.

원본 12건의 해시와 관찰 표기 69개를 지정 페이지에서 재대조했다. 표기 존재는 확인했지만 의미 검증 서명은 0개이며 검증자 필드를 자동으로 채우지 않았다. 합성 필수 정책의 구조적 일관성과 실제 업무상 적절성도 구별한다.

**BOM 수치 대조에서 보완 검토 항목이 발견됐다.** 과급기 1개 및 동일 출력 기준을 가정하면 아래와 같다.

| BOM | 엔진 출력 kW | 과급기 명시 적용 출력 kW | 결과 |
|---|---:|---|---|
| BOM-001 | 9,868.6 | 3,222.4–8,660.2 | 범위 밖 |
| BOM-002 | 15,456.8 | 단일 8,006.4 | 적용 구간 미기재로 판정 보류 |
| BOM-003 | 1,258.75 | 4,783.5–12,011.9 | 범위 밖 |
| BOM-004 | 1,834.8 | 6,193.8–14,681.6 | 범위 밖 |

이는 합성 원장의 수치 비교이며 정격 기준의 동등성·실제 과급기 매칭·물리적 호환성을 승인하거나 불합격으로 확정한 결과가 아니다. 현재 BOM 연결은 가상 관계로만 정의했지만 데이터셋의 기술적 일관성을 높이려면 관계 대상·합성 사양·적용 구간을 근거와 함께 보완해야 한다. 이 검사에서는 제품값/연결을 자동 수정하지 않았다.

Office 미리보기는 QuickLook 샌드박스 초기화 실패로 실행할 수 없었다. 대신 Excel의 Arial 11pt 기준 글자 폭·셀 너비·행 높이를 비교하고 DOCX의 표 너비/페이지 여백, PDF 20건의 글자 시작 위치와 페이지 범위를 점검했다. 추정 경고는 0건이지만 실제 Office GUI의 글꼴 대체·줄바꿈·페이지 분할까지 통과했다고 주장하지 않는다.

이전 자동 무결성 통과는 유지되며 추가 검토 결과는 **BOM 3건 범위 대조 경고·1건 판정 보류**다. 모든 미확인 사항을 통과로 전환하지 않았고 정식 확정/사용자 검토는 계속 대기 상태다.

## 확정 전 보완 완료 — 현재 후보 v2

[BOM 보완 결과](../data/eval/reviews/BOM-REMEDIATION-REPORT.md)에 4건의 전용 합성 과급기 연결과 R1/축출력 정격 기준을 기록했다. 보완 후 범위 경고 0건·판정 보류 0건이며, 실제 장비 선정이 아닌 선언한 합성 사양의 내부 일관성을 확인했다. 이전 결과는 별도 보관하고 현재 원장·등록 입력·기술 본문·정답·비교 라벨·해시를 갱신했다.

DOCX의 Arial 11pt/문단 간격/표 행 분할 방지/헤더 반복을 명시했다. [40개 페이지 미리보기](../data/synth/review-previews/README.md)는 사용자가 바로 검토할 수 있는 자료다. PDF 20건은 실제 입력 페이지이며 Office 20건은 원문 기반 PDF 보조 자료다. Office 원본의 GUI 검토나 사용자 기술적 서명을 대신하지 않는다.

재생성에 create_supporting_files.py(보조 라벨/BOM 갱신)와 create_review_previews.py(검토 자료 생성)를 추가했다. 생성 순서: 본문·초안 → 초안 점검 → 파일 변환 → 보조 파일 갱신 → 실제 위치/추가 정책 검사 → 패키지 검사와 인벤토리 갱신이다.

자동으로 수행 가능한 보완은 완료했고 검증자/검토자 필드는 null로 유지한다. 남은 확정 조건은 사용자의 기술적 의미·업무 정책 검토와 실제 Office 뷰어 확인이다.
