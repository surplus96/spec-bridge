## 🧭 개발 헬퍼 모델 운영 지침 (작업 시작 전에 반드시 읽을 것)

> 이 장은 이 문서를 받아 개발을 돕는 **헬퍼 모델**에게 주는 지침이다. 헬퍼는 작업 중 이 지침에 따라 사용자에게 **안내·경고·중단**을 해야 한다.
> 배경: 헬퍼 모델은 표준 스택 구현·테스트·리팩터링에 충분하다. 다만 ① 미묘한 설계·통계 오류를 놓칠 수 있고 ② **도메인 사실 오류는 어떤 모델을 써도 사라지지 않는다.** 그래서 정해진 시점에만 Opus급 모델로 교차 검토하고, 도메인 사실은 모델이 아니라 **절차**로 막는다.

### H1. 작업 진행 규칙

1. **한 번에 작업 ID 하나만** 진행한다 (예: `W1-1`, `FR-05`). 시작할 때 해당 작업의 목표와 완료 기준(DoD)을 한 줄로 다시 말하고 시작한다.
2. **교육 모드**: 사용자가 직접 타이핑하며 이해하는 방식이다. 전체 코드를 완성해 주지 말고 **단계별 설명 + 참고 코드 조각**을 제시한다. 사용자가 명시적으로 요청할 때만 전체 구현을 보여준다.
3. **완료 선언 조건**: DoD를 명령 실행 결과(테스트, 린터, 평가 수치)로 확인하기 전에는 "완료"라고 말하지 않는다. 확인하지 못했으면 "미확인"이라고 명시한다.
4. **범위 고정**: "선택"으로 표시된 작업은 사용자가 지시할 때만 시작한다. 새 아이디어는 작업하지 말고 문서의 "이후" 목록에 제안만 한다.
5. **커밋·푸시·외부 전송**은 사용자가 요청할 때만 한다.
6. 계획과 다르게 진행해야 하면 먼저 차이와 이유를 알리고 승인을 받는다. 승인된 변경은 [decisions.md](decisions.md)에 기록한다.

### H2. 교차 검토 운영 (헬퍼 → Opus급)

**정기 체크포인트**: 이 문서의 🔶 표시(H4 체크포인트 표와 각 주차 DoD 옆)에 도달하면 헬퍼는 다음 작업으로 넘어가지 말고 아래 절차를 따른다.

1. 사용자에게 알린다: `🔶 교차 검토 체크포인트 [ID] 도달 — 다음 단계 진행 전 Opus급 모델 검토를 권장합니다.`
2. **검토 패키지**를 작성해 제공한다 (사용자가 복사해서 상위 모델에 전달하는 용도):
   - 배경 요약 (5줄 이내): 무엇을 왜 만들었는가
   - 검토 대상: 파일 경로·핵심 코드 발췌 또는 diff, 산출된 수치
   - 체크포인트 표의 **검토 질문 목록** + 헬퍼 스스로 확신이 낮은 지점
   - 전제·가정 목록
3. 검토 결과를 사용자가 가져오면 `docs/decisions.md`에 **날짜 · 체크포인트 ID · 지적 사항 · 조치 · 미해결 항목**을 남기고, 지적 사항을 해결한 뒤 다음 작업으로 진행한다.
4. 헬퍼는 **자기 작업을 스스로 "검토 통과"로 판정하지 않는다.**

**수시 에스컬레이션 트리거** — 체크포인트가 아니어도 아래 상황이면 즉시 알리고 교차 검토를 제안한다.
- 같은 버그를 두 번 고쳤는데도 재현될 때
- 결과가 **너무 좋을 때** (예: 추출 F1이 기준선보다 0.3 이상 급등, 정확도 1.0) → 누수·평가 오류를 먼저 의심
- 비동기 루프·동시성·트랜잭션 관련 코드를 수정할 때
- README·케이스 스터디에 들어갈 수치나 주장을 새로 만들 때
- 되돌리기 어려운 변경 (DB 스키마 변경, 등록 데이터 삭제, 온톨로지 클래스 삭제·병합, 이력 재작성)

### H3. 모델을 바꿔도 해결되지 않는 위험 — 도메인 사실 프로토콜

**위험**: 장비 파라미터 범위, 제조사 형식명 표기 규칙, 규제 수치·조항, 장비 분류 관행은 모델이 **그럴듯하지만 틀리게** 말할 수 있다. 상위 모델로 바꿔도 이 위험은 남는다. 이 오류는 테스트를 통과한 상태로 결과물에 들어가서 포트폴리오의 신뢰를 무너뜨린다.

**헬퍼가 지킬 규칙**
1. 장비·규격·규제 관련 수치나 조항을 **기억에 의존해 사실처럼 쓰지 않는다.** 이번 세션에서 사용자가 제공한 원문이 없으면 `[미검증]` 태그를 붙이고, 확인 방법(어느 문서의 어느 부분을 볼지)을 함께 안내한다.
2. 도메인 데이터가 필요하면 먼저 사용자에게 **원문 발췌(문서명·판본·페이지 포함)** 를 요청한다. 헬퍼는 붙여 넣은 원문을 **요약·구조화만** 한다.
3. 온톨로지·마스터 데이터 중 **실제 세계 사실에 근거한 항목**(허용 범위, 형식명 해석 규칙, 제조사 별칭 등)은 `source`(문서명), `edition`(판본), `location`(페이지·조항), `verified_by`(검증자) 필드가 없으면 만들지 않는다. `verified_by`는 **사용자만** 채운다. 프로젝트가 임의로 정한 항목(클래스 구조, 합성 제품)은 `origin: synthetic`으로 표시한다.
4. 테스트에 쓰는 도메인 수치(허용 범위 등)는 테스트 코드에 직접 적지 말고 **온톨로지·마스터 데이터에서 읽어 온다.** 그래야 원문이 바뀌거나 오류가 발견됐을 때 한 곳만 고치면 된다.
5. **온톨로지 참조 가드**: 코드·문서·프롬프트에 등장하는 클래스·속성 ID는 온톨로지에 존재해야 한다. 헬퍼는 새 ID가 등장하면 온톨로지 존재 여부를 확인하고, 없으면 경고한다.
6. 합성·가정 데이터는 파일과 README에 **합성/가정임을 명시**한다. 실제 데이터처럼 서술하지 않는다.
7. 확신이 없으면 "모른다"고 말하고 확인 절차를 제안한다. 추측으로 빈칸을 채우지 않는다.

### H4. 이 문서의 교차 검토 체크포인트

| ID | 시점 | 검토 질문 |
|---|---|---|
| 🔶 CP-S1 | W1 종료 (온톨로지 v0 + 정의서 + 기존 등록 목록) | 클래스 경계가 겹치지 않아 문서 하나가 한 클래스로 정해지는가? 필수 속성이 "등록에 꼭 필요한 정보"로 정당화되는가? 동의어 사전이 한 정규 표기로 수렴하는가(한 별칭이 두 속성에 걸리지 않는가)? 실제 세계 사실에 근거한 항목에 출처가 있고 `verified_by`가 채워졌는가? |

| 🔶 CP-S3 | W3 종료 (매핑 + 추출 + 정규화 + 첫 비교표) | 정답 매칭 정책(정규화 후 일치, 복수 출현값 처리)이 평가 전에 고정되었는가? 추출 실패를 분모에서 빼지 않았는가? 첫 비교 결과의 해석이 과장되지 않았는가? |
| 🔶 CP-S4 | W6 공개 직전 | G1~G5 보고가 수치로 재현되는가? 합성 데이터·원문 미커밋·출처 표기가 지켜졌는가? 비교 실험의 결론이 데이터가 뒷받침하는 범위를 넘지 않는가? |

**이 문서의 도메인 사실 주의 지점 (H3 최우선 적용)**
- 장비 파라미터의 허용 범위(출력, 회전수, 유량 등), 제조사 **형식명 표기 규칙**(형식명을 실린더 수·보어 등으로 해석하는 규칙), 제조사 별칭은 **반드시 원문 발췌를 받은 뒤** 온톨로지에 넣는다. 확인 전에는 범위 검사 대신 단위 차원·형식 검사만 한다.
- 클래스 계층과 속성 목록은 프로젝트가 정한 **간이 분류**다. 업계 표준 분류(예: 선급·조선소의 장비 코드 체계)를 따른다고 주장하지 않는다.
- 착수 리서치의 규제 조사(M44, MARPOL VI)는 확장 과제(FR-14) 자료다. MVP 온톨로지·검증 규칙에 규제 수치를 넣지 않는다.

## 1. 개요

### 1-1. 한 줄 정의

**spec-bridge**: 선박 기자재 제품 문서(PDF·Excel·DOCX)를 입력받아 **간이 온톨로지에 맞춰 제품 정보를 추출·정규화·검증**하고, **기존 등록 제품과의 중복·유사 여부를 검사**한 뒤, 담당자 검토를 거쳐 **등록 데이터(DB + 표준 JSON)를 생성**하는 로컬 우선 도구. 등록되는 모든 값은 원문 위치 또는 사람의 수정 기록으로 추적된다.

### 1-2. 문제와 동기

- 신규 제품·부품을 시스템에 등록할 때 담당자가 설계 문서, 사양서, BOM을 직접 읽고 항목을 손으로 입력한다.
- 담당자마다 표기 방식이 달라(속성명, 단위, 제조사명, 형식명, 숫자 형식) 누락·중복·오류가 생기고 등록에 시간이 많이 든다.
- 조선 기자재는 문서 형식이 제조사마다 다르고, 같은 장비가 여러 프로젝트에서 반복 등록되기 쉬워 정규화와 중복 검사의 효과가 크다.
- 방산·조선은 보안 요구로 외부 클라우드 사용이 제한될 수 있다 → **로컬 동작**을 기본으로 한다.

### 1-3. 목표 (성공 기준)

목표 수치는 프로젝트가 정한 **제안값**이며 외부 근거로 확정된 값이 아니다.

| # | 목표 | 측정 |
|---|---|---|
| G1 | 속성 추출 | 필드 단위 F1 ≥ 0.90 (정규화 후 값 일치, end-to-end) |
| G2 | 온톨로지 클래스 매핑 | top-1 정확도 ≥ 0.95 |
| G3 | 등록 전 검증 | 주입한 필수 누락·단위·형식·불일치 오류 재현율 ≥ 0.95, 정상 문서 오탐 수 공개 |
| G4 | 중복·유사 검사 | 라벨된 쌍 기준 재현율 ≥ 0.90, 정밀도 ≥ 0.80 |
| G5 | 설계 선택을 수치로 정당화 — **핵심 가설: 코드 규칙으로 풀기 어려운 의미 매핑을 LLM + RAG가 해결하는가**(D-042) | 비교 실험 표 (6-2, 구성 R·A~E와 RAG 변형별 기여) |

보조 목표: 오프라인 모드에서 외부 네트워크 호출 0회(NFR-01), 등록 값 100%가 근거(원문 위치 또는 수정 기록)를 가짐.

### 1-4. 범위

| 포함 (MVP) | 제외 |
|---|---|
| 선박 기자재 **간이 온톨로지 1종** (말단 클래스 6개, [D-002](decisions.md)) | 정식 온톨로지 언어(OWL/RDF) 기반 추론 |
| 입력: PDF(텍스트 기반), Excel(사양 표·BOM), DOCX | 스캔 PDF OCR, 도면·CAD |
| 합성 제품 사양서 40건 + 기존 등록 목록 샘플 | 실제 제조사 문서의 대량 처리 |
| 검토·수정 UI + 등록(SQLite + 표준 JSON) | 실제 ERP/PLM 연동 |
| **문서 언어: 영문**, UI·설명은 한국어 | 가격·납기 등 상업 조건 |
| 로컬 LLM 기본, 클라우드는 비교용 | 파인튜닝 |
| | 규제 적합성 검토, POS 생성, 변경 영향 (→ 확장 FR-14·15) |
| | BOM 일괄 등록 S3 (→ 이후 확장, D-060. `has_component` 관계 정의·`relations` 표·합성 BOM 4건은 유지) |

### 1-5. 명칭·표기 원칙

- 특정 기업 사례에서 착안했더라도 "독립 프로젝트"로만 표기하고, 로고나 협업을 암시하는 표현은 쓰지 않는다.
- 합성 데이터임을 README 첫 화면에 명시한다.
- 제조사 PDF·규칙 원문은 저장소에 커밋하지 않고, 다운로드 스크립트와 출처만 제공한다.

## 2. 사용자 시나리오

**S1. 신규 제품 등록** — 등록 담당자가 제품 사양서(PDF)를 올린다 → spec-bridge가 온톨로지 클래스 후보(신뢰도 포함)를 제시하고, 클래스별 속성을 추출·정규화한다 → 화면에 속성값이 원문 위치 하이라이트와 함께 표시되고, 누락·단위·형식 오류가 표시된다 → 담당자가 값을 수정·확인한다 → 등록하면 DB 레코드와 표준 JSON이 생성되고 수정 이력이 남는다.

**S2. 중복·유사 제품 처리** — 업로드한 문서가 기존 등록 제품과 같은 제품의 다른 표기(예: 제조사 별칭, 단위만 다른 출력값)일 때 → spec-bridge가 `duplicate / similar / new` 판정과 일치·차이 속성 목록을 보여준다 → 담당자가 "기존 레코드에 연결 / 별도 등록 / 취소" 중 선택한다. 자동 병합은 하지 않는다.

**S3. BOM 일괄 등록** *(이후 확장, D-060: 이번 범위 밖. 관계 모델·합성 BOM만 준비)* — Excel BOM을 올린다 → 행마다 구성품을 클래스 매핑·추출하고, 상위 제품과 `has_component` 관계를 만든다 → 오류가 있는 행만 검토 대기로 남기고 나머지는 일괄 확인한다.

## 4. 데이터 설계

### 4-1. 간이 온톨로지

**범위 확정([D-002](decisions.md))**: 말단 클래스 6개 — `Engine`(TwoStrokeMainEngine, FourStrokeEngine), `FluidMachinery`(Pump, AirCompressor, Separator), `EngineComponent`(Turbocharger). 클래스당 속성 8~12개, 관계 3종. 클래스 선정 근거·참고 문서·속성 후보는 [데이터셋 준비 계획](dataset-plan.md) 참고. 속성 목록은 W1에서 참고 문서를 대조해 확정한다.

아래는 각 구성 요소의 필드 정의다.

| 구성 요소 | 내용 |
|---|---|
| 클래스 | `id`, `label`, `parent`(is_a), `description`, `keywords`(매핑 단서), `origin`(synthetic / sourced) |
| 속성 | `id`, `label`, `domain`(소속 클래스, 하위 클래스에 상속), `datatype`(string/int/float/enum/bool/date), `dimension`(pint 차원, 예: `[power]`), `canonical_unit`, `required`, `allowed_values` 또는 `range`(출처 필수), `aliases` |
| 값 동의어 | 열거형 값·제조사명 등의 별칭 → 정규 표기 (실제 제조사 별칭은 출처 필수) |
| 관계 | `id`, `domain`, `range`, `cardinality` — `has_component`(BOM), `manufactured_by`, `variant_of` |
| 외부 참조 | `external_ref`: DNV Gmod 제품 유형 코드(vista-sdk, MIT). 코드와 출처만 기록하고 데이터는 재배포하지 않음 |
| 식별 규칙 | 클래스별 자연키(예: 제조사 + 정규화된 형식명), 정규 제품명 생성 규칙 |

공통 속성(제조사, 형식명, 중량 등)은 상위 클래스에 두고 하위 클래스가 상속한다. 온톨로지 정의서(O2)는 YAML에서 자동 생성해 정의와 문서가 어긋나지 않게 한다.

### 4-2. 등록 데이터 구조

| 객체 | 역할 |
|---|---|
| `SourceDocument` | 업로드 파일, 해시, 형식, 파싱 결과 위치 |
| `ObservedFact` | 문서 내 위치별 추출값(원문 문자열, 정규화 값, 단위, 위치). 같은 속성이 여러 번 나오면 모두 보존 |
| `Finding` | 검증·중복 판정: 유형, 심각도, 상태(`pass / fail / unknown / not_applicable`), 근거 참조 |
| `EvidenceRef` | 근거 종류: 문서 관측값 / 온톨로지 제약 / 기존 등록 레코드 / (확장) 규정 조항 |
| `HumanEdit` | 담당자 수정·결정: 이전 값, 새 값, 사유, 시각 |
| `RegisteredProduct` | 확정 레코드: 클래스, 정규화 속성값(각각 근거 참조), 관계, 판본 |

값 없음·파싱 실패·근거 없음은 `pass`로 바뀌지 않는다. 같은 속성의 출현값이 서로 다르면 다수결로 확정하지 않고 불일치 `Finding`을 만든다.

### 4-3. 합성 데이터

| 데이터 | 규모 | 내용 |
|---|---|---|
| 제품 사양서 | 40건 | 클래스당 6~7건. PDF 20·Excel 12·DOCX 8, 레이아웃(표 / 서술 / 혼합) 3종 |
| 기존 등록 목록 | 150건 | 클래스당 25건. 사양서와 연결된 중복 6 + 유사 4 정답 쌍 |
| BOM | 4건 | 엔진(상위) + 과급기·펌프·청정기(구성품) (S3 시나리오) |
| 독립 수기 사양서 | 4~6건 | 생성기와 독립된 평가용 |
| 정답 라벨 | 전체 | 정답 클래스, 정규화 속성값, 원문 위치, 주입 항목, 중복 대상 ID |

값은 프로젝트가 만든 합성값이며 **가상 제조사·가상 형식명**을 쓴다. 공개 제조사 문서(커밋하지 않음)는 속성 구성·표기 방식·레이아웃의 참고로만 쓰고, 표기 변형은 그 문서에서 수집한 실제 표현 목록(`variant_catalog`)에서 뽑는다. 상세는 [데이터셋 준비 계획](dataset-plan.md).

### 4-4. 주입 분류

| 유형 | 정의 | 주입 방법 | 기대 처리 | 비율(제안) |
|---|---|---|---|---|
| V1 표기 변형 | 정상이지만 표기가 다름 | 속성명 별칭, 호환 단위, 숫자·날짜 형식, 제조사 별칭, 레이아웃 | 정규화 후 정답과 일치 (오류 아님) | 모든 문서에 1~4개 |
| E1 필수 누락 | 필수 속성 없음 | 항목 삭제 | `fail`(누락) | 20% |
| E2 단위 차원 오류 | 차원이 맞지 않는 단위 | 출력값에 회전수 단위 등 | `fail`(단위) | 15% |
| E3 형식 오류 | 데이터형·형식 위반 | 정수 자리에 범위 문자열, 형식명 패턴 위반 | `fail`(형식) | 15% |
| E4 허용값 위반 | 열거형 밖 값 또는 출처 있는 범위 이탈 | 값 교체 | `fail`(허용값) | 10% |
| E5 문서 내 불일치 | 같은 속성의 출현값이 다름 | 한 위치의 값만 변경 | `fail`(불일치), 출현 위치 모두 제시 | 15% |
| E6 중복 | 기존 등록 제품과 같은 제품 | 기존 레코드를 V1 변형해 사양서로 렌더 | `duplicate` | 15% |
| E7 유사 | 같은 계열의 다른 제품 | 핵심 속성 일부만 변경 | `similar` | 10% |

정상 문서(오류 주입 없음, V1만 포함)를 최소 25% 둔다. 대표 유형은 하나로 고정하고 부가 원인은 태그로 둔다. E4의 범위 이탈은 출처가 확인된 범위가 있을 때만 주입한다.

### 4-5. 데이터 분리

- 제품 계열(같은 원본 제품에서 나온 변형) 단위로 개발셋·테스트셋을 나눈다. 테스트셋은 W3 이후 고정한다.
- 정답 라벨은 평가기만 읽는다. 추출기·프롬프트·동의어 사전 작성에 테스트셋을 쓰지 않는다.
- 생성기와 독립적으로 **사람이 직접 작성한 사양서 3~5건**을 별도 평가셋으로 둔다(생성기 편향 점검).

## 5. 아키텍처

### 5-1. 설계 원칙

1. **의미 해석은 LLM + RAG가, 측정·검증은 코드가**(D-042 개정): 문서 표현을 온톨로지 어휘로 옮기는 일(라벨→속성, 표시형→열거 토큰, 비고→기준·조건·범위)은 검색된 근거와 예시를 받은 LLM이 한다. 단위 환산·수치 파싱·스키마·근거 위치 확인·검증 규칙·중복의 식별 일치·채점은 결정론 코드가 한다. 표기 변형이 늘면 코드 규칙이 아니라 **지식 베이스(데이터)**가 늘어난다.
   - ~~LLM은 클래스 후보와 원문 값 추출까지만, 정규화·검증·중복 판정은 결정론 코드가 한다.~~ (v2 원문, 2026-10-13 개정)
2. **온톨로지가 진실원천**: 스키마·프롬프트·검증 규칙·정의서가 모두 온톨로지 YAML에서 파생된다.
3. **근거 없는 값은 등록하지 않는다**: 모든 등록 값은 원문 위치 또는 사람 수정 기록을 가진다.
4. **모름은 통과가 아니다**: `unknown`은 검토 대기로 남는다.
5. **로컬 우선**: 클라우드는 비교 실험용 옵션.

### 5-2. 구성요소(노드)

> **용어(D-043)**: **구성요소(노드)**는 파이프라인의 기능 단위다. W5에서 LangGraph 노드가 되며, 결국 모두 구현한다. **실험 구성(config)**(6-2의 R·A~E)은 같은 파이프라인을 어떤 방식으로 돌릴지 바꾼 비교용 변형이다. 비교 결과로 각 노드의 최종 설계를 고른다.

| 구성요소(노드) | 역할 | LLM 사용 |
|---|---|---|
| Ontology | YAML 로더, 무결성 검사, 스키마·정의서 생성 | ❌ |
| Parser | PDF/Excel/DOCX → 텍스트·표 블록 + 위치 | ❌ |
| Classifier | 키워드 점수 + LLM 판정 → 클래스 top-k | ✅ |
| Knowledge Base · Retriever | 개발 분할 정답 예시·온톨로지 정의를 임베딩해 적재(Chroma/FAISS), 하이브리드 검색으로 값 단위 예시·정의 제공 (D-042) | 임베딩 |
| Extractor | 클래스별 JSON Schema 구조화 출력 → `ObservedFact` | ✅ (+ 정규식 보조) |
| Normalizer | 동의어·단위·형식 정규화 | ❌ |
| Validator | 필수·차원·형식·허용값·불일치 검사 → `Finding` | ❌ |
| Deduplicator | 기존 등록 목록 대비 중복·유사 판정 | 부분 (이름 임베딩) |
| Registrar | 사람 확정 → `RegisteredProduct`, 표준 JSON 출력 | ❌ |
| Orchestrator | LangGraph: 등록 그래프, HITL 중단점 | — |
| Audit | 모든 호출·결정 기록 | ❌ |

### 5-3. 그래프 흐름

- **등록 모드**: 업로드 → Parser → Classifier → (`unknown`이면 HITL 클래스 선택) → Extractor → Normalizer → Validator ∥ Deduplicator → 결과 통합 → **HITL(값 수정·중복 처리·등록 확정)** → Registrar → 표준 JSON
- **일괄 모드(BOM)**: Excel → 행 단위 등록 모드 → 관계 생성 → 오류 행만 HITL

LangGraph interrupt 재개 시 노드가 처음부터 다시 실행될 수 있으므로(착수 리서치 6.4) 등록·로그 쓰기는 멱등하게 설계한다.

### 5-4. 저장소 구조 (제안)

### 6-2. 비교 실험 (핵심 산출물)

> 아래 행은 **실험 구성(config)**이다. 에이전트나 기능 단위가 아니다. 각 구성은 앞 구성에 한 가지를 더하거나 바꾼 변형이라, 두 구성의 차이가 그 변경의 효과다(ablation). **R(규칙 기준선)**은 LLM을 쓰지 않는 바닥선이다(D-025). E의 변형 E0~E3은 [W4-R 계획](superpowers/plans/2026-10-13-w4r-rag-semantic-mapping.md)에 있다.

| 노드 \ 실험 구성 | R | A | B | C | D | E |
|---|---|---|---|---|---|---|
| Classifier | 키워드 | LLM | LLM | LLM | LLM | LLM |
| Extractor(값) | 개발 라벨 사전 | LLM 자유 JSON | LLM + 스키마, 값 정규화도 LLM | LLM + 스키마, 원문 그대로 | C와 같음 | C와 같음 |
| Extractor(한정 정보) | 기본값 | 없음 | LLM이 함께 | LLM이 함께 | C와 같음 | **값마다 RAG 체인 + 근거 구절 검증** |
| Normalizer | 코드 | 없음 | 없음 | 코드 | 코드 | 코드 |
| Validator 피드백 | — | — | — | — | 실패 속성 재추출 1회 | (D와 결합 가능) |

| 실험 구성(config) | 설명 |
|---|---|
| A. LLM 단독 | 문서 전체를 주고 "제품 정보를 JSON으로 추출하라" (자유 형식) |
| B. + 온톨로지 스키마 | 클래스 매핑 후 클래스별 JSON Schema로 구조화 추출 |
| C. + 결정론 정규화 | 동의어·단위·형식 정규화 |
| D. + 검증 피드백 | Validator 결과로 실패 속성만 재추출 1회 |
| **E. + RAG 의미 매핑** (D-042) | 값마다 그 줄·머리글·절 제목과 **검색된 정답 예시·어휘 정의**를 주고 기준·조건·범위(이후 표시형·라벨)를 구조화 출력으로 받는다. 근거 구절은 코드가 확인한다. 변형(검색 방식·Parent Document·Multi-Query·Self-RAG)별 기여를 따로 잰다 |

로컬 모델로 A~D 4행을 기본으로 만든다. 클라우드 행은 모델과 비용 상한이 정해지기 전까지 "미실행"으로 표시한다. 가설은 "온톨로지 스키마가 매핑·추출 구조를, 결정론 정규화가 표기 변형에 따른 F1 손실을 줄인다"이며, 가설이 틀려도 결과를 그대로 기록한다. 모델·프롬프트·컨텍스트·재시도·temperature를 기록하고 입력 정책을 실험 구성 간에 고정한다.
