2026-10-16 · 검토: Codex · 기준: `69829d1` 및 현재 작업 트리의 CP-S4 패키지

**검토 의견: 공개 전 보완 필요.** 저장된 예측에서 핵심 평가 수치와 부트스트랩 구간은 재현됐다. 테스트 E1SV F1 0.913, G3 0.875 미달, 수기 문맥 1/13이라는 결론을 뒤집는 수치 불일치는 발견하지 못했다. 다만 공개 문서의 사실과 다른 보장, 새 환경의 실행 절차 누락, 동결 검사 범위의 공백, 공개 후보 압축파일의 개인 경로 잔존을 수정해야 한다.

## 2. 수정이 필요한 발견 사항

### R1 · P2 · 공개 후보 백업 압축에 개인 절대 경로가 남아 있음

위치: `tests/test_no_originals.py:71–80`, `data/backups/2026-10-08-v2-before-D014.tgz`, `data/backups/2026-10-08-v7-after-D018.tgz`.

홈 경로 검사는 `.tgz`를 제외하고, 압축 검사에서는 참고 문서의 경로/확장자만 본다. 따라서 현재 검사 통과는 압축 안의 공개 적합성까지 보장하지 않는다.

실제 내용을 읽어 확인한 결과, 위 두 압축 각각에서 `docs/decisions.md`와 `__pycache__` 아래 `.pyc` 3개, 총 4개 파일에 홈 절대 경로가 있었다. 경로 원문은 리뷰에 재기재하지 않았다. 세 번째 작성 자료 보관본에서는 같은 패턴을 찾지 못했다. 참고 문서 12개와 동일한 해시의 파일은 세 압축 모두 없었다.

**조치:** 복원용 v2/v7 스냅샷은 새 공개 저장소에서 제외하는 것을 권고한다. 유지해야 한다면 개인정보·캐시·불필요한 메타데이터를 제거한 별도 공개용 사본을 만들고 내부 파일도 검사한다. 기존 보관본을 덮어쓰거나 이력을 삭제할 필요는 없다. 공개 전 검사는 실제로 배포할 파일 집합과 압축 내부까지 대상으로 해야 한다.

### R2 · P2 · 빠른 시작과 재현 가이드가 새 환경의 준비 단계를 빠뜨림

위치: `README.md:57–66`, `docs/run-guide.md:13–21`, `docs/run-guide.md:59–78`.

가이드는 Docling 모델을 첫 PDF 파싱 때 다운로드한다고 설명하지만, 실제 파서는 `HF_HUB_OFFLINE=1`을 강제하고 모델 폴더가 없으면 즉시 `ParseError`를 반환한다. README의 명령만 따라서는 새 환경에서 PDF를 처리할 수 없다.

**재현:** `pdf_parser.MODELS`를 임시의 없는 폴더로 지정하고 합성 PDF를 전달했더니 `Docling models missing: uv run docling-tools models download layout tableformer -o var/models/docling` 오류가 반환됐다. 네트워크나 모델 서버를 호출할 필요 없이 확인할 수 있는 준비 단계 문제다.

최종 실험 재현에도 `var/eval/FREEZE.json`, `var/parsed/test`, `var/parsed/handwritten` 준비가 빠져 있다. 이들은 새 저장소에 없는 산출물이다. 커밋된 동결 사본은 `docs/reports/w6-freeze.json`이고, 실행기는 사본을 자동으로 읽지 않는다. `scripts/w6_runs.sh`도 입력 파싱과 기록 복원을 대신하지 않는다.

**조치:** 오프라인 실행 전에 명시적 Docling 모델 다운로드 명령을 넣는다. 새 환경의 재현 절차는 잠금 파일 설치 → 모델 준비 → dev/test 파싱 → 수기 입력 준비 → 공개된 동결 기록 복원·검증 → 구성별 실행으로 작성한다. 기존 평가를 재현하면서 새 `freeze write`로 다른 시스템을 다시 동결하지 않도록 구별한다. 원자료가 없는 새 저장소에서는 기존 날짜 경로의 `rescore` 명령을 바로 실행할 수 없다는 점도 명시한다.

### R3 · P2 · README의 완전한 테스트 비노출 주장이 기록과 다름

위치: `README.md:30`.

“테스트 분할은 개발 중 한 번도 보지 않았다”는 문구는 다음 기록과 충돌한다.

- D-023: 별칭 선정 중 테스트 분할의 표기 출현 분포 확인.
- D-024: 테스트 정답의 raw_text 문자 집합 1회 접근.
- D-028의 W3-6 기록: 테스트 SYN-009 정답의 앞 80줄, 관찰 4개 출력.
- W2: 테스트 입력 16건의 파싱 smoke test 수행.

각 기록은 사용하지 않고 폐기했다는 설명도 포함한다. 그 설명을 유지하면서 접근 예외를 공개해야 한다. 이번 리뷰가 새로운 튜닝 누출을 발견했다는 뜻은 아니다.

**조치 예시:** “테스트 분할의 최종 성능 평가는 시스템 동결 후 구성별로 실행했다. 개발 중 입력 파싱 점검과 제한된 정답 접근 예외가 있었으며 D-023·D-024·D-028에 기록했다. Copt는 사후 추가 참고 행이다.” 완전한 블라인드·무접근 평가라는 인상을 주지 않도록 한다.

### R4 · P2 · ‘문서 밖 값은 입력할 수 없다’는 사용자 보장이 실제 수정 기능과 다름

위치: `README.md:25`, 관련 구현 `spec_bridge/registry/edits.py:130–153`.

사람 수정은 블록 위치·자료형·정규화 규칙을 검사하지만 값이 해당 블록에 실제로 있는지 확인하지 않는다. `add`의 `occurrence.raw_text`도 사용자 입력 문자열에서 만든다. 모델·데이터 카드 §7은 이미 “원문과 다른 값을 입력해도 정규화·검증을 통과하면 등록된다”고 설명하므로 공개 문서끼리도 충돌한다.

**재현:** 개발 문서에 존재하지 않는 식별 문자열을 `model_designation`으로 지정하고 유효한 블록 0을 가리킨 `FactEdit(op='add', ...)`를 호출했다. `apply_edit`는 unresolved 없이 `outcome='fact'`로 수용했다. 이는 편집 수용 재현이며, 전체 등록까지 실행한 것은 아니다.

**조치:** 현 HITL 정책을 유지한다면 “모든 수정은 원문 위치와 수정 사유를 기록하지만, 사람이 입력한 값과 원문의 의미적 일치는 자동 보장하지 않는다”로 통일한다. 원문 일치 강제는 별도 제품 정책이며 이번 리뷰에서 코드 동작을 바꾸라고 요구하는 것은 아니다.

### R5 · P2 · 동결 검사가 결과에 영향을 주는 설정 변경을 놓침

위치: `spec_bridge/eval/freeze.py:34–51`, `spec_bridge/service.py`의 `RAG_K`, `RAG_EMBEDDING`, `make_rag`.

동결 목록에는 `service.py`가 없다. 이 파일은 검색 사례 수와 임베딩 모델 등 실제 RAG 구성을 결정한다. 정규화 구현(`normalize/values.py` 등), 실행 연결 코드와 파싱 캐시도 현재 목록의 직접 해시 대상이 아니다. 데이터셋은 SHA256SUMS 파일 자체의 해시를 비교하고, `verify()`가 목록의 실제 파일 해시를 다시 검증하지는 않는다.

**재현:** 임시 디렉터리에 실행 모듈·해시 대상 자료·기존 FREEZE 기록을 복사했다. 그 사본의 `service.py`에서 **`RAG_K = 3`을 `RAG_K = 1`로 변경**한 후 별도 Python 프로세스에서 `verify()`를 실행했다. 종료 코드 0으로 통과했고 실제 상수는 1이었다. 원래 작업 트리나 동결 파일은 수정하지 않았다.

**영향:** 현재 보관 실행의 수치가 틀렸다는 증거는 아니다. 다만 `freeze verify` 통과만으로 “결과를 결정하는 시스템 전체가 바뀌지 않았다”고 보장할 수 없다. 모델 digest도 현재 코드에서는 기록 후 대조하는 항목이지 자동 동결 가드가 아니다.

**조치:** 기존 W6 동결 원본은 보존하고, 재현용 manifest/검증에 실행 설정·정규화 코드·의존성·실제 입력/정답 및 파싱 산출물 식별자를 보완한다. 변경을 자동 거부할 범위와 단순 기록하는 범위를 구별한다. 기존 평가 기록을 새 해시로 소급 교체하지 않는다.

### R6 · P2 · 공개 재현 CLI가 테스트와 수기에 개발 기준으로 판정함

위치: `spec_bridge/eval/compare.py:69–85`.

`judge()`는 분할을 받지 않고 문맥 FP 한도 16과 문맥 TP 목표 50을 고정 사용한다. 테스트 사전 등록은 한도 10, 목표 38이고 수기 목표는 7이다. 따라서 현재 `compare` 출력의 `verdict_*`는 D-080 판정기를 재현하는 것이 아니다.

**재현:** 실제 테스트 점수를 넣으면 (b)의 `limit`이 16으로 출력된다. 테스트 문맥 FP가 11~16인 경우 합격을 잘못 낼 수 있고, TP가 38~49인 경우 목표권 충족을 잘못 거부할 수 있다. 현재 실제 값은 FP 8·TP 62이므로 이 차이로 보고서의 현재 결론이 바뀌지는 않는다. 패키지와 보고서가 이 한계를 이미 적은 것은 적절하지만 CLI의 자동 verdict는 여전히 오해를 만든다.

**조치:** D-048 개발 판정과 D-080 최종 판정을 명시적으로 분리하거나, CLI는 수치/구간만 내고 기준이 없는 상태에서 합격 여부를 출력하지 않는다. 수기 ③의 (c)+목표권 조건을 테스트 (a)~(c)와 같은 절차로 자동 판단하지 않도록 한다. 채점기와 기존 지표는 그대로 보존할 수 있다.

### R7 · P3 · SYN-022 E4 누락의 직접 원인을 잘못 기재함

위치: `docs/reports/w6-final-evaluation.md:171`.

보고서는 medium 누락 때문에 허용 목록 검사가 실행되지 않았다고 설명한다. 하지만 Separator의 허용 목록은 **application**에 있고 SYN-022의 정답 E4도 `attribute_ids: [application]`이다.

**재현:** 저장된 E1SV 예측에 정답 medium만 복원하면 E4가 없고, application을 복원하면 E4(application)가 발생한다. 실제 누락 6개 집합 안에 두 속성이 모두 있어 전체 “추출 누락이 원인”이라는 설명과 G3 수치에는 영향이 없지만, 정확한 원인 추적을 위해 `application`으로 고쳐야 한다.

## 3. CP-S4 질문에 대한 판단

### Q1. G1~G5 수치는 재현되는가?

저장된 예측으로 G1~G4와 사전 등록의 핵심 차이/구간을 재현했다. G1 0.913, G2 1.000, G3 0.875, G4 0.938/1.000의 보고는 맞다. G5는 단일 수치 통과 항목이 아니라 비교 설계의 해석이며, 아래 L6/L8의 한계를 함께 붙여야 한다.

원자료 미공개는 이미 밝혀져 있지만, “아무 준비 없이 공개 저장소만으로 기존 결과를 재채점 가능”한 상태는 아니다(R2). 최소 재채점 묶음으로 run 설정·예측 JSON·문서별 점수·동결 사본·해시 목록을 제공하는 방안을 권고한다. 감사 원문은 선택 사항이며 포함 전 경로·인증정보를 별도로 확인해야 한다. 공개 여부는 사용자 결정이다.

### Q2. 합성 고지·원문 미커밋·출처는 적절한가?

현재 추적 파일의 참고 원문 해시/문서 위치 검사는 통과하고 합성 고지는 명확하다. 기존 이력을 그대로 공개하면 안 된다는 D-094의 새 저장소 방식은 유지하는 것이 맞다. 단, `git ls-files` 전체를 무조건 새 저장소에 복사하면 R1의 백업 내용도 공개된다.

| 포함 | 실행 소스·테스트·웹 소스, CI, 잠금 파일, 온톨로지·개발 사전·KB, 동결 합성 입력/정답/registry, 수기 입력/변환 정답, 출처 manifest, 보고서·설계 문서 |

`docs/archive/`와 공개된 조사 출처 URL 자체를 일괄 삭제할 근거는 발견하지 못했다. 현재 문서와 과거 설계가 혼동되지 않도록 보관 상태를 표시하면 된다. 생성기 등 데이터 작성 자료를 공개하려면 전체 과거 스냅샷보다 필요한 작성 소스만 별도 경로로 추려 두는 편이 명확하다. 사용자 검증 서명은 임의로 수정하지 않는다.

이번 감사는 법적 권리 검토가 아니다. 원문 비포함 여부와 프로젝트가 정한 배포 정책 준수 범위를 확인했다. 현재 저장소 비공개라는 사실만으로 과거 전체 기간의 외부 접근이 전혀 없었다고 기술적으로 입증한 것도 아니다.

### Q3. 결론의 수위는 적절한가?

“같은 생성 규칙의 계열 분리 합성 테스트에서 E1SV 구성의 성능이 기준선보다 높았다”는 결론은 자료가 뒷받침한다. “실제 선박 사양서 전반의 어휘/문맥 문제를 해결했다”거나 “LLM 단독은 원래 F1 0.03”이라는 일반화는 뒷받침하지 않는다.

README 표 가까이에 같은 생성 규칙, 16문서·모델 하나, G2/G4 지름길을 짧게 붙이는 것을 권고한다. 수기 F1 저하에는 정규화 밖 표기뿐 아니라 문맥/범위 해석 실패도 있으며, 문맥 1/13을 단위 사전 문제 하나로 설명하지 않는다. 사후 운영 보완과 동결 평가 성능을 분리해 적어야 한다.

## 4. L1~L8 답변

| 항목 | 검토 의견 |
|---|---|
| L1 소표본 bootstrap | 정수 TP에 “51.5% 이상”을 적용하면 ceil이 맞다. 테스트 ceil(72×0.515)=38, 수기 ceil(13×0.515)=7이다. 문서 단위 쌍체 재표집·micro 재계산과 보고된 구간을 재현했다. 16/6문서 및 같은 계열·생성기 상관 때문에 이를 산업 문서 모집단의 확정적 효과나 모델 반복 실행 불확실성 구간으로 확대하지 않는다. 사전 등록 절차를 사후 교체할 필요는 없다. |
| L2 오류 원인 순서 | FN/FP 합계는 맞지만 자동 짝짓기는 원인의 증명이 아니다. 특히 `_miss_cause`는 같은 속성의 관찰 중 하나라도 전체 텍스트에 있으면 not_extracted로 보고, 같은 속성의 unresolved가 하나라도 있으면 그쪽으로 분류한다. 여러 조건의 같은 속성에서 특정 값이 파싱에서 빠진 경우까지 정확히 구별하지 못한다. “parse 0”은 이 휴리스틱의 결과라고 한정하고, 중요 원인은 개별 fact/observation ID·위치·모델 입력/응답으로 확인한다. R7을 고친다. |
| L3 문맥 알림 | `context_hints()`는 실제로 제안됐다가 거부된 문맥이며 속성+위치가 맞는 기록만 표시한다. 아예 제안하지 않은 문맥, 검증을 통과한 잘못된 문맥에는 표시가 없을 수 있다. “문맥 차이가 있으면 표시된다”는 포괄 표현 대신 이 조건을 쓴다. 현재 수치로 인용하지 않은 판단은 적절하다. |
| L4 사후 경고 | D-091은 평가 뒤 같은 오답을 보고 만든 기능이다. 자동 평가 수치는 유지되지만 7/7·오탐 0은 사후 회귀 확인이며 독립 성능 평가가 아니다. README·케이스 스터디의 효과 문장 바로 옆에 이 사실을 명시한다. 모든 미래 사전 밖 표기를 경고한다는 보장도 피한다(실제 term_notes는 개발 사전에 항목이 있는 속성만 다룸). |
| L5 오프라인 | 35건 루프백과 지정 PID의 표본 기록을 재확인했다. “관찰에서 외부 연결이 보이지 않았다”는 표현은 적절하다. 1초 표본, 네이티브/자식 프로세스, 최초 다운로드 및 데스크톱 앱 제외 한계가 있어 모든 실행에서 외부 호출이 불가능하다는 보장으로 바꾸지 않는다. |
| L6 A/B/C | 필수형 표기를 유지하고 표 아래에 스키마 강제의 영향을 받은 특정 설계 결과임을 명시한다. 사후 Copt는 0.497로 차이가 크므로 독자가 일반적인 zero-shot 성능을 0.03으로 오해하지 않게 같은 위치에서 안내한다. E0·E1SV·R에 대한 사전 등록 판정 자체는 이 오류의 영향을 받지 않는다. |
| L7 CI | 로컬 깨끗한 복제본 검사는 GitHub Actions 성공이나 Linux 의존성 신규 설치 성공을 대신하지 않는다. 실제 CI 미실행 표기를 유지한다. 현재 README에 CI 성공 배지는 없어 허위 성공 표시는 발견하지 못했다. 커버리지도 미측정으로 남아 있어 W6 “측정해 보고” 항목은 미완료다. |
| L8 G5 표현 | “사례가 어휘 해석을 가르친다”보다는 “개발 합성 문서에서 해결 사례 제공 뒤 문맥 키 정답이 증가했다”로 좁히는 것이 정확하다. 테스트 E0→E1SV 차이는 검색·지지 검증·충돌 해소의 묶음 효과이며 검색만의 효과를 분리한 테스트 실험은 아니다. 수기 1/13을 함께 제시하고 실제 문서 일반화나 모델 학습 효과로 표현하지 않는다. |
