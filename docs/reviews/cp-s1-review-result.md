## 수정이 필요한 발견 사항

### R1 · P2 · 제조사 재적재에서 기존 DB와의 별칭 충돌을 무시함

위치: `spec_bridge/registry/store.py:87–100`.

`MakerIndex(makers)`는 이번 입력 목록 내부만 검사한다. 기존 DB에 A 제조사의 정규명이 등록된 상태에서, 그 이름을 B 제조사의 별칭으로 넣은 별도 파일을 적재하면 `INSERT OR IGNORE`가 충돌을 무시하고 성공을 반환한다.

재현: 개발 제조사 목록의 첫 제조사를 먼저 적재한 뒤, 두 번째 제조사에 첫 제조사의 이름을 별칭으로 넣어 따로 적재했다. 두 호출 모두 `1`을 반환했고 해당 별칭은 첫 제조사에 남았다. 호출자는 두 번째 제조사의 별칭 등록이 성공한 것으로 오인하며 식별 조회 결과가 입력 계약과 달라진다. 같은 `maker_id`에 다른 내용을 재적재하는 경우도 묵시적으로 무시한다.

권고: 기존 DB와 입력을 함께 비교해 이름/별칭의 소유 제조사가 다르면 전체 트랜잭션을 거부한다. 완전히 동일한 내용만 멱등 재적재로 허용한다. 회귀 검사는 반드시 두 번의 적재 호출로 구성한다.

### R2 · P2 · 제품의 검색 식별자와 저장 사실이 서로 달라도 등록됨

위치: `spec_bridge/registry/store.py:124–135`.

최상위 `maker_id`/`model_designation`으로 제품의 자연키를 저장하면서, `attributes.maker`/`attributes.model_designation`과의 일치 여부를 검사하지 않는다. 생성 모델은 개별 사실 자료형만 검사한다.

재현: 개발의 독립 등록 레코드에서 최상위 모델명만 `VX001-002-CHANGED`로 바꾸고 모델명 사실 `VX001-002`는 유지했다. 적재는 `1`을 반환했고 두 값이 그대로 저장됐다. `find_by_identity()`가 사용하는 모델명과 사실에 기록된 모델명이 달라져 중복 탐지와 제품 표시가 불일치한다.

권고: 모델명은 `model_key`로, 제조사 사실은 등록명/별칭 조회로 대조한다. 실제로 다른 식별자는 거부하고 허용된 공백·하이픈·대소문자 및 제조사 별칭 변형은 유지한다.

### R3 · P2 · 중요 기준이 미상이어도 등록 준비 상태를 ready로 반환함

위치: `spec_bridge/ontology/policy.py:38–46`.

`policy_status()`의 `review` 분기는 조건부 필수 규칙의 분기값만 검사한다. 현재 YAML에서는 사실상 펌프 형식에만 적용된다. `present()`는 basis/condition/scope를 버리므로 다른 클래스의 중요 기준 불명 상태를 판단할 수도 없다.

재현: 정상 개발 AirCompressor 정답의 사실값은 유지하고 모든 `basis`와 `condition`을 비우고 `scope`를 `unknown`으로 바꾸면 생성 모델은 수용하고 `policy_status()`는 `ready`를 반환했다. 이는 `schema-design.md` §5의 압축기 “미상 기준은 review”와 다르다. 엔진·분리기·과급기의 중요 기준에 대해서도 같은 설계 공백이 있다.

권고: 중요 기준의 review 정책을 온톨로지에 명시하고 해석하거나, W1 함수의 의미를 “필수 존재 검사”로 명확히 제한하고 완전한 등록 준비 판정과 분리한다. E4/E5 전체 검사를 W4로 미룬 결정 자체를 결함으로 지적하는 것은 아니다. 현재 `ready` 명칭과 패키지가 참조하는 등록 준비 정책 사이의 차이를 해소해야 한다.

### R4 · P2 · 기존 DB를 열기만 해도 버전 메타데이터가 덮어써짐

위치: `spec_bridge/registry/store.py:73–81`.

생성자는 기존 `schema_version`/`ontology_version`을 비교하지 않고 `INSERT OR REPLACE`한다. `CREATE TABLE IF NOT EXISTS`는 기존 스키마를 마이그레이션하지 않으며 이미 적재된 사실을 재검증하지도 않는다.

재현: version 0 온톨로지로 제품 1개를 적재하고 닫은 뒤, version만 1로 바꾼 온톨로지로 같은 DB를 열었다. 기존 제품은 그대로인데 `ontology_version`은 `1`로 바뀌었다. 이후 내용이 동일한 시드는 멱등 키 검사에서 빠져나가 재검증되지 않는다.

권고: 새 DB에서만 버전을 초기화하고 기존 DB는 호환성을 먼저 검사한다. 버전이 다르면 재생성 또는 명시적 마이그레이션을 요구한다. 재생성 가능한 W1 DB에서는 버전 불일치 오류와 재생성 안내만으로도 처리할 수 있다.

### R5 · P2 · 검토 패키지가 제안하는 별칭별 synthetic 전환을 모델이 표현하지 못함

위치: `spec_bridge/ontology/definitions.py:42–47`, `ontology/ontology.yaml`의 `label_aliases` 목록.

패키지는 미검증 별칭을 항목별 `origin: synthetic`으로 바꾸는 선택지를 제시한다. 그러나 `LabelAlias`에는 `origin` 필드가 없고 `extra=forbid`가 적용된다.

재현: 첫 별칭에 `origin: synthetic`만 추가한 YAML을 로드하면 `label_aliases.0.origin: Extra inputs are not permitted`로 실패했다. 루트의 `origin: synthetic`은 이미 존재하므로 이를 근거로 개별 출처 기반 별칭의 미검증 문제가 해결됐다고 볼 수 없다.

권고: 항목별 출처/합성 상태를 모델과 생성 정의서에서 표현하도록 보완한 후 사용자가 선택한 처리를 적용한다. 검증/합성 전환/제거 중 어느 것을 택할지는 이 리뷰에서 결정하지 않았다.

## 후속 조치

R1~R5에 대한 수정 또는 명시적 범위 조정과 회귀 검사를 먼저 진행한다. 이어서 미검증 별칭의 사용자 결정과 NFR-07의 시드 적용 범위를 문서에 반영한다. 이번 리뷰에서는 실행 코드, 동결 데이터셋, DB 스키마, 사용자 검증 서명을 변경하지 않았다.
