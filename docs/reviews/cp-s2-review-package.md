# 🔶 CP-S2 교차 검토 패키지 — W2 합성 데이터·주입 분류·파서

2026-10-12 · 작성: 헬퍼 모델 · 상태: **검토 완료 — 보완 필요 → R1~R6 수정**([검토 결과](cp-s2-review-result.md), decisions.md `CP-S2`). 헬퍼는 통과 판정을 하지 않는다(H2-4).

## 1. 배경 (5줄)

1. spec-bridge는 선박 기자재 6종 제품 문서에서 속성을 추출·정규화·검증해 중복을 검사하고 등록하는 로컬 우선 도구다. W1(온톨로지·등록 저장소)은 CP-S1 보완(D-022·D-023)까지 끝났다.
2. W2의 합성 데이터 작업(렌더러·오류 주입·라벨·계열 분리)은 데이터셋 v1 단계에서 먼저 끝났고(D-006~D-019, D-020으로 W2 범위 축소), 이번 W2 구현은 PDF·Excel·DOCX 파서와 원문 위치 보존이다.
3. 파서는 LLM·네트워크 없이 문서를 블록 목록(원문 텍스트 + 위치)으로 바꾸고, 실패는 `ParseError`로 보고해 W3에서 unknown 처리한다.
4. 위치 정확도는 개발 분할 24건의 정답으로만 측정했고, 테스트 분할 16건은 파싱 가능 여부만 확인했다(D-020 연장).
5. 이 검토 결과에 따라 W3(매핑·추출·정규화)로 넘어가기 전에 데이터셋·파서를 수정할지 결정한다. 이후 모든 평가가 이 둘에 기반한다.

## 3. CP-S2 검토 질문 (계획서 H4)

1. **표기 변형이 실제 담당자 차이를 대표하는가, 추출기에 유리하게 편향되지 않았는가?**
   - D-015·D-016에서 스키마 토큰 노출을 없애고(본문의 snake_case·`basis:` 0건), 라벨을 원본 관찰 표기 + 합성 일반 라벨로 다양화했다. 절 제목 3세트·표 머리글 3종·레이아웃 table 18/mixed 15/narrative 7.
   - 남은 편향(D-018 독립 감사): 개발셋 라벨 사전만으로 테스트 관찰의 **91.6%**를 속성에 대응할 수 있다. similar는 모델명 시리즈 접두사 규칙만으로 P/R **1.0**이다. 결과 보고 때 이 기준선과 비교하도록 README에 적었다. 이 수준의 편향이 W3 비교 실험(A~D)의 해석을 무너뜨리지 않는가?
   - 라벨 별칭 21개는 전부 `origin: synthetic`(D-022)이다. 원본 표기의 대표성은 사용자 검증 전이다.
2. **오류 유형 간 경계가 겹치지 않아 라벨이 한 가지로 정해지는가?**
   - 오류 20건(E1 6·E2 4·E3 4·E4 4·E5 2), 문서당 최대 1개, 한 관찰이 두 오류에 걸린 경우 0(D-018 감사).
   - E2/E3가 필수 속성에 걸리면 오류 코드는 하나만 쓰고 `missing_required`에 기록한다(D-015). E4는 존재하는 사실로 보아 누락이 아니다. 실린더 범위는 E3에서 정상 문맥으로 전환했다(D-014).
   - E6/E7(중복·유사)는 비교 정답 파일로 분리했고 similar 정의는 "같은 합성 계열"이다(D-016).
3. **파일명·주석·문장에 정답이 노출되지 않는가?**
   - 입력 파일명은 `SYN-xxx`이고 사례·분할 정보가 없다. 본문의 평가 표식(`E1`~`E7`, `FAM-`, `answer` 등) 0건(D-018 감사).
   - 알려진 신호: 모델명 접두사(`VX0nn`)가 계열을, 제조사명 접미사(A/B 개발, C/D 테스트)가 분할을 드러낸다(D-015 문서화). PDF 메타데이터는 `title: Synthetic technical specification`, `author: Synthetic dataset`(정답 정보 없음).
   - 문서 끝 "Supply notes"의 합성 고지 문장은 40건 모두 같다.
4. **데이터 분리가 제품 계열 기준인가?**
   - 계열 24개를 개발 12·테스트 12로 나눴고 계열 겹침 0(D-007, case-plan 검사). 등록 DB도 분할별 파일이다(D-021).
   - W1·W2 코드·테스트·사전은 테스트 분할 정답을 읽지 않는다(`load_dev_answer` 가드, `dev_documents` 필터). 예외 기록: W2-0 특수문자 점검에서 테스트 정답 raw_text 문자 집합을 한 번 읽었고 결과는 폐기했다(D-024).

## 4. 파서 부분 — 헬퍼가 확신이 낮은 지점

| # | 지점 | 현재 처리 | 확인 요청 |
|---|---|---|---|
| P1 | PDF 위치 판정 | 블록(글자 상자) 중심이 정답(레이아웃 영역) 안 ±2pt. 계획의 반대 방향 판정은 틀려서 W2-5에서 정정 | 인접 칸·줄이 같은 영역에 들어갈 가능성 — 원문 포함 조건으로 충분히 배제되는가 |
| P2 | 회수율 지표 | 정답 관찰마다 "같은 위치 + raw_text 포함" 블록이 있는지만 본다(recall) | 블록이 너무 크게 묶이거나(라벨+값+조건이 한 블록) 유령 블록이 생기는 것은 재지 않는다. W3 추출 입력으로 블록 단위가 적절한가 |
| P3 | PDF 원문 | Docling 텍스트 대신 같은 좌표로 PDF 글자층을 다시 읽음(`—` 보존). 표 칸 끝 공백(`'6 '`)도 원문으로 보존 | 좌표 상자가 글자를 일부만 덮는 경우(가장자리 잘림)의 위험 — 합성 PDF에서는 0건이나 일반 PDF에서도 안전한가 |
| P4 | 좌표 원점 | 본문 BOTTOMLEFT·표 칸 TOPLEFT가 섞여 나와 `to_bottom_left_origin`으로 통일 | 다른 Docling 버전에서 원점 표시가 바뀔 때의 회귀는 `test_boxes_use_bottom_left_origin`·표 칸 범위 테스트로 충분한가 |
| P5 | 제목·절 제목 판정 | XLSX: 굵은 행 순서(첫째=title). DOCX: 굵기+16pt. PDF: 첫 SectionHeader=title | 렌더러 스타일(D-017)에 맞춘 규칙이라 다른 문서에는 약하다. 절(section)은 W3 문맥에만 쓰고 판정 근거로 쓰지 않는 것이 맞는가 |
| P6 | DOCX 수정 추적 | `w:ins`/`w:del`이 있으면 처리를 거부(`ParseError`) | 수락본 기준 파싱 같은 대안 없이 거부만 하는 정책이 적절한가 |
| P7 | XLSX 숫자 칸 | `str(value)`로 원문화. 합성은 전부 텍스트 칸이라 영향 0 | 실제 숫자 칸의 표시 형식 손실(`30.50`→`30.5`)을 W3에서 다루면 되는가 |
| P8 | Docling 의존 | 모델·버전에 따라 결과가 달라질 수 있음. 파싱 결과에 파서 버전 기록, 회수율 테스트로 고정 | 모델 파일 해시까지 기록해야 하는가(NFR-03) |
| P9 | 검사 범위 | 위치 회수는 개발 24건만. 테스트 16건은 파싱 성공·위치 유효만 확인 | W6 전까지 테스트 분할 위치 정확도를 재지 않는 것이 맞는가 |

## 5. 전제·가정

- 파서는 원문을 정규화하지 않는다(공백 정리·단위 변환·별칭 치환은 W3).
- 블록은 위치를 반드시 가진다(W1 `Location` 규칙: 페이지·셀·문단·표·줄 중 하나 필수).
- 파싱 실패는 프로세스를 멈추지 않고 문서 단위 실패로 기록하며, 분할 실행은 실패가 있으면 종료 코드 1로 끝난다.
- 스캔 PDF OCR·도면·수정 추적 문서는 범위 밖이다(계획서 1-4, P6).
- handwritten 6건(Markdown 입력) 파서는 W6 직전에 추가한다(D-024).

## 6. W2 범위에서 하지 않은 것

- CP-S1에서 W3~W4로 넘긴 항목(혼합 문맥 분류 테스트, 조건 단위 정책, 구조화 출력 통합 검사, HW-SEP 점도 이전, 근거 종류별 지표).
- 공유 모듈 이식(D-020 보류).
- 블록 정밀도(과대 묶음·유령 블록) 지표(P2).
