# 🔶 CP-S3 교차 검토 패키지 — W3 매핑·추출·정규화·첫 비교표

2026-10-12 · 작성: 헬퍼 모델 · 상태: **검토 대기**. 헬퍼는 통과 판정을 하지 않는다(H2-4). 결과는 [decisions.md](../decisions.md)에 `CP-S3`로 기록한다.

## 1. 배경 (5줄)

1. spec-bridge는 선박 기자재 제품 문서에서 클래스를 고르고 속성을 원문 위치와 함께 추출·정규화하는 로컬 우선 도구다. W1(온톨로지·등록)과 W2(파서)는 CP-S1·CP-S2 보완을 마쳤다.
2. W3에서는 분류기, LLM 추출기(구성 A·B·C), 결정론 정규화기, 규칙 기준선 R, 평가기, 실험 실행기를 만들었다. 개발 분할 24건에서 첫 비교를 두 번(1차, 조정 1회 후 2차) 실행했다.
3. 로컬 모델은 `exaone3.5:7.8b`(Ollama, MacBook Pro M5 16GB)이고, 모든 호출은 temperature 0·seed 7이다(D-025·D-026).
4. 결과: 어떤 LLM 구성도 1차 목표(사실 F1 ≥ 0.8)에 이르지 못했고, 최고인 C(0.552 / 0.546)는 규칙 기준선 R(0.551)과 같은 수준이다.
5. 이 검토 결과로 W4(검증기·중복·구성 D)의 설계 방향과, 보고서 해석의 표현 수위를 정한다.

## 3. CP-S3 검토 질문 (계획서 H4)

### 질문 1. 정답 매칭 정책(정규화 후 일치, 복수 출현값 처리)이 평가 전에 고정되었는가?

- **고정 시점**: 채점 해석 5항을 D-028에 적고 평가기 테스트로 고정한 뒤(W3-6) 첫 실험을 실행했다(W3-7, D-029). 정책 내용은 다음과 같다.
  - 사실 키 = (속성, 기준, 조건, 범위). 계약 기본값(`pressure: not_applicable`, `weight: unknown`)은 생략과 같다.
  - 한 키의 값 집합 전체가 일치해야 TP다(E5 원자 집합).
  - 수치는 절대 허용차 1e-6, 목록은 순서 무시, 범위·치수는 원자 비교.
  - 같은 값의 반복 출현은 사실 하나다.
  - E2/E3 관찰을 "고친" 사실은 FP다.
- **결과를 본 뒤 바꾼 것 — 확인 요청**: D-031에서 분류 집계를 바꿨다. 1차 결과를 본 뒤의 변경이다. 영향 범위는 A의 분류 top-1(0.958 → 1.000) 하나이고, 사실 채점은 바뀌지 않았다. 변경 이유는 "추출만 실패한 문서의 분류를 unknown으로 세면 분류 점수에 추출 실패가 섞인다"는 것이다. 이 변경이 결과에 맞춘 사후 조정으로 보이는지 판단을 요청한다.
- **결과를 본 뒤 바꾼 시스템 쪽(채점 아님)**: 정규화기 단위 정리, 스키마 문맥 필드 필수화, 응답 원문 보존. 모두 D-031에서 "개발셋 조정 1회"로 범위를 정했고, 2차 결과로 따로 보고했다. 1차 결과는 보존했다.
- **E5 처리**: 개발셋 E5 키 1개(값 2개)에 대해 두 값을 모두 낸 경우만 TP다. 2차까지 어느 LLM 구성도 이 키를 맞히지 못했다(문맥 추출 실패로 키 자체가 달라짐).

### 질문 2. 추출 실패를 분모에서 빼지 않았는가?

- 실행기는 **정답 목록**을 기준으로 문서를 순회한다. 파싱 요약의 `parsed_ids`에 없는 문서는 `not_parsed` 실패, LLM 오류는 문서 실패가 된다. 두 경우 모두 정답 사실은 FN으로 들어간다(`test_rule_run_keeps_unparsed_documents_as_failures`: 12건 미파싱이어도 분모 24건 유지).
- 실제 발생: A의 SYN-037이 Ollama `token repeat limit reached`로 재시도 후에도 실패했다. 실행은 계속됐고 FN으로 집계됐다.
- 문서 안에서 근거가 없는 값은 사실이 되지 않고 거부 목록에 남는다(`unknown_line`·`not_in_line`·`unknown_attribute`). 이 값들의 정답은 FN이 된다. 거부 건수는 보고서 표에 공개했다.
- 분모 공개: 사실 키 214, 출현 241(속성 없는 관찰 1건 제외, 수 공개), E2/E3 관찰 7건은 사실 분모 밖(계약 `invalid_unit_or_shape`).

### 질문 3. 첫 비교 결과의 해석이 과장되지 않았는가?

보고서의 주장과 근거는 다음과 같다. 과장 여부를 판단해 달라.

| 보고서의 주장 | 근거 | 헬퍼가 본 약점 |
|---|---|---|
| LLM 구성이 기준선 R을 넘었다고 말할 수 없다 | C 0.552/0.546 vs R 0.551 | 표본 24건, 사실 키 214개. 구성 간 차이의 신뢰 구간을 계산하지 않았다 |
| 사실 F1의 병목은 비고 문구 → 기준·조건·범위 대응이다 | 비고가 필요 없는 속성은 R·C 0.93~1.00, 필요한 속성은 0~0.15. 2차 응답 원문에서 문맥 키 264/264 출현, 내용 있음 기준 2·조건 45·범위 27 | 속성 종류와 문맥 필요 여부가 겹쳐 있어(치수·중량은 거의 항상 범위가 붙음), 두 요인을 완전히 분리하지 못했다 |
| 열거형 표기 정규화는 결정론 코드(C)가 모델(B)보다 낫다 | application·medium·pump_type·cooling_type: B 0.25~0.53, C 0.87~1.00 | C의 사전은 같은 개발 문서의 정답 관찰로 만들었다. 개발셋에서 C가 유리한 것은 구조상 당연할 수 있다(일반화는 테스트 분할에서만 확인 가능) |
| C 설계가 검증 가능성 면에서 유리하다 | 2차에서 잘못 채운 조건을 C는 미해결 32건으로 남겼고, B는 근거 없는 조건을 사실로 냈다 | 정확도 수치가 아닌 관찰이다. W4 검증기가 B의 조건도 잡을 수 있다면 차이는 줄어든다 |
| A는 자유 키가 속성 ID와 이어지지 않아 거의 채점되지 않는다 | 자유 키 183건 casefold 불일치 | D-025 결정 3(동의어 매핑 금지)에 따른 결과다. "LLM 단독이 못한다"가 아니라 "자유 형식은 시스템 어휘와 연결되지 않는다"로만 읽어야 한다 |
| 분류는 이 데이터로 LLM 기여를 측정할 수 없다 | 키워드만으로 24/24(문서 머리 제품 줄) | — |

## 4. 헬퍼가 확신이 낮은 지점

| # | 지점 | 현재 처리 | 확인 요청 |
|---|---|---|---|
| L1 | 개발셋 R의 낙관성 | R 출현 회수 241/241은 같은 문서의 정답 라벨 사전 때문(D-029). 일반화 기준은 D-018 테스트 91.6% | R을 비교 기준으로 쓰는 것이 공정한가, 테스트 분할 R 수치가 나올 때까지 "R 대비" 표현을 피해야 하는가 |
| L2 | 결정론 채점의 문맥 기본값 | `pressure: not_applicable`·`weight: unknown`만 생략과 같게 본다 | 범위 기본값 `main_equipment` 외에 다른 기본값이 필요한가 |
| L3 | E2/E3를 "고친" 사실을 FP로 셈 | 계약 E2/E3 "no invented corrected fact"를 근거로 함 | B처럼 모델이 정규화하는 구성에 불리하다. 의도된 불리함으로 봐도 되는가 |
| L4 | 출현 회수 판정 | 같은 속성 + 같은 위치 + 예측 원문이 정답 원문을 토큰으로 포함 | 예측 원문이 비고까지 포함해도 회수로 인정된다(관대). 정밀도 지표가 필요한가 |
| L5 | 모델 출력의 변동 | 프롬프트가 같아도 스키마만 바뀌면 출력 형태가 바뀌었다(B 2차 값+단위 결합, 근거 거부 41건) | 같은 설정의 반복 실행 분산을 재지 않았다. W4 전에 반복 측정이 필요한가 |
| L6 | 개발셋 조정 범위 | 1회로 제한하고 1차를 보존 | 어휘 설명 프롬프트를 W4에서 추가하는 것이 테스트 분할 해석을 오염시키지 않으려면 어떤 기록이 필요한가 |
| L7 | NFR-01 표현 | 프로세스 내부는 전수, OS 관측은 0.5초 표본, 차단 상태 실행 통과 | 차단 직후 `curl` 출력이 첨부되지 않았다(D-033). 재확인이 필요한가 |

## 5. 전제·가정

- 테스트 분할 16건은 W3에서 실행하지 않았다(D-020). 프롬프트·사전·규칙은 개발 결과로만 정했고, 해시로 고정했다(D-029, 2차는 D-032).
- **알려진 테스트 정답 노출**: D-023(분할 분포 확인), D-024(문자 집합 1회 접근), D-028(W3-6 설계 중 SYN-009 정답 앞 80줄 출력, 관찰 4개, 사용하지 않고 폐기).
- 모델 입력은 파싱 블록과 클래스·속성 정의뿐이다. 정규화기는 같은 분할의 등록 목록만 쓴다(CP-S2 W3 입력 계약).
- 분류는 A·B·C가 같은 단계(키워드 후보 + LLM 선택)를 공유한다(D-031, 계획 대비 변경 승인).

## 6. W3 범위에서 하지 않은 것

- 구성 D(검증 피드백), 검증기(E1~E5), 중복 판정 — W4.
- 비고 문구를 기준·조건·범위 어휘로 옮기는 개선(어휘 설명 프롬프트 또는 규칙) — 새 설계 결정으로 W4에서 다룸(D-032).
- 반복 실행 분산, 구성 간 차이의 통계 검정.
- 클라우드 모델 비교 행(선택 사항, 미실행).
- handwritten 6건 파서(W6 직전, D-024).
