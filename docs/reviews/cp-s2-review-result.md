## 발견 사항

### R1 · P2 · PDF 파일 읽기 실패가 문서 단위 오류로 변환되지 않음

위치: `spec_bridge/parse/dispatch.py:33–41` (실제 읽기: 23행).

`detect_format()`과 지연 import가 `try` 바깥에 있고, 해시 계산/버전 조회도 예외 변환 범위 밖이다. 없는 PDF를 전달하면 `ParseError`가 아닌 `FileNotFoundError`가 발생한다. `run_split()`은 `ParseError`만 처리하므로 전체 실행이 중단되고 요약도 생성되지 않는다.

재현: 임시 경로 `missing.pdf`에 `parse_document()`를 호출하면 `FileNotFoundError`. `split_inputs()`만 그 경로를 반환하도록 대체한 `run_split()`도 같은 예외로 끝났고 `_summary.json`이 없었다. XLSX의 손상 ZIP 테스트만으로는 이 경로가 검증되지 않는다.

권고: 문서 읽기·형식 확인·파서 로딩·파싱·해시 산출 중 예상 가능한 실패를 문서 ID/원인과 함께 `ParseError`로 통일한다. 실패 PDF 다음에 정상 문서가 있는 배치에서 후속 문서 처리와 실패 요약을 검사한다.

### R2 · P2 · 재파싱 실패 후 이전 성공 JSON이 그대로 남음

위치: `spec_bridge/parse/run.py:33–39`.

실패 시 summary에만 기록하고 기존 `<input_id>.json`을 무효화하지 않는다. 같은 출력 디렉터리에서 재실행하면 최신 실패 기록과 이전 성공 데이터가 공존한다. W3가 이 디렉터리의 JSON을 입력으로 읽을 때 이전 결과를 최신 결과로 소비할 수 있다.

재현: 임시 XLSX를 `CACHE`로 한 번 정상 파싱한 뒤 같은 파일을 손상시키고 동일 출력 경로로 재실행했다. 두 번째 결과는 실패 1건인데 `CACHE.json`은 여전히 존재했다. 최초 실행만 확인하는 현재 corpus 테스트는 이 문제를 잡지 못한다.

권고: 실패 문서의 과거 성공 산출물을 제거/격리하거나, 실행별 디렉터리와 성공 목록을 두어 현재 실행 결과만 소비하도록 한다. 성공→실패→성공 순서의 회귀 검사를 추가한다.

### R3 · P2 · Docling의 부분 성공을 완전한 파싱 성공으로 처리함

위치: `spec_bridge/parse/pdf_parser.py:44`.

`convert(path).document`만 취하면서 `ConversionResult.status`와 `errors`를 버린다. 설치된 Docling 2.137.0의 `document_converter.py`는 `raises_on_error=True`여도 `PARTIAL_SUCCESS`를 반환하며, `standard_pdf_pipeline.py`는 일부 페이지 실패/시간 초과 때 이 상태를 만든다. 따라서 블록이 하나라도 남으면 누락된 페이지를 알리지 않고 정상 `ParsedDocument`가 된다.

재현 범위: 개발 PDF SYN-003의 실제 변환 결과를 얻은 뒤 상태만 `PARTIAL_SUCCESS`로 바꾸어 converter 반환값에 주입했다. 파서는 오류 없이 30블록을 반환했고 출력 필드에 부분 실패 정보가 없었다. 실제 합성 PDF에서 페이지 실패가 발생했다는 뜻은 아니며, 라이브러리가 제공하는 실패 상태를 무시하는 경로를 재현한 것이다.

권고: 현재 성공/실패 이분 계약에서는 부분 성공을 원인과 함께 `ParseError`로 처리한다. 부분 결과를 활용하려면 먼저 공통 모델과 W3 소비자에 불완전 상태/실패 페이지를 명시한다. 누락된 값을 문서 원래의 E1로 오판하지 않도록 해야 한다.

### R4 · P2 · 캐시 없는 Excel 수식 셀을 빈 칸처럼 삭제함

위치: `spec_bridge/parse/xlsx_parser.py:17–23`.

`data_only=True`는 수식 자체 대신 저장된 계산 결과를 읽는다. 계산 캐시가 없는 수식은 `None`으로 보이고 `_text()`에서 빈 셀로 제거된다. 다른 텍스트가 있으면 문서 전체는 성공한다.

재현: 새 workbook에서 A1=`Value`, B1=`=1+1`을 저장했다. 결과에는 A1만 있었으며 B1의 수식 존재·위치·미계산 상태가 전혀 남지 않았다. W3는 이를 실제 미기재와 구별할 수 없다.

권고: 수식과 캐시 여부를 함께 읽어 미해결 관찰로 보존하거나, 수식 셀을 지원하지 않는다면 명시적 `ParseError`로 거부한다. 파서에서 수식을 임의 계산할 필요는 없다. 현재 합성 입력이 전부 텍스트 셀이라는 것은 기존 검사 통과 이유이지 일반 XLSX의 무손실 처리 보장은 아니다.

### R5 · P2 · Excel 숫자의 표시 의미를 잃어 W3에서 복원할 수 없음

위치: `spec_bridge/parse/xlsx_parser.py:44–50`.

`str(cell.value)`만 `Block.text`에 넣고 `number_format`과 셀 자료형을 버린다. 소수점 자리수 차이뿐 아니라 백분율·단위가 붙은 서식·선행 0 식별자의 표시 의미도 사라진다.

재현: B1에 숫자 `0.125`, 표시 형식 `0.0%`를 저장하면 블록 텍스트는 `0.125`이고 서식 정보가 없다. 사용자 표시인 `12.5%`를 이 블록만으로 복원할 수 없다. 패키지 P7의 “W3에서 처리”는 현재 출력 계약으로 충분하지 않다.

권고: 원시 값/셀 자료형/표시 형식을 보존하고 표시 텍스트와 구별하거나, 지원 가능한 표시 형식을 파서에서 처리하고 나머지는 명시적으로 거부한다. 최소한 W2→W3 경계에서 원본 표시를 재구성할 정보가 남아야 한다.

### R6 · P2 · DOCX 중첩 표의 텍스트가 누락돼도 성공함

위치: `spec_bridge/parse/docx_parser.py:49–57`.

최상위 표의 `cell.text`만 읽는데, 설치된 python-docx의 이 속성은 해당 셀의 직접 문단만 이어 붙인다. 셀 안의 중첩 표는 포함되지 않는다. 문서에 다른 텍스트가 있으면 누락을 알리지 않고 성공한다.

재현: 본문에 `Specification` 문단, 1×1 외부 표, 그 셀 안에 `NESTED VALUE`를 담은 1×1 중첩 표를 저장했다. 파싱 결과는 본문 문단 하나뿐이었다. 현재 명시된 범위 제외에는 중첩 표가 없다.

권고: 중첩 표를 안정적인 위치 경로로 지원하거나, 현재 Location으로 표현할 수 없다면 발견 시 `ParseError`로 거부한다. 지원하지 않는 구조를 조용히 누락시키지 않는다는 수정 추적 정책과 같은 원칙을 적용한다.

## 추가 확인 사항과 한계

- DOCX 가로 병합 셀 하나를 만들면 `row.cells`가 같은 셀을 반복하므로 동일 텍스트의 블록이 서로 다른 column으로 두 번 생성된다. 이번 임시 2열 표에서 `MERGED`가 (row=2, column=1), (row=2, column=2)로 출력됐다. 병합 범위의 표현인지 독립 출현인지 계약이 없으므로 P2의 블록 정밀도 보완 시 원본 셀 하나/범위 하나로 표현하도록 정해야 한다. 현재 합성 관찰이 중복됐다고 단정하지 않는다.
- PDF 원점 테스트는 첫 개발 PDF의 제목 상대 높이와 표 y축 범위만 본다. 정확한 좌표 변환, 다른 페이지 크기, x축, 가장자리 문자 보존을 직접 검증하는 테스트는 추가할 가치가 있다.
- `HF_HUB_OFFLINE`은 `setdefault`이므로 이미 `0`이면 강제되지 않는다. 로컬 artifacts 경로를 지정한 현재 정상 실행에서 실제 네트워크 호출이 있었다는 증거는 없다. NFR-01의 “외부 호출 0회”는 모델 존재 여부 및 환경값을 달리한 네트워크 차단/관측 테스트로 입증해야 한다. 이번 테스트 통과를 네트워크 호출 계측 결과로 해석하지 않는다.
- W2 계획 Task 2의 예시 코드는 설명을 고친 뒤에도 이전 방향의 bbox 중심 판정이 남아 있다. 실행 도우미는 패키지에 기재한 새 방향을 사용한다. 참고 코드의 조건식도 맞추는 것이 좋다.

| P2 회수율 | 242/242는 정의된 관찰의 위치+부분 문자열 회수율이다. 전체 원문 보존율·블록 정밀도·출현 정확도가 100%라는 뜻은 아니다. 합쳐진 블록 안에서 raw_text의 위치를 어떻게 다시 추적할지 W3 계약이 필요하다. 병합 셀 중복, 누락 구조, 반복 숫자와 과대 bbox 사례를 추가한다. |
| P3 글자층 재읽기 | 개발셋에서 해당 대시가 보존되는 것은 확인됐다. 모든 PDF 글자가 보존된다는 보장은 없다. bbox 경계·여러 줄·회전/페이지 크기·특수문자에 대한 별도 회귀 자료가 필요하다. Docling이 블록을 놓치면 좌표 재읽기로 복구되지 않는다는 한계도 기록한다. |
| P4 원점 변환 | 라이브러리의 origin 변환을 사용하는 방향은 타당하다. TOPLEFT/BOTTOMLEFT의 알려진 좌표를 같은 결과로 변환하는 직접 테스트와 실제 문서 위치 검사를 함께 유지한다. 현재 제목 높이/페이지 안쪽 검사만으로 충분하지 않다. |
| P5 제목·절 | 합성 렌더러 스타일에 맞춘 휴리스틱으로 범위를 명시하는 것이 적절하다. section은 보조 문맥으로 사용하고 위치/원문을 우선한다. 절 판정이 틀렸다고 원문을 제외하거나 필수값을 만들지 않는다. |
| P6 수정 추적 | 미지원 문서를 명시적으로 거부하는 정책은 W2 범위에서 타당하다. 수락본을 임의로 선택할 필요는 없다. 현재 검사는 body의 w:ins/w:del에 한정되므로 모든 종류의 수정 추적 검출을 보장한다고 확대하지 않는다. |
| P7 XLSX 숫자 | W3에 미루려면 표시 형식과 자료형을 함께 넘겨야 한다. 현재는 해당 정보가 소실되므로 R5 조치가 필요하다. 수식의 미계산 상태는 R4처럼 별도로 처리한다. |
| P8 버전·모델 | 재현성을 위해 코드 커밋, uv.lock 식별자, 모델 파일 해시/리비전, 주요 파이프라인 옵션을 실행 메타데이터에 남기는 것을 권고한다. PDF는 Docling만이 아니라 pypdfium2/docling-core 등도 출력에 관여한다. 모델 해시를 블록마다 넣을 필요는 없고 실행별 manifest로 충분하다. |
| P9 테스트 위치 평가 | 최종 평가까지 테스트 정답을 튜닝에 사용하지 않는 방향이 맞다. W6에서는 위치 정확도도 보고하고, 그 결과로 수정하면 수정 전 결과를 보존하고 후속 결과가 동일 테스트셋에 적응한 결과임을 구별한다. 현재 테스트 16건의 파싱 성공을 위치 정확도 검증으로 표기하지 않는다. |

## 후속 조치

R1~R3은 배치 실행과 실패 보고 계약을 보완한다. R4~R6은 입력을 지원해 원문 정보를 보존하거나 명시적으로 거부하도록 정한다. 병합 셀·좌표·과대 블록의 회귀 자료와 실행 재현 메타데이터를 보완하고, W3 소비자가 성공/실패 및 현재 실행 결과를 구별하도록 한다.

이번 리뷰에서는 실행 코드, 동결 데이터셋, DB, 사용자 서명을 변경하지 않았다. 실제 제품 수치나 도메인 규칙을 새로 제안하지 않았다.
