# G5 후속 실험 교차 검토 결과

2026-10-19 · 검토자 Codex · 기준 커밋 `1aebc56` · 대상: `g5-review-package.md`의 질문 1–8.

사용자 판정 **“(c) 미달 확인”을 뒷받침하는 수치가 재현된다.** 다만 LLM 기여에 대한 해석과 동결 보장의 범위는 보완해야 한다. 아래는 리뷰 의견이며 새 사용자 판정이나 검토 통과 선언이 아니다. 동결 코드·데이터·기준과 기존 보고서는 수정하지 않았다.

## 지적 사항

### F1 · P2 · 현재 자료만으로 LLM의 제조사 해석 기여를 분리할 수 없다

근거: `docs/reports/g5-followup-bom.md:58`–60, `spec_bridge/bom/g5/resolve.py:181`의 `verify`, `spec_bridge/bom/g5/rows.py`의 제품 행·음성 행 생성.

보고서는 C·E의 R 대비 향상을 제조사 표기를 읽는 LLM의 능력으로 해석한다. 그러나 같은 BM25 후보 10개에서 `verify`가 허용하는 후보를 모두 구해 **하나면 그 제품, 없으면 없음**으로 답하는 사후 진단은 개발 120/120, 테스트 80/80이다. 제품 행은 모두 허용 후보가 정확히 1개(90/60행), 음성 행은 모두 0개(30/20행)다. 이 계산은 제조사 해석·LLM·사례 검색 없이 가능하다. 제조사를 다르게 쓴 행에서도 현재 데이터는 모델 코드·클래스로 정답이 결정된다.

따라서 “C·E가 사전 지정 R보다 높았다”는 비교는 맞지만, 이 결과로 LLM의 의미 매핑 기여가 입증되었다고 할 수 없다. R의 보수적 제조사·동등품 정책과 C·E의 수락 정책 차이가 함께 비교되었다. 보고서에 이 한계를 추가하고 위 문구를 관측된 구성 간 차이로 한정할 것을 권고한다. 이 진단은 **테스트 공개 후 사후 분석**이며 사전 등록 기준선 교체·추가 실험 판정이 아니다. 제조사를 무시하는 규칙의 제품 적용도 권고하지 않는다.

### F2 · P2 · 동결 검사가 모델·추론 환경 변경을 차단하지 않는다

근거: `spec_bridge/bom/g5/run.py:115`–121, 204–220 및 `spec_bridge/llm/provider.py:17`, 62, 100.

`verify_freeze()`는 파일 해시만 검사한다. `run()`은 동결된 모델 digest와 실제 provider digest를 비교하지 않고 실행 후 metadata에 적는다. `answers`를 빈 결과로 대체한 무호출 재현에서 다른 digest를 가진 provider로 `run('test', 'C', ...)`가 허용됐다. 실제 모델 호출이나 새 테스트 예측은 수행하지 않았다.

또한 동결 목록에는 추론 옵션을 정하는 provider 코드·설정 및 의존성 잠금 파일이 없고, 임베딩은 이름만 있으며 digest는 없다. 따라서 추론 옵션이나 동일 태그 모델이 바뀌어도 파일 검사만으로는 탐지되지 않는다. **이번 C·E 묶음의 생성 모델 digest는 모두 동결과 같으므로 이번 점수가 무효라는 뜻은 아니다.** 향후 실행에는 생성·임베딩 모델 식별자와 추론 옵션을 기록·검사하도록 별도 변경을 권고한다. 동결된 이번 코드는 그대로 두고 새 실험 버전에서 반영해야 한다.

### F3 · P2 · 사전 등록·실행 순서의 입증 범위를 좁혀야 한다

근거: `docs/reviews/g5-review-package.md:9`, `docs/reports/g5-followup-bom.md:20`, `spec_bridge/bom/g5/run.py:209`–217, 커밋 `56adddf`.

D-109와 생성기·테스트 JSON은 모두 `56adddf`(2026-10-17 21:20:20 +09:00)에 최초로 기록된다. 저장소 기록에는 등록 시각과 데이터 생성 시각을 분리한 자료가 없다. D-109에 적힌 “생성 전 등록”은 결정 기록의 진술이며, 파일 해시는 내용 동일성만 확인하므로 그 선후를 독립적으로 입증하지 못한다.

또한 `run.json.at`은 `answers()`가 끝난 뒤 생성한 **종료 시각**이다. 종료 시각이 동결보다 늦다는 사실만으로 실행 시작도 동결 뒤였다고 단정할 수 없다. 이번에는 별도 로컬 audit의 프롬프트 해시를 재구성해 C·E 호출이 동결 뒤였음을 보강했다(아래 질문 1). 재배포 묶음만으로 확인 가능한 내용과 로컬 보강 증거를 구분하고, 향후에는 시작·종료 시각 및 사전 등록 이력을 별도로 보존할 것을 권고한다. 순서 위반을 발견했다는 뜻은 아니다.

## 질문별 답변

### 1. 사전 등록 순서

- D-109와 테스트 행 생성의 선후는 **독립 확인 불가**(F3). 기준은 D-109에 기록되어 있고 이후 판정 공식 변경은 확인되지 않았다.

### 2. D-110 개발 단계 변경

사례의 정답이 현재 후보에 들어간 개발 조건을 제거한 것은 테스트의 제품 분리 조건과 맞추는 조치다. `run.py:157`은 테스트 정답을 제외 조건에 사용하지 않고, 개발에서만 자기 정답을 추가로 제외한다. 저장된 개발·테스트 E 사례를 후보 목록과 대조한 중복은 0건이다.

코드 검증 추가는 개발 오류를 보고 성능을 개선한 **알고리즘 변경**이다. 단순한 환경 정렬로 표현하면 안 된다. 다만 C·E 공통으로 적용됐고 D-110 승인·커밋이 테스트 호출 전에 존재하며, (a)·(b)·(c) 기준은 유지됐다. 테스트 결과를 보고 조정했다는 증거는 없다. 개발에서 C의 천장을 이미 알았다는 점도 기록되어 있다. 최종 결과의 대상은 순수 LLM이 아니라 LLM+검증 파이프라인이다.

### 3. 정답 규칙과 R의 공정성

### 4. 누출

## 사후 진단 재현 방법

아래는 후보와 검증 함수만을 이용하는 F1 진단이다. 저장된 입력을 읽고 임시 SQLite를 사용한다. `case.gold`는 답을 만든 뒤 정확도 집계에만 사용한다. 원래 R을 대체하지 않는다.

```python
from pathlib import Path
from tempfile import TemporaryDirectory
from spec_bridge.bom.g5 import run as g
from spec_bridge.bom.g5.rows import load
from spec_bridge.bom.g5.resolve import Candidates, verify
from spec_bridge.ontology.loader import load_ontology

onto = load_ontology(Path('ontology/ontology.yaml'))
for split in ('dev', 'test'):
    with TemporaryDirectory() as folder:
        store = g.store_for(split, onto, Path(folder))
        try:
            pool = Candidates(store.identities(), g.aliases())
            right = 0
            for case in load(split):
                eligible = [p['product_id'] for p in pool.top(case.line)
                            if verify(onto, case, p) is None]
                answer = eligible[0] if len(eligible) == 1 else None
                right += answer == case.gold
            print(split, right, len(load(split)))
        finally:
            store.close()
```
