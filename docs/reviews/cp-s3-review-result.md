## 발견 사항

### R1 · P2 · macro F1(속성)의 분모가 구성마다 다르다

위치: `spec_bridge/eval/scoring.py:198–213`.

`by_attribute`는 정답 또는 예측에 나온 속성을 모두 모은다. 그래서 정답에 없는 속성(`reported_weight`, `discharge_pressure`, `working_pressure`)을 낸 구성은 F1 0인 항목이 평균에 더해진다. 구성마다 평균을 내는 속성 집합이 다르다.

| 실행 | 평균 대상 속성 수 | 보고된 macro F1(속성) | 정답 속성 24개 기준 |
|---|---|---|---|
| R | 24 | 0.542 | 0.542 |
| C 1차 | 25 | 0.515 | **0.536** |
| C 2차 | 26 | 0.494 | **0.535** |
| B 1차 | 27 | 0.335 | **0.376** |
| B 2차 | 26 | 0.327 | **0.354** |

보고서 표에서 C의 macro F1이 R보다 0.027 낮아 보이지만, 같은 속성 집합으로 맞추면 0.006 차이다. 정답에 없는 속성의 FP는 micro P에 이미 반영되고, 보고서 속성별 표에도 따로 나온다.

권고: macro F1(속성)은 정답 속성 집합으로 평균한다. 정답에 없는 속성의 FP는 별도 열로 공개한다. 보고서 1·2차 표의 해당 열은 수정 전 값을 남긴 채 정정한다. 채점기 테스트에 "정답에 없는 속성 예측이 macro 분모를 바꾸지 않는다"를 추가한다. macro F1(클래스)은 정답 클래스 기준이라 영향이 없다.

### R2 · P2 · R·C의 동률은 "문맥을 무시하는 시스템의 천장"이다 — 보고서가 이 구조를 밝히지 않는다

위치: 보고서 §2 결과 아래 문단, §3 확인됨 1·2.

개발 정답의 사실 키 214개 중 **97개는 기준·조건·기본값이 아닌 범위 중 하나 이상이 명시돼 있고, 117개는 문맥이 없다.** R의 TP는 정확히 117/117(문맥 없는 키)과 0/97(문맥 키)이다. 따라서 문맥을 내지 않는 시스템의 사실 재현율은 이 개발셋에서 0.547이 상한이다. R은 이 상한에 도달했고, C 1차(115/117, 0/97)는 거의 도달했다. "C ≈ R"은 두 구성의 추출 능력이 같다는 뜻이 아니다. 둘 다 같은 천장에 닿았다는 뜻이다.

또한 **교란이 완전하다.** 문맥이 붙는 속성 11개(`dimensions`, `dry_weight`, `motor_power`, `rated_power`, `rated_speed`, `capacity`, `rated_throughput`, `max_pressure`, `differential_pressure`, `head`, `applicable_engine_power`)는 개발셋에서 **항상** 문맥 키를 갖는다. 나머지 13개는 한 번도 갖지 않는다. 패키지가 걱정한 "속성 종류와 문맥 필요 여부가 겹친다"는 부분적인 겹침이 아니라 완전한 일치다. 속성별 F1 비교로는 두 요인을 원리적으로 분리할 수 없다.

대신 메커니즘을 직접 보여 주는 증거가 있다. 문맥 속성의 정답 사실 98개(키 97, E5 1키 2값) 중 **R은 98개 모두** 같은 속성 아래 값·단위를 맞혔다. 키만 틀렸다는 뜻이다. C 1차는 81/98, C 2차는 68/98이다.

권고: 보고서 §3에 "문맥 없는 키 117 / 문맥 키 97" 분할 표와 구성별 TP를 넣는다. 병목 주장의 근거를 속성 비교에서 "값 일치·키 불일치" 수치로 바꾼다. W4 목표(F1 ≥ 0.8)에 필요한 문맥 키 TP는 다음과 같다. 문맥 없는 키 117개를 모두 맞힌다고 가정한다.

- FP가 0이면 재현율 ≥ 0.667, 곧 TP ≥ 143이 필요하다. 문맥 키는 **최소 26개**다(낙관적 하한).
- 정밀도와 재현율이 같으면(FP = FN) TP ≥ 172가 필요하다. 문맥 키는 **55개**다.

현재 최고값은 12개(B 1차)다. 이 산술을 W4 계획에 명시하면 목표의 현실성을 미리 판단할 수 있다.

### R3 · P2 · 2차 변경 ③(문맥 필드 필수화)의 부작용이 순 F1에 가려진다

위치: 보고서 §6 "사실 F1은 C·B 모두 1차와 같은 수준", §6 해석 첫 항목.

| 실행 | TP 문맥 없는 키 (/117) | TP 문맥 키 (/97) | 문맥이 붙은 FP 키 | 문맥 속성 값 일치 (/98) |
|---|---|---|---|---|
| C 1차 | 115 | 0 | 0 | 81 |
| C 2차 | **108** | 5 | 16 | **68** |
| B 1차 | 73 | **12** | 93 | — |
| B 2차 | 79 | **3** | 44 | — |

C의 F1은 0.552 → 0.546으로 "같은 수준"이다. 그러나 안을 보면 문맥 키 +5와 문맥 없는 키 −7이 상쇄된 결과다. 문맥 속성의 값 일치도 81 → 68로 떨어졌다. 필수 필드가 문맥이 없는 값에도 문맥을 채우게 만들었을 가능성이 있다(가설, 응답 원문으로 확인 가능). B는 필수화 뒤 문맥 키 TP가 12 → 3으로 줄었다. 1차 B의 12개는 이번 W3에서 모델이 비고를 어휘로 옮긴 유일한 실질 증거인데, 보고서가 다루지 않는다.

권고: §6에 위 분할을 넣고 "필수화는 순효과 0이 아니라 상쇄"로 기록한다. W4에서 문맥을 묻는 방식을 설계할 때(어휘 설명 프롬프트, 구성 D) 이 부작용을 대조 항목으로 둔다. 예를 들면 "문맥 없음"을 명시적 선택지로 두는 방안과 필수화를 비교한다. 보고서 §6의 "7.8B 모델이 … 어렵다" 문장은 질문 3 표대로 고친다.

### R4 · P2 · 실행 기록에 채점기·정답 버전이 없다

위치: `spec_bridge/eval/experiment.py:155–159`.

`run.json`의 해시는 온톨로지, 개발 사전, 프롬프트 모듈 5개만 다룬다. `scoring.py`·`locations.py`와 정답 집합(또는 `SHA256SUMS`)은 기록하지 않는다. 실행 시점 코드는 `75048dd` + `git_dirty: true`라서 git으로도 복원할 수 없다. 그 결과 다음 두 가지가 산출물로 입증되지 않는다.

- 질문 1의 "채점 정책이 실행 전에 고정됐다"는 decisions.md의 서술과 테스트로만 뒷받침된다.
- D-031 이후 A 1차의 `metrics.json`(0.958)과 현재 채점기의 출력(1.000)이 다른데, 어느 쪽이 어느 채점기 버전인지 기록이 없다. D-031의 "C 1차 + ①만 재채점(0.535)" 결과는 파일로 남지 않았다.

권고: `run.json` 해시에 평가 모듈(`scoring`, `locations`)과 정답 매니페스트·`SHA256SUMS` 해시를 추가한다. 재채점은 원 `metrics.json`을 덮지 않고 `rescored-<채점기 해시>.json`처럼 따로 쓴다. 테스트 분할 실행(W6) 전에 채점기 해시를 decisions.md에 고정한다.

### R5 · P2 · NFR-01 "프로세스 내부 전수"는 범위를 넘는 표현이다

위치: `tests/test_network.py:27–41`, D-033, 패키지 §2 NFR-01 행.

가드는 `socket.socket.connect`와 `socket.getaddrinfo`만 가로챈다. 다음 경로는 잡지 못한다.

- `socket.connect_ex`
- 연결 없는 UDP의 `sendto`·`sendmsg`
- Python `socket` 모듈을 거치지 않는 확장 모듈(C/Rust)의 네트워크 호출
- 자식 프로세스

현재 스택이 이 경로를 쓴다는 증거는 없다. 그래도 "전수"는 "Python 소켓 API 중 connect·이름 조회 경로에서 전수"로 한정해야 한다.

L7(차단 직후 `curl` 출력 미첨부)에 대한 답: **재확인이 필요하다.** 첫 차단 시도가 조용히 실패한 이력이 있으므로, 두 번째 시도가 실제로 차단 상태였다는 증거가 없으면 "차단 상태 실행 통과"는 주장할 수 없다. 같은 로그 안에 `route -n get default`(실패)와 `curl -m 5 https://example.com`(실패)을 테스트 실행 직전·직후로 남기고 다시 실행한다. 비용은 몇 분이다. 차단 실행은 "외부 의존 없이 동작"을 보이고, 가드·lsof는 "시도 0회"를 보인다. 두 주장을 섞지 않는 현재 D-033 구조는 유지한다.

권고: 가드에 `connect_ex`와 `sendto`를 추가한다(두 줄). D-033과 패키지의 "전수"를 위 한정 표현으로 고친다. 차단 실행을 증거 로그와 함께 다시 한다.

### R6 · P3 · "top-3"이 최대 4개 클래스를 본다

위치: `spec_bridge/eval/scoring.py:171–172`, `extract/classifier.py:86`.

`top3_hit`는 `[class_id, *class_candidates[:3]]`로 판정한다. 키워드 후보가 없어서 LLM이 6개 클래스 전체에서 고르면, 선택 클래스와 키워드 상위 3개가 겹치지 않아 정답 후보가 4개가 될 수 있다. D-028 5항의 문구("선택 클래스 또는 후보 상위 3")와는 맞지만, 지표 이름과 다르다. 현재는 top-1이 1.0이라 영향이 없다.

권고: W6 전에 "선택 클래스를 1위로 둔 상위 3개"로 정의를 바꾸거나 지표 이름을 바꾼다. 결정은 decisions.md에 남긴다.

### R7 · P3 · 계약의 문맥 기본값이 채점기와 추출기에 나뉘어 있다

위치: `scoring.py:20`(기준 기본값 2개), `extract/extractor.py:67–71`·`extract/rules.py:70`(범위 기본값 `main_equipment`).

계약 `context_defaults`는 정확히 세 개다(`scope main_equipment`, `basis pressure not_applicable`, `basis weight unknown`). 채점기는 기준 두 개만 처리하고, 범위 기본값은 예측을 만드는 쪽이 채워 준다고 가정한다. 범위를 비워 둔 예측(앞으로의 구성 D, 클라우드 비교 행 등)은 채점기에서 다른 키가 된다.

L2에 대한 답: **기본값을 더 늘리지 않는다.** 계약이 세 개를 열거하고 동결돼 있다(D-019). 늘리려면 계약 변경이 필요하며, 개발 결과를 본 뒤의 변경이 된다. 대신 범위 기본값도 채점기의 `fact_key`에서 처리해, 채점이 생산자 구현에 의존하지 않게 한다. 이것은 계약을 코드로 옮기는 정리이고, 현재 수치는 바뀌지 않는다.

## 헬퍼 확신이 낮은 지점(L1~L7)에 대한 답

| # | 답 |
|---|---|
| L1 | R은 비교 기준으로 쓸 수 있다. 다만 개발셋에서 R은 "개발 정답 사전을 가진, 문맥 없는 시스템의 천장"이다(R2). C도 같은 개발 사전으로 정규화하므로 R과 C는 사전 측면에서 대칭이다. A·B는 사전이 없다. "R 대비" 표현은 "개발셋(사전 낙관 조건)"이라는 한정을 붙이면 써도 된다. "LLM이 R보다 낫다/못하다"는 일반화 주장은 테스트 분할(W6) R 수치가 나온 뒤에 한다 |
| L2 | 추가하지 않는다(R7) |
| L3 | 의도된 불리함으로 본다. 계약 E2/E3("no invented corrected fact")가 등록 안전성 요구이기 때문이다. 크기도 작다. B 1차가 E2/E3 위치에서 낸 사실은 7개, B 2차는 2개, C는 0개다(FP 141개 중 최대 7개). 보고서에 이 건수를 공개하면 충분하다 |
| L4 | 관대함은 `same_place`(같은 칸·같은 문단·PDF 영역 중심)로 제한된다. 추출기도 줄 안에서 값 토큰을 가진 블록이 정확히 하나일 때만 위치를 인정하므로, 실질 영향은 작다. W4 구성 D가 출현 수를 바꿀 것이므로, **출현 정밀도**(정답 관찰과 맞지 않는 예측 출현 비율)를 W4 전에 지표로 추가하기를 권한다. 비용은 작다 |
| L5 | 보고서가 "변동"이라고 부른 것은 반복 실행의 무작위 분산이 아니라 **스키마 변경에 대한 민감도**다. 두 개념을 구분해 쓴다. W4에서 D와 C의 차이는 작을 수 있으므로, W4 전에 C를 같은 해시로 1회 재실행해 문서별 출력이 같은지 확인한다(약 15분). 같으면 잡음 하한은 0이고, 다르면 그 차이를 비교의 최소 효과 크기로 둔다 |
| L6 | W4에서 어휘 설명 프롬프트를 추가한다면, 다음 네 가지를 decisions.md에 남겨야 테스트 분할 해석이 오염되지 않는다. ① 어휘 설명의 출처: 온톨로지 정의문에서 썼는지, 개발 문서의 비고 문구를 옮겼는지. ② 프롬프트에 실린 개발 문구 예시 목록. ③ 개발셋 조정 횟수와 각 해시. ④ 테스트 실행 전 동결 해시. 합성 데이터는 문구 생성 규칙을 두 분할이 공유할 수 있다. 그래서 개발 비고 문구를 예시로 넣으면, 테스트 점수는 실제 문서에 대한 일반화보다 낙관적일 수 있다. 이를 확인하려고 테스트 분할의 문구를 들여다보지는 말고(D-023 선례), 출처 ①을 온톨로지 정의문으로 제한하는 편이 안전하다 |
| L7 | 재확인이 필요하다(R5) |
