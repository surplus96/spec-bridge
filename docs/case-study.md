# 케이스 스터디 — 사양서의 "문맥"을 등록 가능한 사실로

spec-bridge를 만들며 내린 설계 판단과, 그 판단을 수치와 화면 확인으로 검증한 과정을 정리한다. 수치는 모두 [W6 최종 평가 보고서](reports/w6-final-evaluation.md)와 [W4-R 보고서](reports/w4r-rag-semantic-mapping.md), 결정 기록에서 가져왔다. 데이터는 합성이다([모델·데이터 카드](model-data-card.md)).

## 1. 문제를 다시 정의하기

처음 목표는 "사양서에서 속성 값을 뽑는다"였다. W3 첫 비교에서 값과 단위는 대부분 맞혔지만, 등록 가능한 사실로는 부족했다. 같은 속성의 값이 여러 개일 때(최대·사용 압력, 50 Hz·60 Hz 정격, 점도별 처리량) 무엇이 무엇인지 구분하는 **기준·조건·범위**를 맞히지 못했다. 규칙 기준선 R, zero-shot LLM C, 클라우드 모델 모두 개발 문맥 키 97개 중 0~12개였다(W4-R 보고서 §1).

그래서 채점 단위를 "값"에서 **"사실 = 속성 + 값 + 기준 + 조건 + 범위"**로 바꿨다. 문맥이 하나라도 다르면 틀린 것으로 센다. 이 엄격한 기준에서 R의 개발 F1은 0.551이다.

## 2. 설계 원칙

| 원칙 | 구현 |
|---|---|
| 역할 분담: LLM은 해석, 코드는 측정·검증, 지식은 데이터 | LLM은 비고를 어휘로 옮긴다. 숫자·단위·근거 구절의 실재는 코드가 확인한다. 해석 사례는 KB(개발 정답 234사례)에 있다 |
| 문서에 없는 것은 만들지 않는다 | 근거 구절이 원문 줄에 없으면 문맥 필드를 버린다. 빠진 값은 채우지 않고 보강 요청서를 만든다(D-066) |
| 사람이 마지막에 결정한다 | 등록 전 검토 중단점. 수정도 같은 정규화기를 거친다. 자동 병합은 없다 |
| 모든 값에 근거 | 등록 사실은 원문 위치(`observed`) 또는 수정 기록(`human_edit`)을 가진다(NFR-07) |
| 평가는 미리 정하고 한 번만 | 판정 기준을 실행 전에 등록하고(D-048, D-080), 시스템을 해시로 동결한 뒤 테스트 분할을 한 번 실행한다 |
| 도메인 사실은 기억으로 쓰지 않는다 | 온톨로지·사전은 `origin: synthetic` 또는 원문 출처를 가진다. 테스트의 도메인 값은 데이터에서 읽는다(H3) |

## 3. 문맥을 맞히기까지 (개발 24건)

| 단계 | 시도 | 결과 | 배운 것 |
|---|---|---|---|
| W3 | zero-shot 추출 C(문맥 선택형·필수형), 클라우드 | 문맥 키 0~5/97 | 값 추출은 쉽고 문맥이 어렵다 |
| W4-1 | 문맥 축을 모두 채우게 함(필수형 확대) | F1 0.163, 문맥 없는 키 26/117(D-040·D-041) | 강제하면 문맥을 지어내고 사실 키가 무너진다 |
| W4-R E0 | 값마다 따로 문맥 질의, 사례 없음 | F1 0.573, 문맥 9/97, 지어낸 문맥 60 | 분해만으로는 부족하다 |
| W4-R E1 | + 해결 사례 3개 검색(BM25 + bge-m3) | F1 0.905, 문맥 83/97, 지어낸 27 | 개발 합성 문서에서 해결 사례를 준 뒤 문맥 키 정답이 크게 늘었다 |
| W4-R E1SV | + Self-RAG 지지 판정 + 속성 충돌 해소 | **F1 0.946, 문맥 85/97, 지어낸 11** | 검증 단계가 지어낸 문맥을 줄인다 |

테스트의 E0 → E1SV 차이(문맥 4 → 62)는 검색, 지지 판정, 충돌 해소를 함께 넣은 묶음 효과다. 테스트에서 검색만의 효과를 따로 재지는 않았다. 결과는 같은 생성 규칙의 합성 문서에 대한 것이고, 수기 사양서(문맥 1/13)는 반대 신호다.

검색 방식도 수치로 골랐다. 생성 없이 검색만 진단했을 때 하이브리드(BM25 + bge-m3)의 hit@3가 이론 상한 0.814에 닿았다. LLM으로 질의를 다시 쓰는 Multi-Query는 hit@3가 0.51~0.53으로 크게 떨어지고 느려서 버렸다(D-047).

## 4. 동결 후 테스트

시스템을 동결하고(D-086) 개발 분할을 다시 돌려 이전 수치와 완전히 같음을 확인했다(D-087). 그다음 테스트 16건과 수기 사양서 6건을 한 번씩 실행했다.

- **테스트**: E1SV F1 0.913, 문맥 62/72, 지어낸 문맥 8이다. 사전 등록 기준 (a)~(c)와 목표권이 모두 성립했다(사용자 판정).
- **수기 사양서**: F1 0.549, 문맥 1/13이다. 원인을 분석하니 파싱 문제는 0건이었다. 놓친 28개 중 15개가 정규화 사전 밖 표기(`395 t`, `30 barg`, `Seawater`, `HFO / MGO`)였다. 나머지는 문서 구절형 범위와 조건 해석 실패, 추출 누락이다. 사전과 KB가 합성 생성기의 표기만 안다는 한계가 드러났다. 이 "파싱 0건"은 오류 분석 도구의 휴리스틱 분류 결과다(보고서 §6).
- **G3 미달(0.875)**: 검증기 자체의 오판이 아니었다. 모델이 문서에 있는 값 6개를 빠뜨렸고, 그 때문에 "필수 누락" 오탐 4건과 허용값 검사 누락 1건이 생겼다. 같은 누락이 G4의 유사 쌍 누락 5개도 모두 설명했다.

## 5. 사람의 자리: 검토 화면이 막아야 하는 것

자동 지표가 오답으로 세는 값이 운영 경로에서는 어디로 가는지 확인했다(D-091).

- 단위를 읽지 못한 값은 경고와 보강 요청서로 담당자에게 간다.
- 그런데 **사전에 없는 표기**는 허용값 목록이 없는 속성이면 조용히 등록될 수 있었다. 그래서 "표준 용어로 바뀌지 않은 값" 알림을 추가했다. 담당자가 용어로 고치거나 "적힌 그대로 확인"을 눌러야 등록된다.
- 적용 결과, 수기 세트의 표기 오답 7개가 모두 담당자에게 갔다. 맞는 값에 대한 알림은 0개였다. 단, 이 기능은 **평가 뒤 같은 오답을 보고 만든 것**이라 이 수치는 사후 확인이지 독립 평가가 아니다. 사전에 용어가 정해진 속성만 다루므로, 앞으로 나올 모든 사전 밖 표기를 잡는다고 보장하지 않는다.
- 문맥 차이는 모델이 제안했다가 검증에서 거부된 문맥이 속성·위치와 맞을 때만 "문맥 확인 필요"로 표시된다. 제안되지 않은 문맥이나 검증을 통과한 잘못된 문맥은 표시되지 않는다. 문맥을 고치는 기능은 보류했다.

## 6. 화면 확인에서 찾은 결함

단위 테스트가 통과한 상태에서 사용자가 실제 화면으로 확인하며 찾은 결함이다(W5 보고서 §4, W6).

| 현상 | 원인 | 조치 |
|---|---|---|
| 클라우드 모델로 작업 실패 | strict가 아닌 응답에서 필드가 문자열로 옴 | 객체가 아닌 필드를 거부(D-067) |
| 수정 전에 멈춘 작업이 예전 안내를 보임 | 그래프 중단 페이로드가 체크포인트에 고정됨 | 조회할 때마다 다시 계산(D-071) |
| 로컬 서버 첫 로드 500 | 서비스 동시 생성으로 임베딩 요청이 겹침 | 한 번만 만들고 성공한 것만 보관(D-075) |
| 등록 버튼을 누른 뒤에야 제조사 거부 | 검토 단계에서 미리 확인하지 않음 | 검토 화면의 차단 사유로 앞당김(D-076) |
| 재업로드가 동일 제품 대신 유사 제품에 연결 | 연결 후보 순서와 화면 기본값 | 동일 제품을 먼저(D-079) |
| 사전 밖 표기가 조용히 등록됨 | 정규화기가 모르는 표기를 그대로 둠 | 표준 용어 확인 알림(D-091) |

이 결함들은 화면이 여러 요청을 동시에 보내거나, 사람이 기본값을 그대로 쓰거나, 다른 모델 응답 형식이 들어올 때만 드러났다.

## 7. 평가를 정직하게 유지한 장치와 실수

- **사전 등록과 동결**: 판정 기준을 실행 전에 기록하고, 채점기·프롬프트·KB·온톨로지를 해시로 고정했다. 해시가 다르면 테스트 실행이 거부된다.
- **채점기 ID 고정 테스트**: 패키지 전체 포맷 한 번에 채점기 해시가 바뀐 일이 있어(D-070) 테스트로 막았다.
- **헬퍼의 실수 공개**: 테스트 실행 스크립트가 비교 행 A·B·C를 W4-1의 문맥 필수형으로 돌렸다. 결과(F1 0.026~0.036)는 실행한 그대로 공개했다. 선택형 C는 "결과를 본 뒤 추가한 참고 행"으로 따로 표시했다(D-089).
- **원문 미커밋 점검**: 공개 준비 중 제조사 참고 PDF가 첫 커밋부터 추적되던 것을 발견했다. 추적을 끊고 자동 검사를 추가했다. 공개는 깨끗한 새 저장소로 한다(D-094).

## 8. 남은 한계

- 합성 데이터의 개발·테스트 분할은 같은 생성 규칙을 공유한다. 테스트 0.913은 "같은 규칙의 새 문서"에 대한 결과다.
- 수기 사양서 6건은 헬퍼가 초안을 썼고 개발 중 열람했다. 그래서 독립 평가가 아니다.
- 모델은 로컬 7.8B 하나다. 클라우드 모델은 테스트 문서를 외부로 보내야 해서 돌리지 않았다.
- 상세는 [보고서 §7](reports/w6-final-evaluation.md)에 있다.
