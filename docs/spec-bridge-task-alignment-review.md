# spec-bridge 과제 정합성 검토

작성일: 2026-10-05 · 대상: [프로젝트 계획서](spec-bridge-project-plan.md)(2026-09-23 확정본), [착수 리서치](spec-bridge-kickoff-research.md), [착수 체크리스트](spec-bridge-kickoff-checklist.md)
기준: **과제 1. Ontology 기반 제조 Product 정보 생성 및 등록 자동화** (사용자 제공 과제 정의서 스크린샷)

작업 ID: **W0-ALIGN** — 현재 설계가 과제의 타겟 포인트를 따르는지 항목별로 대조하고, 차이와 개선안을 정리한다.

이 문서는 **분석과 제안**이다. 계획서의 확정 사항을 바꾸지 않았다. 개선안 채택 여부는 사용자가 결정하고, 채택 시 `docs/decisions.md`에 기록한 뒤 계획서를 개정한다(H1-6).

## 1. 결론

**현재 계획은 과제의 "검증" 기능에는 강하지만, 과제의 핵심인 "문서 → 온톨로지 기반 추출·정규화 → 등록 데이터 생성"이라는 주 흐름을 중심에 두고 있지 않다.**

| 구분 | 판단 |
|---|---|
| 정합도(대략) | 과제 항목 14개 중 충족 3 · 부분 충족 8 · 미충족 3 → **약 50%** (충족 1, 부분 0.5, 미충족 0으로 단순 합산한 참고 지표) |
| 가장 큰 차이 | ① 흐름의 방향이 반대다(과제: 문서 → 데이터 / 계획: 데이터 → 문서 생성 + 규제 검증) ② **온톨로지(분류 체계·관계)가 없다** ③ **기존 등록 제품과의 중복·유사 검사가 없다** |
| 과제 밖에 투입되는 노력 | 규제 조항 레지스트리 30개·Citation Guard(G2), POS 초안 생성·DOCX(S1), 변경 영향 분석(G3) — 필수 FR 13개 중 약 6개가 과제 요구와 직접 연결되지 않는다 |
| 일정 위험 | CP-S1(규제 조항 30개의 `verified_by` 확인)이 W2 진입 조건이다. 과제 핵심 작업(스키마·합성 데이터)이 **과제에 없는 규제 작업에 막혀 있다** |
| 살릴 자산 | 스키마 = 진실원천, 결정론 검증, 원문 위치 보존(`ObservedFact`), `unknown` 상태, 합성 데이터 + 정답 라벨, HITL, 감사 로그, 로컬 우선 — 모두 과제에 그대로 재사용 가능 |

**권장:** 도메인(선박 기자재)과 검증 자산은 유지하고, 프로젝트의 중심축을 **"선박 기자재 제품 정보 등록 자동화"** 로 재배치한다. 규제 인용·POS 생성·변경 영향은 확장 과제로 내린다(4장 안 A).

## 2. 항목별 대조

범례: ✅ 충족 · 🟡 부분 충족 · ❌ 미충족

### 2.1 배경·목표

| # | 과제 타겟 | 계획서 대응 | 판정 | 차이 |
|---|---|---|---|---|
| T1 | 문서를 입력하면 **등록용 데이터를 자동 생성** | S2 검증 모드에서 POS → Extractor → 스키마 추출(5-3). 그러나 출력은 결함 리포트이고, 주 시나리오 S1은 반대 방향(스키마 → POS 문서) | 🟡 | 추출 결과를 "등록 레코드"로 확정·저장하는 단계가 없다 |

| T3 | **담당자마다 다른 표기 방식** 정규화 (누락·중복·오류 감소) | pint 단위 처리, R-UNIT(kW/bhp 혼용), 형식명 ↔ 필드 일치 | 🟡 | 단위 외 표기 변형(제조사 별칭, 형식명 표기, 약어, 대소문자·구분자, 날짜·숫자 형식)을 정규화하는 **동의어·통제 어휘**가 없다 |

### 2.2 주요 기능

| # | 과제 타겟 | 계획서 대응 | 판정 | 차이 |
|---|---|---|---|---|
| F1 | 제품 문서(**PDF, Excel** 등) 업로드·파싱 | Docling은 **규칙 PDF** 파싱용(Ingest). POS 입력 형식은 미정의(리서치 10장에서 지적) | 🟡 | Excel(사양 표·BOM) 입력이 없다. 제품 문서 업로드 경로가 정의되지 않았다 |

| F4 | **필수 항목 누락, 단위·형식 오류** 자동 검증 | D4 필수 누락, R-UNIT, pint, R-CONS-SMCR, 결정론 Rule Checker, `unknown` 상태(리서치 6.1) | ✅ | 강점. 다만 "필수"의 기준이 M44 제출도서 등 **규제 체크리스트**에 묶여 있다. 과제의 필수 항목은 **온톨로지가 정한 클래스별 필수 속성**이다 |

### 2.5 난이도 지침

과제는 "온톨로지 설계는 교육 범위 밖이므로 **간이 온톨로지를 사전에 제공**"을 권장한다. 즉 과제의 어려움은 온톨로지에 집중하라는 신호다. 현재 계획은 온톨로지 대신 **해사 규제 해석**(MARPOL VI, IACS M44, 선급 규칙)이라는 더 무겁고 도메인 사실 오류 위험이 큰 영역(H3)을 핵심 난제로 삼고 있다.

## 3. 평가

### 3.1 잘 맞는 부분 (유지)

1. **결정론 검증 원칙**("수치·규칙은 코드가, 문장·해석은 LLM이")은 F4에 정확히 들어맞는다. LLM 추출 결과를 코드로 검증하는 구조가 과제의 "누락·오류 감소" 목표를 직접 뒷받침한다.
2. **원문 위치 보존**(리서치 6.1의 `ObservedFact`)은 F5 검토 화면에서 "이 값이 문서 어디서 왔는가"를 보여 주는 핵심 기능이 된다. 과제에 명시되지 않았지만 검토 시간을 줄이는 차별점이다.
3. **`pass / fail / unknown / not_applicable`** 판정 상태는 추출 실패가 등록 데이터에 조용히 섞이는 것을 막는다.
4. **합성 데이터 + 정답 라벨 + 시드 고정**은 O3(추출 정확도 평가)의 기반으로 그대로 쓸 수 있다.
5. **HITL·감사 로그**는 "담당자 검토 후 최종 등록" 흐름과 맞다.
6. **평가 엄밀성**(리서치 9장: 데이터 분리, 일대일 매칭, end-to-end와 검증기 단독 구분)은 과제 평가에도 그대로 적용된다.

### 3.2 어긋난 부분

| 심각도 | 문제 | 영향 |

## 4. 개선 방향 선택지

| 안 | 내용 | 장점 | 단점 |
|---|---|---|---|
| **A (권장)** 중심축 재배치 | 도메인은 선박 기자재로 유지. 주 흐름을 "문서 → 추출 → 클래스 매핑 → 정규화 → 검증 → 중복 검사 → 검토·수정 → 등록(JSON/DB)"로 재정의. 규제 인용·POS 생성·변경 영향은 확장으로 | 과제 항목 전부 충족 가능. 기존 검증·근거 추적 자산 재사용. 도메인 차별성 유지. H3 부담 감소 | 계획서 1~7장 개정 필요. 기존 "Cohere×한화 POS PoC" 서사가 약해짐 |
| B 기존 계획 + 등록 모듈 추가 | spec-bridge는 그대로 두고 온톨로지·중복 검사·JSON 출력을 덧붙임 | 계획 변경 최소 | 범위가 과제보다 훨씬 커짐(6주 내 불가능에 가까움). 평가자에게 과제와 다른 프로젝트로 보일 위험 |
| C 일반 제조 도메인으로 전환 | 펌프·밸브·모터 등 범용 부품으로 새로 설계 | 과제 예시와 가장 가까움 | 그동안의 도메인 학습·리서치 자산 손실 |

안 A를 권장한다. 선박 기자재는 "제조 Product"에 해당하고, 과제가 요구하지 않는 규제 해석을 걷어내면 H3의 도메인 사실 위험도 크게 줄어든다.

## 5. 안 A 세부 개선안

### 5.1 간이 온톨로지 설계

과제 지침대로 **간이**하게 유지한다. OWL/RDF 같은 정식 온톨로지 언어는 쓰지 않고, YAML 정의 → Pydantic 모델·JSON Schema 자동 생성으로 시작한다. rdflib/SHACL은 확장 후보로만 둔다.

| 구성 요소 | 정의 내용 | 예시(구조 예시이며 실제 분류 체계 아님) |
|---|---|---|
| 클래스 계층 | `is_a` 트리, 5~8개 말단 클래스 | `Equipment > Engine > MainEngine2Stroke`, `Equipment > Engine > GeneratorEngine4Stroke`, `Equipment > Component > Turbocharger` … |
| 속성 | 이름, 데이터형, 단위 차원(pint), 필수 여부, 허용값·범위, 상속 여부 | `rated_power`: float, [power], required |
| 동의어·통제 어휘 | 속성명 별칭, 값 별칭(제조사명·연료명 등), 정규 표기 | `"MCR power"`, `"Max. continuous rating"` → `rated_power` |
| 관계 | 제품 간 관계, 카디널리티 | `has_component`(BOM), `manufactured_by`, `variant_of`, `compatible_with` |
| 식별 규칙 | 중복 판정용 자연키, 정규 제품명 생성 규칙 | `maker + normalized_model_designation` |

**H3 적용:** 클래스 구조·속성 목록은 프로젝트가 정한 **합성·가정** 정의로 명시한다. 실제 엔진 수치(출력 범위, SFOC 등)를 허용 범위로 쓸 때만 원문 출처를 요구하고, 없으면 `[미검증]`으로 둔다. 범위 검사는 출처가 확인된 값이 생길 때까지 형식·차원 검사로 제한한다.

### 5.2 파이프라인 재정의

```
문서 업로드(PDF/Excel/DOCX)
  → 파싱(Docling, openpyxl)            ─ 원문 위치 보존
  → 클래스 매핑(LLM + 키워드 규칙)       ─ 후보 클래스 top-k + 신뢰도
  → 속성 추출(클래스별 JSON Schema 구조화 출력)
  → 정규화(동의어 사전, pint 단위 변환, 형식 표준화)   ─ 결정론
  → 검증(클래스별 필수 속성, 단위 차원, 형식, 섹션 간 일치)   ─ 결정론
  → 중복·유사 검사(기존 등록 목록)
  → 검토·수정 화면(원문 위치 하이라이트, 값 수정, 중복 판정 확정)
  → 등록(SQLite 레코드 + 온톨로지 기반 표준 JSON, 감사 로그)
```

기존 계획의 Extractor·Rule Checker·HITL·Audit가 이 흐름에 그대로 들어간다. Clause Judge·Citation Guard·Drafter·Impact Analyzer는 빠진다.

### 5.3 중복·유사 검사 설계

| 단계 | 방법 |
|---|---|
| 블로킹 | 같은 클래스(또는 상위 클래스) 안에서만 비교 |
| 정확 중복 | 정규화된 자연키 일치 |
| 유사 후보 | 핵심 속성 거리(단위 정규화 후 상대 오차) + 제품명 임베딩(bge-m3) 또는 문자열 유사도 결합 |
| 판정 | `duplicate / similar / new` + 근거(일치·차이 속성 목록). 자동 병합은 하지 않고 검토 화면에서 확정 |
| 데이터 | 기존 등록 목록 샘플(합성) 100~200건 + 의도적 중복·근접 변형 쌍 라벨 |

### 5.4 평가 재설계 (O3 중심)

성공 기준을 과제 산출물 기준으로 바꾼다. 아래 목표 수치는 **프로젝트가 정하는 제안값**이며 근거 자료로 확정된 값이 아니다.

| 신규 목표 | 지표 | 제안 목표 |
|---|---|---|
| G1' 속성 추출 | 필드 단위 P/R/F1(정규화 후 값 일치), 단위 정확도, 원문 위치 정확도 | F1 ≥ 0.90 |
| G2' 클래스 매핑 | top-1 정확도, 클래스별 혼동 행렬 | ≥ 0.95 |
| G3' 검증 | 주입한 필수 누락·단위·형식 오류의 재현율, 정상 문서당 오탐 | 재현율 ≥ 0.95 |
| G4' 중복 검사 | 라벨된 쌍 기준 P/R | R ≥ 0.90, P ≥ 0.80 |
| G5' 설계 정당화 | 비교 실험 표 | 아래 구성 |

비교 실험 구성(검증 비교 대신 추출 비교):

| 구성 | 설명 |
|---|---|
| A | LLM 단독, 자유 형식 추출 |
| B | + 온톨로지 기반 클래스별 JSON Schema |
| C | + 결정론 정규화(동의어·단위) |
| D | + 결정론 검증과 재추출 1회 |

리서치 9장의 엄밀성 규칙(데이터 계열 분리, 정답 정보 비노출, end-to-end와 단계별 결과 분리, 분모 공개)은 그대로 적용한다. 가능하면 "수작업 입력 대비 검토 시간"을 소규모로 측정하되, 표본이 작으면 시간 절감을 주장하지 않는다.

### 5.5 합성 데이터 재설계

| 항목 | 현재 | 제안 |
|---|---|---|
| 제품 다양성 | 주기관 1종 × 케이스 4 | 말단 클래스 5~8개 × 제품 5~8개 = 사양서 40건 |
| 형식 | 미정(Markdown/DOCX 렌더) | PDF(표·서술 혼합), Excel(사양 표·BOM), DOCX |
| 주입 변형 | 결함 D1~D7(규제 중심) | **표기 변형**(속성명 별칭, 단위 혼용, 숫자·날짜 형식, 제조사 별칭, 레이아웃 차이) + **오류**(필수 누락, 단위 차원 오류, 형식 오류, 섹션 간 불일치) + **중복**(기존 목록과 같은 제품의 다른 표기) |
| 라벨 | 결함 위치·유형 | 정답 클래스, 정답 속성값(정규 표기), 원문 위치, 오류 라벨, 중복 대상 ID |

기존 D3(내부 불일치)·D4(필수 누락)·R-UNIT은 그대로 살린다. D1·D2·D5·D6(규제·판본·변경 이력)은 확장으로 내린다.

## 8. 이번 산출물의 한계

- 과제 정의는 사용자가 제공한 스크린샷 한 장만을 근거로 했다. 과제의 평가 기준·배점·제출 형식은 확인하지 못했다.
- 정합도 50%는 항목 수를 단순 합산한 참고 지표이며, 과제 평가자의 가중치를 반영하지 않는다.
- 5장의 온톨로지 클래스·속성 예시는 구조 설명용이며 검증된 도메인 분류가 아니다. 목표 수치는 제안값이다.
- 계획서·리서치·체크리스트는 수정하지 않았다. 구현·실험은 하지 않았다.
